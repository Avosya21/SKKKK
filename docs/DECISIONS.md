# Зафиксированные решения SKKKK

Эти решения не пересматриваются без явного запроса пользователя.

## Конкретные модели (двойной слух + диаризация)

| Роль | Модель | Вход | Запуск |
|---|---|---|---|
| Текст (канон) | Parakeet-TDT 0.6B v3 (`nemo-parakeet-tdt-0.6b-v3`) | 16 кГц моно | `venvs\lab`, ONNX (`asr/lab_pipeline.py`) |
| Кто говорит | Nemotron 3 Diarization (`nvidia/Nemotron-3-Diarization`), до **8** спикеров; откат — Sortformer 4spk v2.1 ONNX (`DIAR_MODEL=sortformer4`) | 16 кГц моно | `venvs\nemo-diar` отдельным процессом из стадии `03_diar` (`asr/lab/nemotron_runner.py`); Sortformer — `venvs\lab` |
| Второй слух | [ai-sage/GigaAM-v3](https://huggingface.co/ai-sage/GigaAM-v3), ревизия `e2e_rnnt` | 16 кГц моно | контейнер `skkkk-gigaam` — сверка/вычитка, не таймлайн |
| Голос | WeSpeaker (`pipeline._embedding` в GigaAMGUI) | клипы | `skkkk-gigaam` docker exec |

Контейнеры Whisper (`skkkk-whisper`) и T-one (`skkkk-tone`) **на диске остаются** (откат), воркер их **не** вызывает. Compose: [../asr/docker-compose.yml](../asr/docker-compose.yml).

GigaAM в Docker — клон `vendor/GigaAMGUI` (CUDA 12.4, torch 2.6+cu124, `onnxruntime-gpu`, официальный пакет GigaAM). Хостовый порт 18102, внутри контейнера 8000. Токен Hugging Face только из `.env` (`HF_TOKEN`), ключ REST — `GIGAAM_API_KEY`.

## Инварианты

1. **Двойной слух, не тройной ансамбль.** Канон после загрузки — лабораторный контур: Parakeet-TDT (слова и таймлайн) + диаризация Nemotron 3, до 8 спикеров (кто говорит; откат — Sortformer 4spk) + Cursor (спорные спикеры и вычитка) + свой прогон GigaAM (второй слух) + WeSpeaker (голоса в `speaker_profiles`). Whisper, T-one и LLM-склейка окон 120–180 с **не вызываются**.
   - Изоляция: всё в `artifacts/{id}/lab/runs/{run_id}/`, `LabRun.resolve()` не выпускает путь наружу.
   - GigaAM не становится нарезкой: в вычитке модель выбирает только lab vs giga.
   - Диаризация: Nemotron 3, **не больше 8 спикеров** (решение пользователя 2026-09-25, проверено на слух на созвоне проекта 35). Каналы с малым объёмом речи не отбрасываются — это реальные люди. Пороги у каждой модели свои: `asr/lab/diar_models.py`.
2. **LLM — два допустимых провайдера** (`LLM_PROVIDER` в `.env`, выбор при старте `python -m app.app.main`):
   - **`lmstudio`** (по умолчанию): модель **`LMSTUDIO_MODEL`** (сейчас `qwen/qwen3.8-27b`), LM Studio `http://127.0.0.1:1234/v1`, клиент OpenAI-compatible (`api_key=lm-studio`). Не дублировать ту же модель в Ollama, llama.cpp, vLLM. **JIT-автозагрузка в LM Studio выключена** — load/unload управляет оркестратор. Склейка с `reasoning_effort: none`.
   - **`cursor`**: Cursor SDK (`cursor-sdk`), `CURSOR_API_KEY`, модель `CURSOR_MODEL` (напр. `composer-2.5`). Текст созвонов уходит в Cursor API. Gemma в VRAM **не** загружается; шаги `gemma_load` / `gemma_unload` пропускаются.
   - **Единый код:** `app/app/services/llm.py`, ASR-скрипты — `asr/llm_client.py`. Один и тот же набор промптов и задач: sense/proof, выжимка, нормализация, сущности, ТЗ, чат, **vision для картинок** (Cursor: `UserMessage` + `SDKImage`).
   - **Не меняется:** Ollama-эмбеддинги, sqlite-vec, граф. Канон ASR — двойной слух (п. 1), не ансамбль из трёх движков.
3. **Эмбеддинги только через Ollama.** Модель уже стоит: `bge-m3`. Не тащить sentence-transformers на GPU.
4. **Всё живёт в `C:\1C_NEW_SKKKK`.** Код, план, правила, скилы, промпты, данные проектов, логи, venv, документация. Не писать артефакты проекта в `C:\app`, `C:\data`, home и т.п.
5. **Одна GPU, 24 ГБ VRAM, Windows 11.** В режиме **lmstudio** ASR и модель не пересекаются в VRAM на время GPU-шагов ASR: модель выгружается на шаг и загружается снова после него (`llm_keeper.asr_gpu_hold`; решение владельца 2026-10-05, Р1 по замеру — ниже «Две полосы локальной модели»). `LMSTUDIO_KEEP_DURING_ASR=true` — держать рядом, только если карта вмещает обе. В режиме **cursor** Gemma в VRAM нет, GPU только под ASR (и прочие локальные модели диаризации).
6. **Ollama `bge-m3` работает на CPU** (`num_gpu = 0`), чтобы не отбирать VRAM у LM Studio / ASR.
7. **Адреса как в Agent1C.** Web UI и API SKKKK — `http://127.0.0.1:1111`. Порт **8000 не использовать**: его занимает MCP 1С (`http://127.0.0.1:8000/mcp/`). Подробности: [AGENT1C-BRIDGE.md](AGENT1C-BRIDGE.md).

## Диаризация отдельно от ASR

Текст и «кто говорит» — два слоя. Три ASR дают слова. PyAnnote (сейчас через GigaAM) даёт интервалы спикеров. Склейка Gemma **не** выдумывает «Спикер 1/2» и **не** пересказывает: она восстанавливает битые слова ASR по смыслу и фонетике, оставляя исходные формулировки. После склейки слова накладываются на интервалы по пересечению таймкодов (`asr/speakers.py`).

- Диапазон участников неизвестен заранее, но на типичном созвоне задаём `min_speakers=4`, `max_speakers=8`: три похожих женских голоса при `min=2, max=15` схлопываются в одного, а порог ниже 0.50 раздувает 15 фейков. Точное число всё равно не фиксируем.
- Кластеризация: порог `0.52`, `min_cluster_size=6`. Микрокластеры короче 20 с отдаются **целиком** одному основному голосу (не каждый кусок — к ближайшему соседу по времени).
- **Голос обязателен привязан к спикеру, границы строятся заново по голосу, не по сырым интервалам PyAnnote.** Агломеративная кластеризация PyAnnote (`data/gigaam/dump_pyannote.py`, внутри контейнера `skkkk-gigaam`) используется только как затравка: по её длинным (≥2 с, суммарно ≥6 с) репликам на кластер строится голосовой центроид той же модели WeSpeaker, что уже в пайплайне (`pipeline._embedding`, cosine). Финальные интервалы «кто говорит» строит `resegment_by_voice` — скользящее окно (`RESEG_WINDOW_SEC=1.5`, шаг `RESEG_HOP_SEC=0.5`) по всей записи: каждое окно классифицируется по ближайшему центроиду при сходстве не ниже `RESEG_SIM_FLOOR`, а переключение спикера подтверждается только если новый голос держится подряд не меньше `RESEG_HOLD_SEC=1.2` с (гистерезис). Так метка спикера жёстко привязана к голосу: голос сменился и держится пару секунд — новый спикер, голос не менялся — один и тот же спикер, даже если сырые сегменты PyAnnote резали иначе. Без надёжных центроидов (мало длинной речи) — откат на сырые кластеры PyAnnote, это видно в `pyannote_segments.json` по полю `source`.
- Текст склейки Gemma **не** нарезается пропорционально по сырым островкам диаризации для UI. Часы — Whisper words → фразы; спикеры — Sortformer/PyAnnote по пересечению (`asr/timing_align.py`). См. раздел «Привязка текста к времени».
- Слой спикеров — **сырые интервалы PyAnnote/Sortformer**, не чанки GigaAM. У e2e RNNT часто нет word-timestamps, и тогда GigaAM вешает одного спикера на 18 с по середине чанка.
- Короткие чужие островки внутри длинной реплики того же голоса отбрасываются (`drop_contained_islands`). Пока интервал текущего спикера ещё длится, метка не прыгает на пересекающийся кластер (`flatten_overlaps`). Стыки короче 2.5 с схлопываются (`smooth_islands`).
- Имена вместо «Спикер №N» и слияние дублей — руками (и в HTML-просмотре), не автоматически.
- Навигация по стенограмме: клик по реплике ставит плеер, фильтр по человеку. Прототип: `python asr/build_transcript_view.py --serve` → `http://127.0.0.1:18104/out/transcript.html`.
- Диаризацию Whisper (sherpa) для «кто говорит» не используем: на реальной записи она режет десятки фейковых SPEAKER. Whisper остаётся источником текста.

## Sortformer + реестр голосов (2026-08)

- **Границы спикеров:** Sortformer v2.1 GGUF (OpenResearchTools Engine, Vulkan) — основной диаризатор вместо PyAnnote+resegment на новых созвонах. PyAnnote остаётся fallback/сравнение.
- **Sortformer не даёт текст** — только интервалы `SPEAKER_XX`. Флаг `--no-transcription` в `run_sortformer_gguf.ps1` обязателен для диаризации; это не ASR. Четвёртый вариант для Gemma из Sortformer **невозможен**. Engine умеет опционально Whisper-транскription, но это дубль контейнера `skkkk-whisper`, не Sortformer.
- **Три ASR + Gemma** — снято (2026-08-26). Канон — двойной слух, см. инвариант 1.
- **Верификация голоса:** WeSpeaker (`pipeline._embedding` в `skkkk-gigaam`) — cosine с `speaker_profiles` в SQLite. Скрипты: `data/gigaam/embed_voice.py`, `asr/match_sortformer_speakers.py`, логика `asr/speaker_registry.py`.
- **Базы голосов:** `scope=project` (отдельно на проект, эталон — project 1) и `scope=global` (общая, позже). Автоимена — **подсказка** (`status=suggested`), подтверждение в UI; без silent override.
  - *Уточнено 2026-09-24 (R3, `plans/AUTO-REVIEW-PLAN.md`):* голос с cosine лучшего кандидата ≥ `VOICE_AUTO_ACCEPT_MIN` (0.85) **и** отрывом от второго ≥ `VOICE_AUTO_ACCEPT_MARGIN` (0.10) принимается автоматически с пометкой `matches[label].auto`. Отрыв считается до лучшего кандидата **другого человека**: профили одного человека по `voice_aliases` («Заказчик 2 Клиент Б» → «Сергей Орлов») пропускаются — иначе отрыва нет никогда (прод 2026-09-24). На истории 33 из 80 голосов, 0 расхождений с человеком; в журнал пишется разбор каждого голоса (`speakers.auto_checked`). Профиль при этом не дообучается и в global не синхронизируется. Карточка голоса показывает «узнан автоматически», человек может переназвать. Остальное — подсказка; подсказка имени от модели по обращениям в тексте (`llm_hint`) — тоже только подсказка.
- **Алгоритм:** длиннейший чистый кусок каждого `SPEAKER_XX` (≥2.5 с, без overlap) → embedding → match/merge дублей (≥0.82) → match профилю (≥0.72).

## Voice turn audit (автопроверка меток, 2026-08)

После нарезки реплик и match, **до** `transcript_ready` / индекса: WeSpeaker сверяет каждую реплику ≥2 с с leave-one-out центроидами спикеров этого же созвона.

- Почти уверенный чужой голос (`cosine(best) ≥ 0.88` и `best − current ≥ 0.12`) → **auto_reassign** метки реплики без UI.
- Серые случаи не трогаем. Короткие реплики и единственный спикер — skip.
- Пишет `voice_audit.json`, бэкап `docker_gigaam_speakers.before_audit.json`, обновляет `_speakers` / smooth / merged txt для индекса.
- После enroll/merge — повторный audit; если были auto-правки и артефакт уже `indexed+` — сразу reindex чанков.
- Не заменяет диаризацию. На новой линии после cutover не вызывается: спикеров держит Sortformer + sense + WeSpeaker.

## Защита от чужого Tone / перепутанных raw (2026-08)

**Обязательный staging:** перед T-one и GigaAM embed WAV копируется из `SKKKK_ASR_WORK`
(каталог арtefactа) в `asr/work` (`asr/docker_stage.py`). Контейнеры видят только mount
`asr/work` → `/data` или `/work`; без staging они читают **stale** файл прошлого job.

**Проверка после staging:** `assert_docker_work_matches` — размер + SHA256 источника и копии.

**Второй рубеж:** перед align/merge `engine_timeline.tone_for_align` отбрасывает Tone,
если длительность или лексика начала не совпадают с Whisper/GigaAM (rescale только при
overlap ≥ 0.35). Иначе LLM честно склеит чужой созвон поверх таймлайна этой записи.

**Parsed-копии:** `finalize_audio_outputs` всегда перезаписывает `parsed/*_raw_*.txt` из
`artifacts/.../asr/` (раньше stale-копии не обновлялись, если файл уже существовал).

## Привязка текста к времени (2026-08)

Склейка Gemma идёт **окнами без посекундных таймкодов**. Готовый текст склейки — **единственный источник слов** для UI и `_final.txt`.

Канон доверия (не смешивать слои):

| Слой | Источник | Что даёт |
|------|----------|----------|
| **Текст** | только окна Gemma (`docker_merged_windows.json`) | что сказано |
| **Часы** | monotonic alignment Gemma ↔ Whisper words; на петле Whisper — Tone или интервалы спикеров | когда сказано |
| **Кто** | Sortformer/PyAnnote, `overlay_text` по пересечению | кто сказал |

Запрещено: подставлять в финал сырой Whisper/Tone «как правку» или частично заменять фразы Gemma на Whisper. Иначе нельзя доверять следующей расшифровке — непонятно, чей это текст.

Петля Whisper (одна фраза × минуты): такие **часы** отбрасываем, сетку берём у Tone/спикеров, **текст всё равно из Gemma** на этом интервале.

Нарезка Gemma по часам — **не** пропорционально длительности (`split_text_by_weights` запрещён в финальном пути). Внутри окна: выравнивание токенов/предложений Gemma с Whisper words (порядок времени), сироты Gemma не удаляются — время интерполируется между соседями или границами окна. Бюджет плотности режет текст **только** на этапе merge (до/после LLM); в `align` / финальном UI текст склейки не урезаем.

Петля Whisper на хвосте (одна фраза × минуты) даёт большую «дыру» в часах: предложения окон Gemma раскладываются **равномерно по Tone-сегментам внутри каждого окна**, а не на первые N сегментов всей дыры (иначе UI обрывался ~на 35 мин при аудио ~41 мин, хотя `docker_merged_plain.txt` был полным).

После удлинения склейки (remerge) часы якорятся к **тексту Tone/ASR-сегментов** и Tone-токенам в окне, а не к равномерной сетке по счётчику предложений — иначе клик по нижней части стенограммы открывает чужой фрагмент.

**2026-08-24 — LLM Cursor API:** `LLM_PROVIDER=cursor` — merge/склейка через Cursor API (`cursor-sdk` в venv), не локальная Gemma. ASR-скрипты с LLM: `venv\Scripts\python.exe`, не голый `py`. Правило: `.cursor/rules/08-llm-cursor.mdc`.

**2026-08-24 — timing UI:** если `clock_source=tone`, align использует **только Tone-токены** (`prefer_tone_clock`), без Whisper words и без tone-supplements; длинные слоты режутся по `_cap_turn_spans_by_text`.

**2026-08-25 — timing UI (Tone-клик + gate):** после align при `prefer_tone_clock`: коррекция швов окон (`correct_seams_by_tone`), привязка к Tone (`snap_turns_to_clock`), нарезка длинных реплик по Tone (`split_long_turns_at_tone`), якорь клика `seek_start` (`apply_tone_seek_anchors`). HTML кликает по `data-seek`. `transcript_integrity.json`: реплики >25 с, unpunctuated blob >400 символов, drift клика vs Tone; `status=fail` блокирует `transcript_ready` и индекс.

Ошибки «кто говорит» при одновременной речи допустимы. Вырезание целых фраз Gemma и показ петли Whisper вместо склейки — нет.

Запасной путь без timed ASR — `carve`/`apply_merged_windows` (хуже по клику); не считать нормой, если есть Whisper words.

## Защита от галлюцинаций ASR на тишине (2026-08)

Опасный класс багов: Whisper (реже другие движки) на паузе «додумывает» правдоподобный текст; Gemma сохраняет его, потому что он уже есть в черновике; `apply_merged_windows` / `carve_text_by_speakers` втискивают простыню в короткие острова диаризации → в UI абзац за 4 секунды.

Инварианты защиты (таймлайн исходного аудио **не** сжимаем — плеер должен совпадать с файлом):

1. **До Gemma** (`asr/hallucination_guard.py` + `merge_ensemble.py`): схлопнуть соседние повторы фраз; выкинуть loop Whisper; если в окне почти нет речи и жив только один движок — окно не слать в LLM.
2. **Бюджет речи** считать по **Sortformer/PyAnnote**, не по 18 с чанкам GigaAM; энергия WAV режет тишину, но при согласии 2+ движков не должна съедать тихий VoIP (`silence_energy.resolve_speech_budget_sec`).
3. **После Gemma**: обрезать текст окна бюджетом `speech_sec × 20 символов/с`, но если живы **2+** ASR-черновика — бюджет не ниже объёма самого длинного черновика окна (иначе режется реальный финал/прощание при заниженном diar speech_sec). Тот же пол — в `prepare_engine_texts` до LLM, чтобы Gemma видела полный черновик.
4. **При навеске на спикеров**: meta/loop scrub без урезания содержания Gemma; densе-cap на репликах UI **не** режет канон склейки (см. «Привязка текста к времени»).
5. Полный Silero-VAD с вырезанием пауз из WAV — отдельно, только если позже понадобится экономия ASR; сейчас режем ложный **текст** на этапе merge, не дорожку.

Пороги и эвристики можно ужесточать; отключать слой защиты без явного решения пользователя нельзя.

## Итоговая выжимка созвона

В самом начале HTML-страницы просмотра (`asr/transcript_view.py`) — блок с итоговой выжимкой созвона: **протокол встречи** (позиции сторон, тематические блоки, итог, таблица Кто/Что, не закрыто).

- Строится **только из текста финальной стенограммы** (`docker_gigaam_speakers.json` — реплики после proof и подписи имён). Аудио и видео для выжимки не анализируются.
- Генерирует **LLM** (lmstudio или cursor — см. инвариант 2), промпт `docs/prompts/call_summary.md`, скрипт `asr/summarize_call.py`. Запускать **после** confirm спикеров и индекса. В режиме lmstudio — Gemma должна быть загружена (фаза LLM, не во время ONNX/GigaAM). В режиме cursor — load Gemma не нужен.
- Длинный созвон не помещается в контекст одним запросом: стенограмма режется на фрагменты ~6000 символов по границам реплик, по каждому фрагменту LLM делает черновые заметки (map), затем один запрос сшивает заметки в протокол (reduce). Короткий созвон (один фрагмент) идёт в reduce напрямую, без прохода map.
- Reduce — до **4096 tokens** (map ~1200). Пустые разделы в ответ не включаются.
- Результат кладётся в `asr/call_summary.md` и рендерится в HTML простым markdown (`##`/`###` заголовки, списки `- `, таблицы).

## Prod-стенограмма (cutover 2026-08-26)

в статусах (`asr_running` → `speakers_pending` → после confirm knowledge).
Метка диаризации — `speaker_N`. CLI `asr/lab_voice.py` по-прежнему только
слепки; enroll/merge — кнопки UI.

Причина появления — три конкретных дефекта старого пути, закрытые архитектурно:

1. **Подмешивание файлов.** Глобальные `asr/work` и `asr/out` с фиксированными
   именами перезаписывались между прогонами. В лаборатории всё живёт в
   `artifacts/{id}/lab/runs/{run_id}/`, а `LabRun.resolve()` физически не умеет
   вернуть путь наружу.
2. **Тихие fallback'и.** Раньше при отсутствии файла подставлялся файл из
   другого прогона. Теперь нет входа — `MissingInput` с именем файла.
3. **Придуманные фразы на тишине.** Вместо вычищения текста постфактум:
   TDT-декодер вместо авторегрессионного, а стадия `07_verify` вторым проходом
   через Silero VAD показывает слова, попавшие в тишину, и расхождение проходов.
   *(уточнено 2026-09-28, решение пользователя: провал проверки — только если
   больше 2% слов лежат **на тишине**, то есть звук под словом на 20 дБ тише
   обычной речи записи или тише −50 дБFS. Слова на громком звуке, который VAD не
   принял за речь, дают `warn` с участками времени и обработку не останавливают.
   Повод — созвон проекта 40: 3 минуты голоса, искажённого сбоем связи, не
   услышали ни VAD, ни диаризация, а прежнее правило остановило всю запись.)*

Что зафиксировано и не меняется молча:

- **Порядок ASR → диаризация**, не наоборот. Если диаризация промахнётся мимо
  тихой реплики, при обратном порядке текст будет потерян навсегда.
  Длинный файл режется на окна ≤80 с с перекрытием: ONNX Parakeet держит
  ~100 с позиционных эмбеддингов. Это не VAD и не отбрасывание тишины.
- **Sortformer отдаёт вероятности, а не сегменты.** Пороги бинаризации —
  параметр стадии, перебинаризовать можно без повторного инференса. Внутренние
  эмбеддинги Sortformer — не слепки голоса и для сверки между записями непригодны.
- **Слепки голоса считает WeSpeaker** в контейнере `skkkk-gigaam`, тот же, что
  наполнил `speaker_profiles`. Другая модель обесценит уже сохранённые профили.
- **Пропуск стадии — по отпечатку** (sha256 входов + параметры), не по mtime.
- **Спорные и бесхозные слова остаются в тексте** с пометкой. Молчаливая раздача
  их ближайшему спикеру и порождала ощущение «текст подмешался».
- **Снимок 2026-08-26** (`asr/lab/FREEZE.md`, эталонный прогон
  `20260826T174104Z_48a796`). Три принятых этапа, ни один не переписывается молча:
  1. конвейер 01–07 без DeepFilterNet (Python 3.10.9, onnx-asr 0.12.0,
     onnxruntime-gpu 1.23.2, Parakeet-TDT v3, Sortformer 4spk v2.1);
  2. прогон Cursor — смысловая разноска в `sense/` (`asr/lab_sense.py`,

- **Этап 3 лаборатории — сверка с GigaAM, а не переход на его нарезку.**

## Роли (пароли)

Три общих пароля (хеши в `.env`): `admin`, `manager`, `user`.

Вход только для логинов из `Login_up.txt` (без учёта регистра). Пароль роли регистр сохраняет.

**Роль = пароль этого входа.** Какой из трёх паролей ввели — такую роль пишем на учётку (новый логин и повторный вход). Разослали менеджерский пароль — человек заходит менеджером; админский — админом. Свой старый хеш в БД для входа не используется.

Поле `position` на пользователе (не пароль): `customer` | `analyst` | `developer` | `manager` | `admin`. Права определяет `role` от пароля, не `position`.

**Изоляция проектов.** Admin видит все. Остальные — проекты своего логина: создал (`created_by`), загрузил файл, писал в чат или есть строка в `project_members`. Роль от пароля на это не влияет: зашли менеджером или user — свои проекты на месте. Чужой без следа логина или неактивный — **404**. Удаление проекта — admin или создатель.

**Выдача доступа.** Блок «Выдать доступ» на странице проекта (после MCP). В проект можно добавить любого логина с ролью `manager` или `user`. Портального admin через этот список назначить нельзя. Кто в списке — видит проект и действует по роли в проекте. Пароль роли `user` — нет match, MCP и «Выдать доступ», даже если человек создатель проекта.

**Лаб только admin.** Кнопка **лаб**, `GET /report-lab`, файлы прогона и lab enroll/merge — 403 для manager/user даже на своём файле.

**Match и «Пересобрать» файла.** enroll / merge / confirm / recalculate / rebuild-summary / reindex — admin и manager на своих проектах. Роль `user` — 403. «Пересобрать ТЗ» — только admin. Скрытие кнопки в UI недостаточно: те же правила на каждом API (`project_access.py`).

## Meeting Mind (2026-09-12)

Встреча — новый мультимодальный источник данных для существующего конвейера, не вторая система знаний. Своих RAG, графа и базы знаний у неё нет. Ниже — решения, принятые до начала работ.

### Двойной слух на нативных дорожках сохраняется целиком

- Каждая дорожка участника проходит **полный** контур: Parakeet → sense → GigaAM → reconcile → proof. Урезать второй слух ради скорости нельзя.
- **Sortformer на дорожке не запускается.** Одна дорожка — один человек, говорящий известен из participant mapping LiveKit. Sortformer остаётся для внешних смешанных записей, fallback, валидации и подозрительных сегментов (несколько голосов на дорожке, потеря metadata).
- Цена принята осознанно: воркер один, дорожки идут последовательно. Встреча на N участников — N прогонов; часовая встреча на четверых занимает воркер примерно как четыре часовых созвона.
- Канон текста тот же — `proof`, не сырой timeline GigaAM.

### Живой звук комнаты ≠ денойз расшифровки (пересмотрено 2026-10-05)

- Шумодав голоса — **в браузере говорящего**: DFN3 (WASM, `static/vendor/dfn3`) стоит процессором livekit-client на микрофоне, после эхоподавления браузера. Слушатели получают одну, уже очищенную дорожку человека; задержка шумодава ~20 мс. Кнопка «Шумодав» включает и выключает фильтр у себя, серверу ничего не сообщает.
- Рядом браузер публикует **сырую** дорожку `skkkk-raw` (тот же захват до DFN3, без шумоподавления браузера) — только для записи: люди на неё не подписываются.
- Нет DFN3 (телефон, нет WASM/AudioWorklet, не загрузился) — шумоподавление браузера, одна дорожка; её же пишет рекордер.
- Почему не сервер: прежняя схема (бот `skkkk-dfn` чистил каждого и публиковал `clean-*`, слушатель выбирал между сырой и очищенной) добавляла 0,25–0,56 с, давала эхо и задвоение (находки 80–89, разбор 2026-10-05) и так не делает ни один из сравнённых проектов (LiveKit+Krisp, Jitsi, Janus, Pipecat).
- `tools/livekit/voice_cleaner.py` (участник `skkkk-dfn`, имя историческое) — **только рекордер голоса**, ничего не публикует. DeepFilterNet/torch на сервере не нужны.
- На `01_audio` / Parakeet / GigaAM денойз не включать: он уже срезал согласные.

### Архив созвона — сырые дорожки, связанные комнатой

- Канон записи — **сырой** микрофон (и экранный звук) каждого человека: дорожка `skkkk-raw`, а без неё (телефон) — основная. Шумодав в комнате и архив для двойного слуха — разные дорожки.
- Все дорожки одного созвона лежат в `data/meetings/{room_name}/` и перечислены в `manifest.json`. Связь с встречей — `meetings.room_name`. Identity из LiveKit (`member:{id}`, `guest:{hex}`).
- `MEETING_RECORD=0` выключает запись. Удаление проекта сносит и этот каталог. ASR с дорожек стартует кнопкой **Проанализировать**, не в момент записи. Канон встречи — одна стенограмма: дорожки по отдельности (без Sortformer, имена из LiveKit), склейка по таймкодам, одно аудио.

### Стенограмма созвона — track-first и проверяемый источник (2026-09-13)

- Production meeting pipeline атрибутирует речь **по native-дорожке** LiveKit, не угадыванием LLM.
- Leak detection работает **до** финальных реплик. Удалённые фрагменты пишутся в `proof/leaks.json` с причиной и методом (`rank` / `rms` / `diarization`). Молча выкидывать текст нельзя.
- Если rank и RMS неоднозначны, локальный diarization fallback — **только на спорном окне**. Нет уверенности → `CONFLICT` / `UNRESOLVED`, текст не удаляется и не получает выдуманного имени.
- Два человека в один микрофон: несмапленный кластер = `unknown`, не имя предыдущего участника. `A→B→A` нельзя принять как `A→A→A`.
- Screen-share audio — отдельный source channel. Издатель экрана ≠ говорящий в видео; без доказательства имя не ставится (`external_or_unknown`).
- Call-derived `decision` / `task` / `fact` из комнаты привязываются к реплике (`source_span_id`). Нет совпадения — сущность остаётся с `needs_review` и пустым span, не удаляется. Текст из `leaks.json` в БД не пишется.
- `NO_DATA` не считается `PASS`. Старые созвоны без `started_epoch` / `events.jsonl` честно серые.
- Пока нет новой живой записи, приёмка уровня B (контрольный созвон A–I) закрывается синтетическим пакетом `test_meeting_control_call.py` + unit/integration без GPU. Живые метрики `speaker_sync` p50/p95 появятся только после следующего реального созвона.

### Контракт созвона и провенанс (2026-09-13)

- Каждая опубликованная существенная фраза имеет дорожку, говорящего и время. Недостаточно данных → `WARN` / `CONFLICT` / `UNKNOWN`, имя не выдумывается. `NO_DATA` ≠ `PASS`.
- Провенанс сущности — в `Entity.value_json` (`speaker`, `speaker_source`, `start_sec`, `end_sec`, `decided_by`, `source_span_id`, `text_hash`, `recorded_at`, `source_status`). Отдельной таблицы нет. Реплики созвона в БД тоже не копируются: единственный источник — `_final.txt`, код читает его через `transcript_turns.load_turns` (кэш по mtime). У чанка хранится только его отрезок времени (`chunks.start_sec`, `end_sec`). *(уточнено 2026-09-23)*
- Фильтр knowledge (`filter_call_payload`) и `needs_review` для непривязанных — только для встречи из комнаты: `source_type=call` и есть реплики с `source_span_id` (`speaker_source: "track"` — имя по дорожке, доказательство). Перефраз — `_text_overlap`; без совпадения — `needs_review`, не удаление. `summary` не обнуляется. Текст из `leaks.json` в сущности не пишется.
- Созвоны из загруженных файлов тоже получают `speaker` / `start_sec` / `end_sec` по репликам канона, но с `speaker_source: "voice"` (опознание по голосу — вывод, не доказательство); без совпадения — `source_status: "unbound"`, без `needs_review`. Говорящий `unknown` не превращается в имя (`speaker: null`, `source_status: "speaker_unknown"`). Чат и контракт показывают источник атрибуции. *(2026-09-23)*

### Кто и когда в чате проекта (2026-09-23)

- Повод: чат не мог сказать, кто и когда принял решение — таймкод срезался при нарезке, реплики дробились по смене говорящего, у фрагментов не было ни файла, ни даты, у решений загруженных созвонов — ни говорящего, ни времени. ### Автопроверка локальной моделью (2026-09-24)

- Повод: из 1524 решений/задач человек подтвердил 19, из 59 конфликтов не разрешено ни одного — очереди не разбирались. План: [`plans/AUTO-REVIEW-PLAN.md`](plans/AUTO-REVIEW-PLAN.md).
- Модель (та же LLM, что у воркера) проверяет требования по источнику и конфликты по двум источникам и датам; человеку — только «не уверена» и контрольная выборка (каждое `AUTO_REVIEW_AUDIT_EVERY`-е решение).
- Решение модели отличимо от человеческого: `value_json.model_review` / `links.model_review`, `needs_review` по-прежнему значит «человек не смотрел», человек главнее модели. В контракте — третье значение `verification: model_confirmed` («проверено моделью, не человеком»).
- Ничего не удаляется: отказ модели выключает (`is_active=false`), разрешение — `Resolution(status=model_resolved|model_dismissed, resolved_by=NULL)`; любое решение модели отменяется «Вернуть».
- Режим `AUTO_REVIEW_MODE`: `shadow` (по умолчанию — вердикты без последствий) → `live` только после разметки выборки человеком (`scripts/eval_auto_review.py`: ложное подтверждение ≤ 5 %, ложное отклонение ≤ 2 %, «не уверена» ≤ 25 %). Live применяет уже записанные теневые вердикты без повторного вызова модели.
- Фоном: задачи очереди `kind=auto_review` / `refresh_knowledge` всегда после расшифровки; чат обработка не блокирует (с 2026-10-05, Р2 — «Две полосы локальной модели»). Новые виды задач ставятся, только если запущенный воркер их понимает (`worker.started kinds=` в журнале): старый воркер выполнил бы любую задачу как расшифровку.
- Защиты по замеру: конфликт не выигрывает пункт, чей источник его не подтверждает (модель «объяснила» неверно извлечённый факт с уверенностью 0.95); конфликтом считаются только `decision`/`task`/`fact` — граф больше не помечает конфликтом пары участников/упоминаний (было 30 из 59), старые такие пары закрываются правилом без модели.
- Новые задачи модели — новые файлы промптов (`review_requirement.md`, `review_conflict.md`, `suggest_speaker_names.md`) с версией в вердикте: работающий процесс читает промпты с диска на лету (урок 2026-09-23).

### Противоречия решает система: правила вместо разбора по одному (2026-09-25)

- Цель — автономия: человек один раз задаёт правила и видит сводку важного, а не каждый конфликт. План: [`plans/CONFLICT-AUTONOMY-PLAN.md`](plans/CONFLICT-AUTONOMY-PLAN.md). Приняты рекомендации Р1–Р4 плана (пользователь, «приступай к полной реализации»).
- **Р1 — вес источника** (`services/conflict_rules.py`, кодом, без модели): документ заказчика (`priority_weight` ≥ 0.95) 3 > утверждённое решение созвона (`decided_by`) или внутренний документ 2 > высказывание 1 > вопрос/вариант 0. Противоречие без явной отмены — в силе более весомый, при равном весе более поздний. Явная отмена («передумали», «отменяем…») выключает прежнее, только если отменяющий пункт не слабее отменяемого или сам утверждён (вес ≥ 2): утверждённое на созвоне решение может явно отменить пункт документа, простое высказывание — нет, вопрос — никогда. Уточнение 2026-09-28 (ответ заказчика в переписке) — ниже, «Актуальность в ответе чата».
- **Р2 — модель называет отношение, не победителя** (промпт `review_conflict_v3.md`): отмена / противоречие / уточнение / одно и то же / разные объекты / не решение / неверно извлечено. Победителя выводит код по Р1. «Неверно извлечено» выключает пункт, только если и код не находит его в источнике (`_source_supports`).
- **Р3 — важное не блокирует:** авторешения по деньгам и срокам (`is_material_topic`) решаются сразу и попадают во вкладку «Важное» экрана конфликтов с «Вернуть».
- **Р4 — чат не просит уточнение из-за открытого противоречия:** обе версии с датами и источниками идут в контекст (`conflict_context`), модель называет обе и какая позже. Уточнение остаётся только для «документы vs созвоны без правила приоритета» (`source_split`). Чат и ТЗ получают противоречия хронологией («В силе / Раньше считалось / Основание»), не сырым `value_json`.
- Явная отмена без модели (`graph._try_auto_resolve`) — только конфликты своего артефакта, фраза — в источнике нового пункта, «новее» — по дате материала, человек главнее; решение отменяется «Вернуть». «Исправляем» больше не считается отменой.
- Связь конфликта без направления (A↔B — одна строка); пересборка графа не трогает решения человека.
- **Эталон — один на все проекты** (`data/eval/conflicts_gold.csv`), размечается один раз. Контрольный прогон `scripts/eval_auto_review.py --gold` обязателен при смене модели, промпта или извлечения; live — при 0 неверных победителей, ≥ 20 размеченных, «не уверена» ≤ 30 %. Пополнение — только парами, где человек нажал «Вернуть».
- **Автооткат:** больше 5 % «Вернуть» среди ≥ 10 авторешений проекта за 14 дней → `conflict_review_mode=shadow` в настройках проекта, решения снова ждут человека. Вернуть live — убрать ключ после контрольного прогона.

### Требования: понятные, с «кто и когда», актуальные (2026-09-27)

- План: [`plans/REQUIREMENTS-PLAN.md`](plans/REQUIREMENTS-PLAN.md). Решения А1–А10 приняты пользователем.
- **А1** устаревшее выключается обратимо (как проигравшая сторона конфликта, «Вернуть»); **А2** тема — потребность или объект, не способ решения; **А3** уже в тени устаревшее и дубли прячутся из «Ждут вас» на свои вкладки (прятать ≠ выключать); **А4** без известной даты записи замена автоматически не применяется (с 2026-09-28 дата загрузки считается датой материала — см. ниже); **А5** «выполнено» — только отметка.
- **А6 — смысл подтверждения.** «Подтвердить» = «верно извлечено, это звучало и было решено на тот момент». Защищает от вердиктов модели «не говорили / мусор / дубль», но не от замены более поздним материалом: подтверждено до появления заменяющего материала → замена применяется сама и попадает во «Важное»; подтверждено после → пара ждёт человека. В контракте у заменённого — статус `superseded` со ссылкой на заменивший.
- **А7** виды пунктов: требование к системе / решение по проекту / организационная задача / открытый вопрос. В очередь требований и контракт — только первые два; организационное — в «Задачи и сроки», вопросы — в «Вопросы к заказчику» и раздел ТЗ «Открытые вопросы и риски».
- **А8** формулировка понятна без созвона: объект + действие + условие или цель; рядом исходная цитата.
- **А9** у каждого источника — кто сказал и кто утвердил (со стороной), где и когда (дата записи + таймкод; переписка — автор и время сообщения). Неизвестное пишется честно; дата загрузки не выдаётся за дату встречи. Говорящий — из привязанных реплик; совпадение слов — запасной путь с пометкой.
- **Якоря источников (2026-09-28, план [`plans/SOURCE-ANCHORS-PLAN.md`](plans/SOURCE-ANCHORS-PLAN.md), решения Я1–Я5 приняты пользователем):** выгрузка Telegram разбирается на сообщения по разметке (номер, автор, время с поясом, ответ) и не нормализуется моделью; **Я1** сообщение из двух пересекающихся выгрузок — источник только в самой ранней загруженной, в поздней — контекст; **Я2** «утвердил» в переписке — другой участник ответом или следующим сообщением в пределах 10 сообщений и 24 часов; **Я3** созвон и сообщение одного дня сравниваются, только если у обоих известно время, иначе «неясно»; **Я4** ссылка на момент созвона перематывает плеер и подсвечивает реплику, звук — по кнопке; **Я5** ручная дата материала может быть со временем начала.
- **Дата нового материала — автоматически (2026-09-28):** встреча → имя файла (со временем — точность «минута»; «22.09.26 14-00-34», «14 мая») → метаданные записи → шапка документа («Дата: …», «… от …») → свойства файла (дата правки docx/xlsx/pptx/PDF/снимка; в интерфейсе с пометкой «проверьте») → дата загрузки. Ручная дата главнее любой автоматической и автоматикой не перезаписывается.
- **Дата загрузки — запасная дата материала (решение владельца 2026-09-28, уточняет А4 и А9):** у каждого материала есть дата; нет фактической — дата загрузки, и по ней решается «что сказано позже». В интерфейсе она подписана «по дате загрузки» и не выдаётся за дату встречи. Материалы, загруженные в один день без времени, по-прежнему «неясно» (Я3). Цена: документ, загруженный позже, чем был создан, может «заменить» более новое — такое видно на вкладке «Устарело» и возвращается кнопкой «Это актуально»; точную дату можно поставить вручную.
- **Автопроверка — боевой режим для всех проектов (решение владельца 2026-09-28):** `AUTO_REVIEW_MODE=live`, контрольная выборка выключена (`AUTO_REVIEW_AUDIT_EVERY=0`) — человеку идут только спорные пункты. Тень для отдельного проекта — `auto_review_mode=shadow` в его настройках; автооткат конфликтов (выше) продолжает действовать.
- **А10** старые материалы переизвлекаются по новой схеме по проекту; ручные подтверждения и статусы переносятся на новые пункты по цитате и репликам, не перенесённое — отчёт человеку. Это отменяет прежнее «старые созвоны массово не переводятся» для извлечения сущностей.

Отдельный certbot не ставим — EFF прекратил поддержку Windows в феврале 2024. Nginx из плана заменён на Caddy, второй прокси не заводим.
- Валидация только **HTTP-01 на порту 80**: TLS-ALPN на IP-адресах у Let's Encrypt нестабилен и в конфиге выключен. Снаружи `:443` не открываем.
- Публичный HTTPS — **`https://<IP>:777`** (`SKKKK_HTTPS_PORT`). Caddy слушает 777, портал — `127.0.0.1:1777` (`WEB_PORT`). На одном порту HTTP-01 и HTTPS не уживаются, поэтому роутер обязан слать внешний `:80` на `SKKKK_ACME_HTTP_PORT` (8088), а не на 777.
- Почему HTTPS обязателен: браузер отдаёт `getUserMedia` / `getDisplayMedia` только в защищённом контексте. `https://IP:777` для браузера достаточен, адрес без `:777` — нет.
- **Uvicorn слушает только loopback** (`WEB_HOST=127.0.0.1`). Наружу смотрит один Caddy.
- Цена решения: сертификат живёт шесть дней, Caddy продлевает примерно раз в двое суток. `main` при старте проверяет файл `:777`: нет файла, просрочен, staging или до конца меньше `SKKKK_TLS_RENEW_HOURS` — просит Caddy перевыпустить на `SKKKK_ACME_TLS_PORT` (8443). Нужен живой HTTP-01 на `:80`. Если Let's Encrypt не ответил, портал на loopback всё равно поднимается.

### Повторное использование ID встреч — не мигрируем (2026-09-18)

- В SQLite без `AUTOINCREMENT` номер удалённой встречи может достаться новой. Проверено: имя комнаты (`_room_name()`) и гостевой токен случайные и от ID не зависят; ID виден только сотруднику в адресе `/projects/{pid}/meetings/{id}/room`.
- Риск — старая закладка сотрудника может открыть другую встречу того же проекта. Данные гостей и записи от этого не страдают, поэтому миграцию схемы на `AUTOINCREMENT` не делаем. Вернуться к вопросу, если ID начнут попадать в публичные ссылки или внешние системы.

### `public_payload()` не отдаёт `project_id` гостю — намеренно (2026-09-18)

### Время: хранить UTC, показывать в поясе пользователя (2026-09-18)

- Факт: БД и API пишут время в **UTC без метки пояса** (`2026-09-18T20:27:48`), а имена версий ТЗ (`current_tz_…_2307`) и часть логов используют **местное** время сервера (сейчас UTC+3). Браузер читает ISO без `Z` как местное, поэтому любое время события из API на экране сдвинулось бы на 3 часа.
- Сегодня в UI времена событий не показываются (только даты дедлайнов без времени), поэтому видимого расхождения нет.
- Правило на будущее: (1) в БД — UTC; (2) когда экран начнёт показывать время, API обязан отдавать ISO **с `Z`**, а клиент форматировать через `toLocaleString` в поясе пользователя; (3) имена версий ТЗ остаются местным временем — это имя файла, а не данные. Нарушение правила ловить тестом на сериализацию, а не правкой каждого экрана.

### Модель ролей: роль сессии в токене (2026-09-18)

### Личный пароль пользователя (2026-09-26)

- Вход в два шага: логин + Telegram ID + **пароль роли** (роль по-прежнему определяет он) → затем **личный пароль** логина. Нет личного пароля — придумать его (два поля). Что у логина нет пароля, узнаёт только знающий пароль роли.
- **Telegram ID скрыт с формы входа (решение владельца 2026-09-28, «пока что»):** учётку определяет логин, а Telegram ID нужен только для уведомлений о готовности файла, бот не настроен (`TELEGRAM_BOT_TOKEN` пуст) — уведомления не уходят. Сервер принимает вход без него: указанный — пишется на учётку, как раньше; без него у учётки остаётся прежний, у новой — заглушка `pending-<логин>` (столбец обязательный и уникальный). Поле скрывает маршрут `pages.login_page` (`hide_telegram`), а не шаблон: шаблон подхватывается с диска сразу, код — только после перезапуска, и старый код без поля не пустил бы (так и случилось на пару минут 2026-09-28 — поле вернули до перезапуска). Вернуть поле — убрать `hide_telegram`.
- Режим `PERSONAL_PASSWORD`: **`required` — по умолчанию и всегда** (без личного пароля не войти; сессии, выданные без него, перестают действовать); `off` — только тесты и аварийный откат. Режим `optional` («Позже») убран 2026-09-26 решением владельца.
- Хеши — Argon2id, в отдельной базе `data/credentials.db` (не `app.db`), по логину из `Login_up.txt` без регистра. Пароли в открытом виде нигде не пишутся.
- Правила пароля: 10–128 символов, не равен логину и ни одному паролю роли; без требований «заглавная/цифра/символ».
- **От «захвата» не защищаемся** (решение владельца): кто первым знает пароль роли и логин без личного пароля, может задать пароль за другого. Людей мало, при захвате админ сбрасывает пароль.
- Сброс — пункт **7** меню запуска `main` в PyCharm или `scripts/personal_password.py`; страницы пользователей в портале нет. Смена и сброс увеличивают версию пароля (`pv` в токене) — старые сессии логина перестают действовать.
- Одним логином пользуется один человек (предположение; иначе личный пароль придётся знать всем).

### Карточка пользователя (2026-09-26)

### Индекс проекта: отдельная БД, локальный MCP, без GPU (2026-09-21)

При сбое модели порядок остаётся гибридным. Замеры — `scripts/eval_index.py [--holdout] [--rerank]`.
- Карта не должна расходиться с кодом: реестр модулей в `PROJECT-MAP.md` генерируется (`check_map_drift.py --fix`), тест-сторож падает при новом файле без записи, мёртвом узле или битом ребре манифеста.

### Соединение БД не держим на время ответа LLM (2026-09-21)

- Обработчик, у которого есть сессия БД, обязан вызвать `db.commit()` **до** обращения к LLM: транзакция после чтения держит соединение из пула на всё время ответа модели (десятки секунд), и пул исчерпывается. Причина ошибок `QueuePool limit ... reached` — именно это (находка 64).
- Проверки: детектор `db.thread_held_connections` (в `api.log` предупреждение со стеком, в тестах — ошибка через `SKKKK_STRICT_DB_HOLD=1`) и статический тест по всем функциям с параметром `db`.
- Пул портала — 10+20 соединений, ожидание 15 с; при исчерпании в `api.log` пишутся стеки держателей (`db.describe_pool_holders`).

### Дорожки встречи: время второго слуха — запасной источник, когда Parakeet недостоверен (2026-09-21)

- Основной распознаватель (Parakeet) остаётся источником слов и времени, но на тихих микрофонах он молчит, галлюцинирует или «схлопывает» речь (находка 65). Реплика Parakeet после вычитки недостоверна, если в ней больше 25 знаков на секунду (при длине от 20 знаков) либо есть слово длиннее 6 с либо не меньше 40 % слов с нулевой длительностью.
- Признак вырождения — не одно длинное слово (пауза после слова бывает у любой реплики), а доля времени реплики в длинных словах ≥ 30 % либо ≥ 40 % слов с нулевой длительностью. Недостоверные реплики отбрасываются только при наличии реплик GigaAM (проверить нечем — оставляем). Реплики GigaAM, не покрытые оставшимися по времени (с допуском 1,5 с), добавляются со временем GigaAM (разрешение около 2 с, слова равномерно по реплике). Решение принято в слое встреч (`services/meeting_track_repair.py`): замороженный лабораторный конвейер `asr/lab` (FREEZE.md) не менялся.
- Дорожка без слов Parakeet не отбрасывается: второй слух мог услышать речь. Каждое отбрасывание и добавление пишется в `proof/meeting_repairs.json` дорожки и в журнал (`meeting.track.repaired`).
- Наблюдаемость: после сборки стенограммы `reports/track_coverage.json` сверяет звук на микрофоне каждого участника (порог −48 дБ, окно 0,5 с) с его репликами (допуск 2 с); проверка `track_coverage` предупреждает, если ≥ 3 с и ≥ 25 % звука остались без текста, `replica_density` даёт FAIL при > 25 знаков/с в реплике. В журнал пишется `meeting.track.uncovered_audio`. Так потеря речи тихого участника видна сразу, а не находится вручную.

### Таблицы документов в базе знаний (2026-09-25, согласовано владельцем)

### Память решений: акты, предметы, журнал, итог (2026-10-06, Э2–Э6)

План и ход — `docs/plans/DECISION-MEMORY-PLAN.md`.

- **Акты.** Каждая реплика переписки и созвона получает до трёх речевых актов (предложил, согласился, отказал, отложил, спросил, ответил, сделано, отменил, препятствие, сведение). Цитата акта проверяется кодом: дословно из реплики, от 4 знаков; иначе акт отбрасывается. Сторона и человек — из реестра проекта.
- **Предметы.** Акты раскладываются по предметам по близости вектора (≥0.80 — тот же, <0.58 — новый, серая зона — вопрос модели). Предмет — «о чём решали», а не пункт требований.
- **Журнал событий** — append-only; состояние — свёртка по правилам сторон: согласие значимо от заказчика или другой стороны, отказ своей стороны снимает предложение, событие человека главнее всего. Порядок внутри дня при точности «день» неизвестен — флаг, а не догадка.
- **Судья итога** (модель) только поправляет свёртку в сложных случаях («согласился с отказом»); ссылки-основания проверяет код, человека судья не перебивает.
- **Человек.** Решение человека — событие `decided_by=human`; снять его можно только кнопкой «Вернуть модели».
- **Чат** журнал только читает: подбирает предметы по вопросу, добавляет ленту и состояние на названную дату. Пустого ответа «нет данных» при найденном предмете быть не должно.
- **Пороги.** A1 ≥ 80 %, A2 ≥ 90 %, M2 ≥ 90 %; не достигнуты после двух итераций промпта — остановка и разбор с владельцем.
- **Раскладка по предметам — проход модели по окну** (`services/subject_windows.py`, 2026-10-06): жадная раскладка по векторам дробила и склеивала решения. Код проверяет метки (акт — из окна, предмет — из показанных); не размеченный акт получает отдельный предмет, а не склейку.
- **Позиции внутри предмета** (`subject_positions`, судья `subject_judge-v2`, 2026-10-06): состояние хранится и у предмета, и у его вариантов или значений («цена 144 000» заменена «ценой 126 000»). Склейка дублей предметов — моделью по парам с близкими центрами; предмет с решением человека не склеивается.
- **Память решений работает без ручной разметки** (владелец 2026-10-06: цель проекта — убрать ручную работу): человеку остаётся только поправить неверный итог кнопкой на экране. Спорные пункты между памятью и прежним контуром решает арбитр-модель (`memory_compare`, `memory_arbiter-v2`), а не человек; перед спором состояние предмета переводится на формулировку пункта (`memory_view-v1`: «отказаться от X» при отклонённом X — пункт в силе).
- **Режимы памяти** `off` / `shadow` / `live` (`DECISION_MEMORY_MODE`, настройка проекта `decision_memory`): в `shadow` память строится и видна админу, в `live` — менеджерам и чату. Переход `shadow` → `live` — сам (`DECISION_MEMORY_AUTO_LIVE`), когда пройдены проверки готовности (`memory_mode.readiness`): построена, цитаты на месте, итоги судьи у 80 % предметов, сравнение с прежним контуром выполнено, память верна не менее чем в 85 % сравнённых пунктов и уступает прежнему контуру не более чем на 5 п.п. Критерий «память права в 70 % споров» заменён этим: доля среди одних споров не отражает качество, когда большинство пунктов совпадает.
- **Акты проверяются вторым проходом** (`speech_acts_review-v1`, `speech_acts-v5`): модель видит окно и черновую разметку и исправляет виды актов по контексту (реакция на предложение — согласие; выбор варианта — отказ от другого и согласие с выбранным; прошедшее время о выполненном — «сделано»).
- **Итоги инкрементальны:** судья пересчитывает только предметы с изменившейся лентой (`subjects.judged_sig`); итоги неизменных предметов переживают пересборку событий (`snapshot_judged` / `restore_unchanged`). Задачи очереди `memory` (акты материала) и `memory_judge` (итог проекта, один раз за партию).
- **Метрика M2 по журналу** проверяет предмет, который о правиле (главный по числу совпадений), а не любое упоминание слова в другом предмете.
