## Обозначения в файлах этапов

- **Проверка** — то, что человек выполняет руками и видит результат глазами.
- **Тест** — то, что запускается через `pytest` и падает само.
- **Критерий готовности** — чеклист; все пункты обязательны.

## Маркеры тестов

```
pytest -m "not gpu"     # быстрые, без моделей: логика, права, БД, парсинг
pytest -m gpu           # реальные ASR; при lmstudio — ещё LM Studio
pytest -m slow          # длинное аудио, нагрузка
```

Подробности — в [../TESTING.md](../TESTING.md).

## Единый порядок закрытия этапа

Этап закрывается только когда пройдены все три вида проверки, в этом порядке. Пропускать нельзя — «код скомпилировался» не значит «работает так, как задумано».

1. **Тесты.** `pytest -m "not gpu"` зелёный для этого этапа; для этапов с GPU (3, частично 5/7) — дополнительно `pytest -m gpu` руками на реальном железе.
2. **Открыть страницу вживую.** Поднять то, что относится к этапу (`uvicorn ...`, `python asr/build_transcript_view.py --serve`, и т.п.), открыть нужный URL в браузере, пройти сценарий из таблицы «Проверки» руками — не только глазами по коду.
3. **Скриншот «было задумано» vs «получилось».** Для каждого этапа с UI (1, 2, 4 частично, 5, 6, 7) сделать скриншот ключевого экрана и сверить с тем, что описано в разделе «Что появляется на диске / Результат» этого этапа и в `docs/PLAN.md`. Расхождение — не «мелочь на потом», а повод доделать этап. Скриншоты не обязательно хранить в репозитории; достаточно свериться визуально при закрытии этапа.

Для этапов без собственного UI (0, 3 частично, 8, 9, 10) пункт 3 заменяется контрольным логом/выводом команды, указанным в разделе «Проверки» этого этапа (`nvidia-smi`, `check_env.ps1`, вывод воркера и т.п.).

## Про раздел «Полезные проекты на GitHub»

Каждый файл этапа ниже содержит подборку 1–5 существующих открытых проектов, которые дают либо готовый кусок кода, либо проверенный паттерн для этого этапа. Это не обязательные зависимости — большинство уже упомянуты как решённые в [DECISIONS.md](../DECISIONS.md) (тройной ASR, LM Studio, Ollama). Секция — источник идей и код для подсматривания при реализации, а не список того, что надо `pip install` не глядя. Перед использованием чужого кода — смотреть на лицензию и не тащить лишние тяжёлые зависимости (Celery, Redis и т.п.), если это конфликтует с [DECISIONS.md](../DECISIONS.md).
