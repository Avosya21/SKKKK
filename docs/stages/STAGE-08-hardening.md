# Этап 8. Укрепление

## Цель

Система переживает реальную эксплуатацию: сбои моделей, параллельные загрузки, перезагрузку машины, ошибки людей. До этого этапа она работала на «хорошем сценарии».

## Предусловия

Этап 7 зелёный.

## Шаги

1. **Логирование**: единый формат строки во всех процессах, файлы `api.log`, `worker.log`, `asr.log`, `llm.log` в `data/logs/` с ротацией по размеру. В каждой строке обработки — `artifact_id` и `job_id`, чтобы можно было проследить путь одного файла.

2. **Устойчивость очереди**: осиротевшие `running` при старте воркера возвращаются в `queued` с инкрементом попыток; предел попыток; понятное сообщение в UI вместо «error».

3. **Таймауты**: на каждый вызов LM Studio, Ollama, FFmpeg и процессы ASR — свой таймаут и корректное завершение зависшего процесса.

4. **Проверка здоровья** `GET /health`: доступность БД, LM Studio, Ollama, свободная VRAM, длина очереди. Используется страницей администратора и службами этапа 9.

5. **Права по всему API**: пройти каждый эндпоинт из плана и подтвердить проверку роли. Отдельно — что скачивание файла и транскрипции требует авторизации и проверяет принадлежность проекту.

6. **Прямой доступ к файлам закрыт**: раздача только через эндпоинт с проверкой прав, каталог `data/` не отдаётся статикой.

7. **Подтверждение Telegram ID** (опционально, по решению администратора): бот присылает код, пользователь вводит его при первом входе. Закрывает риск «назваться чужим ID».

8. **Бэкап**: расписание `VACUUM INTO` для `app.db` в `data/backups/`, хранение N последних копий, проверка восстановления.

9. **Нагрузка**: одновременная загрузка нескольких аудио, контроль VRAM и длины очереди. Ансамбль обрабатывает файлы **последовательно** — карта одна; проверяется, что очередь не пытается запустить второй ансамбль параллельно.

10. **Диагностика**: `scripts/check_env.ps1` из этапа 0 дополняется проверкой служб и очереди, вызывается со страницы администратора.

## Полезные проекты на GitHub

Без Redis/внешних сервисов (см. DECISIONS.md) — берём только то, что работает на процессе/файле.

| Проект | Что даёт | Как используем |
|---|---|---|
| [hynek/structlog](https://github.com/hynek/structlog) | Структурные (JSON) логи с контекстом на весь запрос/задачу через `contextvars`, без внешней инфраструктуры | Прямая замена ручного форматирования строк логов в п. 1 шагов — привязать `artifact_id`/`job_id` через `structlog.contextvars.bind_contextvars` один раз на вход в обработку, а не прокидывать в каждый вызов логгера |
| [laurentS/slowapi](https://github.com/laurentS/slowapi) | Rate limiting для FastAPI/Starlette, поддерживает **in-memory backend** (без Redis) | На 20 сотрудников достаточно in-memory лимитера на `/auth/login` и `/chat` — защита от случайного цикла запросов, не от DDoS |
| [Delgan/loguru](https://github.com/Delgan/loguru) | Простая ротация файлов по размеру «из коробки» (`rotation="100 MB"`), без настройки `logging.handlers` вручную | Альтернатива стандартному `logging` для `data/logs/*.log` из п. 1, если ручная настройка ротации/ежедневных файлов станет обузой |
| [Tinche/aiofiles](https://github.com/Tinche/aiofiles) | Асинхронная запись файлов — уже в зависимостях этапа 1 | Проверить, что бэкап (`VACUUM INTO`) и запись логов не блокируют event loop под нагрузкой из п. 9 |

## Проверки

| Проверка | Действие | Ожидание |
|---|---|---|
| Убийство воркера | Снять процесс во время ASR | После перезапуска задача вернулась в очередь, не «висит» |
| Падение LM Studio | Остановить LM Studio во время склейки | Внятная ошибка, повтор, артефакт не потерян |
| Падение Ollama | Остановить во время индексации | Ошибка и повтор, чанки не дублируются после восстановления |
| Зависший процесс ASR | Смоделировать зависание | Таймаут, процесс снят, статус `error` |
| Перезагрузка | Перезагрузить машину с задачами в очереди | После старта очередь продолжилась |
| Параллельные загрузки | Пять аудио одновременно | Все в очереди, ансамбль по одному, VRAM в пределах |
| Прямой доступ | Открыть путь к файлу в браузере | Отказ |
| Чужой проект | Скачать файл чужого проекта по ID | 403/404 |
| Здоровье | `GET /health` при выключенной Ollama | Явно показывает недоступность |
| Бэкап | Выполнить и восстановить копию | Приложение стартует на восстановленной БД |

Скриншот `GET /health` в браузере (или через `curl | jq`, но глазами тоже) в двух состояниях — всё живо и с искусственно остановленной Ollama — чтобы визуально подтвердить, что страница администратора реально показывает деградацию, а не просто зелёную галочку всегда.

## Критерий готовности

- [ ] Ни один сбой из таблицы проверок не оставляет задачу в подвешенном состоянии
- [ ] Файлы недоступны в обход прав
- [ ] Каждый эндпоинт проверяет роль
- [ ] Очередь переживает перезапуск воркера и машины
- [ ] Бэкап создаётся и восстанавливается
- [ ] `/health` честно показывает состояние зависимостей

## Типичные отказы

| Симптом | Причина | Что делать |
|---|---|---|
| Логи не пишутся из воркера | Конфликт хендлеров в двух процессах | Разные файлы на процесс |
| VRAM не освобождается после снятия процесса | Процесс убит некорректно | Завершать дерево процессов ASR |
| Очередь встала | Осиротевшая `running` | Требуемый механизм возврата в очередь |
