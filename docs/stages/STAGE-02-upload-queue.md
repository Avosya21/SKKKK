# Этап 2. Загрузка и очередь

## Цель

Файл попадает в проект, регистрируется в БД и проходит через очередь до конечного статуса — **без единой модели**. Это позволяет отладить всю механику конвейера отдельно от GPU, где отладка стоит минут на итерацию.

## Предусловия

Этап 1 зелёный.

## Шаги

1. **Загрузка** `POST /projects/{id}/upload`:
   - принимает несколько файлов, пишет потоково на диск (не читать 2 ГБ в память);
   - лимит `MAX_UPLOAD_BYTES`, превышение — 413;
   - `file_type` по расширению и MIME, `source_type` из поля формы;
   - `stored_filename` генерирует система: `art_YYYY-MM-DD_HHMMSS_{rand6}{ext}`; пользовательское имя живёт только в `original_filename`;
   - считается `sha256` потока; дубль в рамках проекта — не создавать новый артефакт, вернуть существующий с пометкой «уже загружен»;
   - для аудио — длительность через `ffprobe`, запись в `duration_sec`, отказ при превышении лимита длительности;
   - `priority_weight` по таблице весов из `projects.settings_json`;
   - статус `uploaded`, создаётся запись в `jobs` со статусом `queued`.

2. **Очередь.** Таблица `jobs`: `kind`, `phase` (`asr`/`llm`/`embed`), `status`, `attempts`, `error_message`, временные метки. Забор задачи атомарный (`UPDATE ... WHERE status='queued'` с проверкой числа изменённых строк), чтобы два воркера не взяли одну задачу.

3. **Воркер** `app/app/workers/gpu_worker.py`: отдельный процесс, цикл забора задач, диспетчер по `file_type`. При `DRY_RUN=1` вместо моделей пишет заглушечные тексты в те же файлы и проводит артефакт по всем статусам. Это режим разработки и режим тестов.

4. **Уборка.** Каталог `tmp/` артефакта чистится в `finally`, независимо от исхода.

5. **UI статусов.** На странице проекта таблица файлов, статус обновляется опросом раз в 3–5 секунд. Показывать `error_message`, если есть.

6. **Telegram-заглушка** `services/notify.py`: интерфейс отправки, при пустом токене только пишет в лог. Реальная отправка включается на этапе 3.

## Что появляется на диске

```
data\projects\{id}\raw_inputs\calls\art_2026-08-18_143012_a1b2c3.wav
data\projects\{id}\tmp\                     (пусто после завершения)
data\logs\worker.log
```

## Полезные проекты на GitHub

Идея этапа — «таблица `jobs` + один воркер, без Celery» уже зафиксирована как решение. Ниже — готовые реализации того же паттерна для подсматривания в детали (атомарный захват задачи, восстановление после падения воркера), не для установки как зависимости — своя таблица `jobs` уже спроектирована под наши статусы и `phase`.

| Проект | Что даёт | Как используем |
|---|---|---|
| [KPouianou/GigQ](https://github.com/KPouianou/GigQ) | SQLite-очередь с ретраями и backoff, восстановление «зависших» задач при падении воркера, WAL-режим | Смотреть реализацию атомарного захвата (`UPDATE ... WHERE status='queued'`) и восстановления `running` → `queued` при рестарте — то же нужно в `test_retry_increments_attempts_and_stops_at_limit` |
| [unkloud/liteq](https://github.com/unkloud/liteq) | Однофайловая очередь на чистом `sqlite3`, `BEGIN IMMEDIATE` для конкурентной записи, Dead Letter Queue после `max_retries` | Референс для `busy_timeout`/`BEGIN IMMEDIATE` вместо голого `UPDATE`, если `database is locked` всё же проявится в тестах на два воркера |
| [rnovatorov/schlange](https://github.com/rnovatorov/schlange) | Персистентная очередь на SQLite с CLI для просмотра статусов задач | Идея для будущей страницы `/admin/jobs` (не в этом этапе, но задел) — как показывать очередь человеку без захода в БД руками |

## Проверки

Открыть `http://127.0.0.1:1111/projects/{id}` в браузере после загрузки файла и сделать скриншот таблицы статусов (обновляется поллингом) — сверить с целью этапа: «файл лежит в дереве проекта, в БД статус меняется воркером» должно быть видно глазами, не только в БД через DB-браузер.

| Проверка | Действие | Ожидание |
|---|---|---|
| Загрузка | Загрузить wav через UI | Файл в `raw_inputs\calls`, строка в `artifacts`, задача в `jobs` |
| Имя файла | Загрузить `отчёт (финал)#1.pdf` | На диске безопасное `art_...pdf`, в UI видно исходное имя |
| Дубликат | Загрузить тот же файл повторно | Второго артефакта нет, UI сообщает о дубле |
| Прогон вхолостую | `DRY_RUN=1`, запустить воркер | Статусы меняются до `done`, в `parsed\` заглушечные файлы |
| Ошибка | Подсунуть битый файл | Статус `error`, текст ошибки виден в UI, `tmp` пуст |
| Крупный файл | Файл больше лимита | 413, на диске ничего не осталось |
| Два воркера | Запустить воркер дважды | Каждая задача обработана один раз |
| Обход каталога | `curl` с `filename="..\..\evil.txt"` | Файл лежит внутри проекта, не выше |

## Критерий готовности

- [ ] Файл проходит весь путь до `done` при `DRY_RUN=1`
- [ ] Дубликат не обрабатывается второй раз
- [ ] Задачу нельзя забрать дважды
- [ ] `tmp` чист после успеха и после ошибки
- [ ] Пользовательское имя файла не попадает в путь на диске
- [ ] Тесты `test_upload.py` и `test_queue.py` зелёные

## Типичные отказы

| Симптом | Причина | Что делать |
|---|---|---|
| `database is locked` | Воркер и API пишут одновременно | WAL, короткие транзакции, `busy_timeout` |
| Память растёт при загрузке | Файл читается целиком | Потоковая запись чанками |
| Задача «висит» в `running` | Воркер упал | При старте воркера возвращать «осиротевшие» `running` в `queued` с инкрементом `attempts` |
