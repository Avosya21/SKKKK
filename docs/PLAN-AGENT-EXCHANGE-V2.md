## Что появится на странице проекта

Новые сворачиваемые карточки в стиле существующих (`mcp-access-card`, `meetings-card`). Всё на нашем портале, внешних мессенджеров нет. **Подтверждать, отклонять и одобрять может только admin** (проверка на сервере, `require_role("admin")`); manager видит карточки только для просмотра. Роль manager можно будет добавить позже, поменяв одну проверку. Каждая со счётчиком в заголовке, состояние «свёрнуто/развёрнуто» запоминается. Код выносится из `project.html` (там уже 2 800 строк) в отдельные файлы `static/px_*.js` и включаемые шаблоны.

| Карточка | Что в ней | Кому |
|---|---|---|
| **Подтверждение требований** | очередь требований с цитатой, автором, стороной, датой; кнопки «Подтвердить», «Отклонить», «Изменить статус» (с причиной); фильтры: статус, сторона, `status_basis`, только без подтверждения; массовое подтверждение выбранных | действия: admin; просмотр: manager |

## Шаги

Обозначения: **S** — до полудня, **M** — день, **L** — несколько дней. Каждый шаг закрывается тестами, и в конце шага прогоняется полный набор и перезапускается сервер (на локальной модели).

### Фаза 0. Подготовка (S)
0.1. Вынести из `project.html` панель ключей и общие хелперы в `static/px_common.js`; шаблонный include `partials/px_card.html` для единого вида карточки (заголовок, счётчик, сворачивание, запоминание состояния).
0.2. Согласовать список эндпоинтов (ниже) и записать в `docs/agent-exchange/API.md`.
*Готово, когда:* существующие карточки работают без изменений (смоук `run_all` зелёный).

### Фаза 1. Настройки проекта вместо зашитого «Пилота» (M) — пункт 1 из списка

**Что такое «пакет якорей» (простыми словами).** Для каждого требования система сейчас угадывает, к какому месту в информационной системе оно относится, и пишет это как подсказку агенту анализа (например, «Документ.ЗаказКлиента» в 1С или «crm.deal» в Битрикс24). Угадывает по словам в тексте по заранее заданному словарю. Этот словарь написан только для 1С и Битрикс24. Пакет якорей — просто отдельный файл с таким словарём. Для ваших проектов на 1С и Битрикс24 остаётся тот же пакет, поведение не меняется. Для проекта на другой системе подсказки были бы неверными, поэтому по умолчанию у нового проекта пакета нет (подсказок нет, а не ложные), а если такая система появится, добавляется ещё один файл-словарь. **Сейчас нужны ровно два варианта: «1С + Битрикс24» (как есть) и «нет».** Больше пакетов делать не надо, пока не понадобится.

1.1. Модель `ProjectAgentSettings` (или JSON в `Project.settings`): `participants[{name, side}]`, `timezone`, `domain_pack`, `exchange_enabled`, `key_defaults`. Миграция.
1.2. `contract_text.anchors_for` берёт правила из выбранного пакета; пакеты — файлы `app/app/data/anchor_packs/<имя>.json` (`1c_bitrix24` — текущие правила, `none` — по умолчанию для новых проектов).
1.3. Определение стороны: сначала явные `participants`, затем роль, затем `unknown`. Убрать из `SIDE_*_RE` названия конкретных компаний.
1.4. Идентификаторы `req-<slug>-NNNN`, часовой пояс и правило расхождений `scope` читают настройки проекта.
1.5. Карточка «Настройки для агентов» + эндпоинты `GET/PUT /projects/{id}/agent-settings` (валидация; изменять может admin, manager видит).
1.6. Золотой набор: второй тестовый проект без 1С (например, переписка про сайт) в `tests/fixtures`, контракт по нему не содержит якорей 1С и не путает стороны.
*Готово, когда:* новый проект с пакетом `none` отдаёт контракт без «1c:…» якорей; проект #18 отдаёт тот же контракт, что сейчас (тест сравнивает).

### Фаза 2. Идентификаторы обращений выдаёт сервер (S)
2.1. `submit_question` / `submit_verdicts`: `request_id` необязателен; если не передан, сервер выдаёт и возвращает его. Старый способ (агент задаёт число) остаётся.
2.2. Ответ шлюза при занятом номере подсказывает свободный. Обновить руководство агента и тесты.
*Готово, когда:* повтор с `client_request_id` возвращает тот же выданный номер; конфликты номеров невозможны.

### Фаза 3. Подтверждение человеком (M–L) — пункт 3 из списка
3.1. Эндпоинты: `GET /projects/{id}/requirements/review` (порциями, фильтры; чтение для admin и manager), `POST …/requirements/{id}/confirm|reject|status` (причина обязательна для смены статуса) и пакетное `POST …/requirements/confirm` — **только admin**; manager получает 403 (тест).
3.2. Подтверждение записывается на исходную сущность (`needs_review=false`) и в журнал действий (кто, когда, что было); `verification` в контракте становится `human_confirmed`; `side_agreed` заполняется подтвердившим.
3.3. Отклонение: сущность выключается мягко (`is_active=false`), не удаляется; в контракте статус `rejected` с основанием `human_rejected`.
3.4. Карточка «Подтверждение требований»: список с цитатой, ссылка на источник, фильтры, массовые действия, счётчик «ждут подтверждения».
3.5. Смоук Playwright: подтвердить, отклонить, отфильтровать; контракт меняется.
*Готово, когда:* подтверждённое требование видно агенту как `human_confirmed`; действие можно отследить в журнале.

### Фаза 4. Экран «Обмен с агентами» (M) — пункт 4
4.1. Эндпоинты: `POST …/agent-verdicts/{entity_id}/confirm|reject`, расширить журнал фильтрами (решение, источник, дата), счётчики `GET …/agent-exchange/summary`.
4.2. Вкладка «Вопросы»: очередь, черновик локальной модели, одобрение, ручной ответ (уже есть в API, нужен интерфейс).
4.3. Вкладка «Вердикты»: подтверждение и отклонение; подтверждённый вердикт получает `verification: human_confirmed` в `analysis`.
4.4. Вкладка «Журнал».
4.5. Уведомление о новом вопросе агента: счётчик в заголовке карточки и бейдж на странице проекта (внешних уведомлений нет: агента в мессенджерах нет и, возможно, не будет).
4.6. Смоук: агент (через MCP) задаёт вопрос, человек отвечает на странице, агент получает ответ.

### Фаза 5. Ключи и агенты (S–M) — пункт 6
5.1. Поля токена: `scope` (`read` / `questions` / `questions_verdicts`, заменяет `can_submit`), `agent_name`, лимит обращений. Срока действия нет (решение владельца: ключ отзывается кнопкой). Миграция с сохранением текущих значений (`can_submit=true` → `questions_verdicts`).
5.2. Проверка права при каждом вызове; понятная ошибка `read_only_key` (уже есть) и новая для «только вопросы» при попытке отправить вердикты.
5.3. Интерфейс: выбор прав при выдаче ключа, значения по умолчанию из «Настроек для агентов», смена прав в таблице.
5.4. Журнал показывает `agent_name`.

### Фаза 6. Честность эвристических полей (M) — пункт 2
6.1. Поле `basis` у каждого вычисляемого значения (`in_current_tz`, `side`, `code_anchors`, `estimate`) и описание эвристики в `state.json.gaps`.
6.2. Оценка качества: золотой набор ≥ 40 размеченных вручную требований проекта #18 (разметка через карточку «Подтверждение»), скрипт `scripts/eval_contract.py`: точность `status`, `side`, `in_current_tz`. Результат пишется в `docs/eval/`.
6.3. Улучшение `in_current_tz` по результатам оценки и по проверке от агента анализа (он обещал пункты ТЗ); порог совпадения выносится в настройки.

### Фаза 7. Поиск по сообщениям (L) — пункт 7
7.1. Перечанковка переписок по сообщениям с автором и временем в метаданных (для чата и `search_project`).
7.2. Миграция индекса с резервной копией и проверкой (`verify_backup.py`, `audit_integrity.py`).
7.3. Регрессия: `eval_chat.py` до и после, сравнение точности и времени.

### Фаза 8. Автоответ локальной модели (M) — разрешён владельцем
8.1. Флаг проекта «автоответ на вопросы» (в «Настройках для агентов», выключен по умолчанию, включает admin).
8.2. Условия автоответа: в ответе обязательны ссылки на найденные фрагменты; ответ помечен «ответ локальной модели, не проверен человеком»; вопросы без найденных источников, с условными формулировками («по дооценке», «возможно») и вопросы про статус/согласование уходят на ручной ответ; тот же контроль утечек, что у ручных ответов.
8.3. Человек видит такие ответы во вкладке «Вопросы» и может исправить: правка заменяет ответ, и агент получает исправленный.
8.4. Замер качества на первых 20–30 вопросах (доля ответов, которые пришлось исправить); результат в `docs/eval/`. Если исправлений много, флаг отключается.

9.2. Смоук-набор обновлён, `run_all` зелёный; полный прогон тестов; перезапуск на локальной модели.
