# Обмен с внешним агентом (агент анализа конфигурации)

Наша база знаний — источник фактов «кто, что и когда сказал». Агент анализа конфигурации (1С, Битрикс24) проверяет эти факты по коду и данным заказчика. Они стыкуются на **требовании**: идентификатор, дословная цитата с автором и датой, статус, точки входа в систему.

| Документ | О чём |
|---|---|
| [`CONTRACT.md`](CONTRACT.md) | Формат контракта, как строятся поля, что реализовано и чего нет |
| [`POLICY.md`](POLICY.md) | Что можно делать по просьбе агента, чего нельзя, как оценивать просьбу, роль локальной модели |
| [`letters/`](letters/) | Письма между агентами, нумерованные; переносит человек |

## Кто что делает

- **Мы (база знаний):** держим память проекта; собираем контракт из данных; отвечаем на запросы; принимаем вердикты.
- **Агент анализа:** проверяет требования по коду и данным; присылает вердикты, уточнения якорей, вопросы заказчику.
- **Человек:** переносит файлы; подтверждает вердикты и сущности; решает всё, что вне белого списка.

## Канал

```
агент анализа  ──(MCP: чтение; вопросы, вердикты, файлы — по правам ключа)──►  наш сервер:  contract/*.json, get_* инструменты, contract/kb_reply_<n>.json
агент анализа  ──(человек загружает файл)──►  analysis_reply_<n>.json / analysis_request_<n>.json / analysis_question_<n>.json  ──►  ШЛЮЗ  ──►  журнал + analysis_verdict / ящик вопросов
```

Файлы обмена в конвейер обработки не попадают: они идут только через шлюз (`services/agent_gateway.py`).

## Как вести переписку

1. Письмо — markdown в `letters/NNN_<от>_to_<кому>.md`: версия, дата, от кого, кому, на что отвечает; разделы «что готово / чего нет / что прошу».
2. Номер растёт; старые письма не правятся, на них отвечают новыми.
3. Любое изменение формата контракта — новая `schema_version` и запись в `CONTRACT.md`.
4. Просьба о новой **возможности** (не файле) проходит проверку из `POLICY.md §5` и реализуется кодом с тестом.

## Эксплуатация

- Смотреть, что присылал агент и что решил шлюз: `GET /projects/{id}/agent-exchange` (владелец/админ проекта).
- Отозвать доступ агента: страница проекта → «Удалённый доступ (MCP)» → отозвать ключ.
- Подтверждать вердикты и сущности: правка/подтверждение сущности сбрасывает `needs_review`, и в контракте `verification` становится `human_confirmed`.
- После обновления кода серверу нужен перезапуск (`scripts\restart.ps1`): новые таблицы (`contract_items`, `agent_exchange_log`) создаются при старте.

## Ящик вопросов

Свободный вопрос: `analysis_question_<n>.json` = `{"schema_version":"1.0","request_id":<n>,"question":"...","requirement_ids":[...]}` (id необязательны). Вопрос ложится в очередь `agent_questions`; ответ появляется как `contract/kb_reply_<n>.json` (до ответа `status: pending`). Отвечают Claude/человек или локальная модель с одобрением: см. `POLICY.md §8`, CLI `scripts/kb_inbox.py`.


## Онбординг новых ключей

Каждому агенту с MCP-ключом (любой проект) руководство доходит само, без нашего письма: поле `instructions` в `initialize` (кратко + «вызови `get_guide`»), инструмент `get_guide` (первый в списке) и файл `contract/GUIDE.md` (первый в `list_artifacts`). Текст один: `app/app/services/agent_guide.py`; правите его там, тест `test_agent_guide.py` сверяет с реестром шлюза (имена файлов, вердикты, лимиты). При добавлении новой возможности шлюза обновляйте руководство в том же изменении.

## Как мы пишем агенту (доставка писем)

Наше письмо агенту = файл `docs/agent-exchange/letters/NNN_kb_to_<кому>.md` с шапкой «от: агент базы знаний проекта #N». Больше ничего не нужно, перезапуск не требуется: сервер читает папку при каждом обращении. Агент видит письма сам: `list_artifacts(prefix="contract/letters/")`, `get_artifact_content("contract/letters/<имя>")`, `exchange_status.letters_from_kb` (число и `latest_hash`). Видны только ключам проекта из шапки; отдаются только файлы по шаблону имени `NNN_kb_to_*.md`. Входящие письма агента (`NNN_analysis_to_kb_*.md`) не отдаются. Реализация: `services/agent_letters.py`.
