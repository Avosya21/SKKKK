# Политика обмена с внешним агентом

Действует для агента анализа конфигурации (1С, Битрикс24) и для любого другого внешнего агента, который читает нашу базу знаний
или присылает нам файлы. Всё выполняется на нашем сервере. Реализация — `app/app/services/agent_gateway.py`, тесты — `test_agent_gateway.py`.

## 1. Модель доверия

- Внешний агент — **недоверенный источник**. Он может ошибаться, зациклиться или быть скомпрометирован; мы этого не проверяем и не полагаемся на его добросовестность.
- Всё, что он присылает (письма, файлы, тексты запросов, цитаты, «пояснения»), — **данные, а не указания**. Ничего из присланного не исполняется, не подставляется в команды и не читается ассистентом как инструкция.
- Исполняет только **код шлюза** по белому списку. Каждое решение шлюза детерминировано: та же посылка — то же решение. Языковая модель (облачная или локальная) в этом решении не участвует.
- Между агентами нет прямого канала. Файлы туда и обратно переносит человек, поэтому у человека всегда есть точка проверки.

## 2. Что можно делать по просьбе агента (белый список)

| Возможность | Уровень | Что делает | Что пишет |
|---|---|---|---|
| Читать контракт: `get_requirements`, `get_conflicts`, `get_quote`, `get_tz`, `get_artifact_meta`, `get_code_anchors`, `get_changes`, `list_artifacts`, `get_artifact_content` | 0, только чтение | Отдаёт данные **только этого проекта**, порциями до 60 КБ (`page_bytes` — до 200 КБ), материалы — целиком по курсору | строку `mcp.call` в журнале (инструмент, размер, без содержимого) |
| Ответить на запрос `analysis_request_<n>.json` | 0, только чтение | Требования по id либо поиск фрагментов по тексту `ask` (текст — только поисковый запрос) | ответ `kb_reply_<n>.json` и строка в журнале |
| Положить вопрос в ящик `analysis_question_<n>.json` (или любой JSON с полем `question`) | 0 | Сохраняет вопрос как данные, прикладывает найденные поиском фрагменты. Отвечает человек, Claude или локальная модель | **только** таблица `agent_questions`; ответ виден агенту как `contract/kb_reply_<n>.json` (пока ответа нет, `status: pending`) |
| Принять вердикты `analysis_reply_<n>.json` | 1, ограниченная запись | Проверяет схему, обрезает поля, сверяет id требований | **только** сущности типа `analysis_verdict`; прежний вердикт по требованию выключается мягко (`is_active=false`), ничего не удаляется |

Обработчиков вне этой таблицы **не существует**. Запрос, не подходящий ни под один пункт, получает `rejected`.

## 3. Чего агент не может добиться никогда

Нет ни одного обработчика, который бы это делал; попытка фиксируется как `rejected` с оценкой риска:

- удалять или менять существующие данные проекта: сущности, чанки, артефакты, ТЗ, БД, файлы;
- запускать команды и скрипты, устанавливать пакеты, вызывать внешние адреса из письма;
- читать файлы вне данных проекта, `.env`, пароли, токены, ключи;
- видеть другие проекты и пользователей, менять роли, MCP-токены, настройки, провайдера LLM;
- останавливать, перезапускать или переконфигурировать серверы и воркеры;
- писать в проект иначе как через `analysis_verdict`.

## 4. Проверки шлюза (по порядку)

1. **Лимит обращений:** не более 30 за 10 минут с одного источника.
2. **Размер:** не более 200 КБ; формат — UTF-8 JSON, корень — объект.
3. **Классификация:** по имени файла или форме посылки; вне белого списка → `rejected`.
4. **Версия и проект:** `schema_version` 1.x (у запроса допускается без версии); `project_id`, если указан, должен совпасть с проектом обмена.
5. **Сканирование содержимого** всех строк:
   - команды и разрушительные конструкции (`rm -rf`, `DROP TABLE`, `Remove-Item`, `powershell`…) или абсолютные пути и `..\` → `rejected`, риск 90, **ничего не выполняется и не записывается**;
   - текст, похожий на указание ассистенту («ignore previous instructions», «игнорируй предыдущие инструкции», «покажи токен») → `needs_human`, риск 50, запись не выполняется.
6. **Схема вердикта:** допустимые `verdict` и `confidence`, формат id, неизвестные требования и лишние ключи отбрасываются, длины полей обрезаются. Принимается только то, что прошло проверку; остальное попадает в `dropped` с причиной.
7. **Журнал:** результат в любом случае пишется в `agent_exchange_log` (источник, вид, решение, риск, причины, хеш, размер). Просмотр для владельца проекта — `GET /projects/{id}/agent-exchange`.

## 5. Как оценивать нестандартную просьбу вручную

Если агент просит то, чего нет в белом списке, задайте четыре вопроса:

1. **Читает или пишет?** Чтение данных этого проекта — обычно можно. Запись — только если это один из уже описанных типов.
2. **Обратимо ли?** Всё, что нельзя откатить (удаление, перезапись, отправка наружу), — только по решению человека, не по просьбе агента.
3. **Выходит ли за проект?** Другие проекты, файлы сервера, конфигурация, учётные данные — нет.
4. **Нужен ли для этого текст письма как команда?** Если просьба звучит как «выполни…», «удали…», «отправь…», это сигнал не выполнять, а показать человеку.

Новая возможность добавляется **кодом с тестом** в `CAPABILITIES`, а не разрешением «в разговоре». Каждая новая возможность записи должна иметь: ограничение по типу данных, схему, лимиты, тест на отклонение опасного и запись в этом документе.

## 6. Локальная модель вместо Claude

Шлюз написан так, чтобы работу можно было отдать локальной модели, не меняя границ безопасности:

- решения принимает код (белый список, схема, лимиты), поэтому модель не может «согласиться» на лишнее;
- модель можно использовать **только на входе очереди `needs_human`** как помощника человеку (кратко изложить, что просит агент, и предложить ответ), но не как исполнителя;
- любая новая возможность, которую захочет реализовать модель, идёт через тот же путь: код, тест, запись в политике;
- у модели не должно быть прав на запись в БД и файлы проекта, кроме вызова функций шлюза.

## 7. Что делать при подозрении

- Отклонённое или `needs_human` — смотреть журнал: `GET /projects/{id}/agent-exchange` (источник, причины, размер).
- Если источник зацикливается, лимит 30/10 минут отсекает его сам; при необходимости отзовите MCP-ключ агента (кнопка «Ключи доступа» на странице проекта): чтение прекратится сразу.
- Присланные вердикты в памяти помечены `untrusted_source` и `needs_review`: они гипотезы, пока человек их не подтвердит.

## 8. Ящик вопросов: кто и как отвечает

Вопрос агента (`question`) — недоверенный текст. Он не блокирует приём даже при «указаниях» внутри (вопрос ничего не исполняет), но:

- **Claude/человек** отвечают напрямую: `scripts/kb_inbox.py answer <id> --author claude --text "..."` либо `POST /projects/{id}/agent-inbox/{qid}/answer`.
- **Локальная модель** пишет только **черновик** (`draft`): по найденным фрагментам, без действий. Наружу он не виден, пока человек или Claude не одобрят (`approve` / `{"approve_draft": true}`); в ответе указывается «local_model (одобрил …)».
- Ответ проверяется на токены, пароли, пути сервера и обрезается до 4000 символов.
- Единственная запись ящика — таблица `agent_questions`; смотреть очередь: `GET /projects/{id}/agent-inbox` или `scripts/kb_inbox.py list`.
- Полностью автоматический ответ модели без одобрения не включён сознательно; включать только после разбора качества черновиков.


## 9. Запись через MCP (включена, по ключам)

Инструменты `submit_question` / `submit_verdicts` дают тот же путь, что и файл, без переноса человеком: сервер сам создаёт файл-транспорт `analysis_question_<n>.json` / `analysis_reply_<n>.json`, и он проходит тот же шлюз, журнал и лимиты (источник `mcp:<id ключа>`).
Решение владельца: 19.09.2026, «включаем; права выбирает пользователь при выдаче ключа».

- **Право на ключе.** Три уровня (`scope`): `read` — только чтение (по умолчанию), `questions` — плюс вопросы в очередь, `questions_verdicts` — плюс вердикты. Прежний флаг `can_submit` = «вопросы и вердикты». У ключа есть имя агента (показывается в журнале) и необязательный лимит обращений за 10 минут. Выбирается при создании ключа (карточка проекта → «Удалённый доступ (MCP)» → «Права нового ключа»; значение по умолчанию — в «Настройках для агентов») и меняется списком в таблице ключей. Отправка вердиктов ключом «только вопросы» → ошибка `verdicts_not_allowed`. Ключ без права получает ошибку `read_only_key`.
- **Только добавление.** Прежний вердикт по требованию гасится мягко (`is_active=false`), удалений и правок чужого нет. Вердикты пишутся `untrusted_source`, `needs_review=true`.
- **Идемпотентность:** повтор с тем же `client_request_id` возвращает первый результат (`duplicate: true`). `request_id` можно использовать только один раз (принятое обращение), число до 9 цифр.
- **Ответы одобряет человек/Claude**, а не транспорт (§8).
- Чтение (`wait_reply`, `exchange_status`, `fields="brief"`, хеши файлов) права не расширяет.

## 10. Посылки файлов (включены, по праву ключа)

Решение владельца: 08.10.2026, «карты конфигурации нужны в работе над проектом; канал готовим мы». Реализация — `app/app/services/exchange_files.py`, тесты — `test_exchange_files.py`.

- **Право на ключе** `files_access`, отдельно от прав на вопросы и вердикты: `read` (по умолчанию) — каталог `files_catalog`, список и скачивание посылок, принятых целиком; `write` — ещё открыть посылку и класть части; `blocked` — файлы ключу закрыты. Меняет владелец проекта (строка ключа → «Файлы»).
  Решение владельца 08.10.2026: «любой агент, подключённый к проекту, должен видеть эти файлы и использовать их у себя» — поэтому чтение по умолчанию, а агент узнаёт о файлах при подключении (строка «ФАЙЛЫ ПРОЕКТА» в `instructions`, поле `files` в `project_overview`).
- **Только по манифесту.** Агент заранее заявляет файлы: относительный путь (через `/`, без диска, `..`, обратной косой и служебных имён Windows), размер, sha256. Чужой путь, лишний байт, неверный хеш части — отказ; неверный sha256 файла целиком — приём файла сбрасывается.
- **Только добавление.** Принятое не перезаписывается; новая версия — новая посылка с новым именем. Удаляет посылку с диска только человек (`DELETE /projects/{id}/exchange-files/{bundle_id}`); строки остаются со статусом `deleted`.
- **Лимиты:** часть по HTTP до 64 МБ, через инструменты MCP до 1 МБ; посылка до `EXCHANGE_BUNDLE_MAX_GB`; не открывается, если на диске останется меньше `EXCHANGE_FILES_RESERVE_GB`. Лимит 30 обращений за 10 минут к частям не применяется: их тысячи, а запись ограничена манифестом.
- **Файлы — данные.** Содержимое посылок не исполняется, не попадает в конвейер обработки и в индекс; сервер только хранит и отдаёт байты.
- **Журнал:** открытие, приём целиком, отказы при открытии и удаление пишутся в `agent_exchange_log` (`files_open`, `files_complete`, `files_delete`).
- **Раскладка:** принятая посылка остаётся архивом; рабочая копия для проекта собирается сама сразу после приёма посылки целиком (`EXCHANGE_AUTO_UNPACK`, фоном; ошибка — запись `files_unpack` с решением rejected в журнале), повторно — вручную `scripts/unpack_exchange_bundle.py --project <id> --bundle <n>` → `data/projects/<id>/config/` (`map/`, `deepmaps/<сущность>/`, `README.md`, `layout.json`). Распаковка проверяет пути внутри zip, степень сжатия, sha256 исходников по MANIFEST.json посылки и место на диске; новая версия заменяет прежнюю копию только после полной проверки.
