## 1. Как будет работать (для пользователя)

1. Выгрузка Telegram разбирается на сообщения: автор, дата и время до секунды, номер, «в ответ на».
2. Модель видит переписку пронумерованными сообщениями «M106 [25.08.2026 15:58] Ivan Sample: …» — как реплики созвона —
   и указывает, из каких сообщений пункт и кто его подтвердил. Код проверяет номера и авторов.
3. У пункта из переписки в карточке: «Сказал: Ivan Sample (заказчик) · утвердил: Елена · переписка · 25.08.2026 15:58».
4. В поиске устаревшего пункты переписки сравниваются по времени сообщений — и друг с другом, и с созвонами.
5. Одно сообщение из двух пересекающихся выгрузок — один пункт, а не два.
6. Рядом с каждым источником — «открыть ▸ 12:34»: страница стенограммы открывается на нужной реплике, реплика подсвечена,
   плеер перемотан (звук — по кнопке). Для переписки — на нужном сообщении, для документа — на найденном абзаце.

## 2. Решения пользователя

| # | Вопрос | Рекомендация |
|---|---|---|
| Я1 | Пересекающиеся выгрузки одной переписки | одно сообщение — один источник: принадлежит **самой ранней загруженной** выгрузке; в более поздней — только контекст (модель его видит, но пункты из него не извлекает). Переписка узнаётся по названию группы из заголовка выгрузки |
| Я2 | «Утвердил» в переписке | ответ другого участника на сообщение (`reply_to`) или его следующее сообщение в пределах 10 сообщений и 24 часов со словами согласия; дальше — не утверждение |
| Я3 | Созвон и сообщение в один день | сравнивать, только если у обоих известно время: у созвона — начало записи с точностью до минуты (встреча из комнаты, метаданные файла, ручная дата со временем) + таймкод; иначе «неясно» (как А4) |
| Я4 | Звук по ссылке | не запускать автоматически: перемотать, подсветить реплику и показать кнопку «▶ с 12:34» (браузер без клика всё равно блокирует звук) |
| Я5 | Ручная дата созвона | разрешить указать и время начала («22.07.2026 14:30»), тогда созвон сравнивается с перепиской в пределах дня (Я3) |

## 3. Принципы

1. Даты и авторы — **из разметки выгрузки**, не от модели. Модель называет только номера сообщений.
2. Сохранённые отчёты не пересобираются: переход по ссылке — скрипт, который `_serve_report` подмешивает при отдаче.
3. Старые переписки — через уже готовое переизвлечение (REQUIREMENTS-PLAN этап 9): ручные решения переносятся.
4. Новые промпты — новые файлы; LLM только `*_no_think`; `db.commit()` до вызова модели.

## 4. Этап 1 — разбор выгрузки Telegram

- `services/chat_export.py`: `parse_telegram_html(html) -> ChatExport(title, messages)`; сообщение — `id`, `at` (с поясом),
  `author` (у `joined` — автор предыдущего), `text` (ссылки текстом, вложения — «[файл: …]», «[фото]»), `reply_to`, `forwarded_from`.
  Служебные сообщения пропускаются.
- При разборе документа (`process_document_artifact`) выгрузка Telegram распознаётся по разметке и сохраняется как
  `parsed/documents/<artifact_id>_messages.json`; чистый текст для индекса собирается из сообщений в едином виде
  «[25.08.2026 15:58] Имя: текст», который понимает и `contract_text.parse_chat`.
- Дата материала переписки — период «переписка 06.07–27.08.2026» (первое–последнее сообщение), источник `messages`;
  на странице проекта вместо «дата записи неизвестна».
- `scripts/chat_exports.py --project N [--apply]` — разобрать уже загруженные выгрузки (отчёт: сообщений, период, пересечения).
- **Тесты:** `test_chat_export.py` — фрагменты реальной разметки: время с поясом, `joined`, ответ, служебные, вложения;
  `contract_text.parse_chat` понимает новый чистый текст.
- **Готово, когда:** обе выгрузки «ПИЛОТА» дают 146 и 224 сообщения, общий участок 106–148 найден.

## 5. Этап 2 — извлечение из переписки по сообщениям (Я1, Я2)

- `entities._numbered_message_parts`: «M<id> [дд.мм.гггг чч:мм] Автор: текст (в ответ на M105)», части по целым сообщениям,
  хвост предыдущей части — контекст (как у созвона). Сообщения, принадлежащие более ранней выгрузке (Я1), идут блоком
  «Уже разобрано в другой выгрузке — только контекст».
- Промпт `extract_entities_v3.md` (новый файл): для переписки — `messages: [106, 107]` вместо `turns`, `decided_by` с номером
  сообщения согласия.
- `bind_chat_source`: номера сообщений проверяются, пункт привязывается к сообщению с наибольшим совпадением слов;
  в значение пишутся `message_id`, `message_at` (ISO с поясом), `speaker` (автор), `speaker_source="chat"`; «утвердил» —
  по Я2 (автор другого сообщения, ответ или следом, окно 10 сообщений / 24 ч). Нет совпадения — `source_status=unbound`.
- Контракт: источник пункта переписки — из привязки (автор, время, номер сообщения, цитата), `date_basis="message"`;
  совпадение слов — запасной путь. `contract_text.parse_chat` получает сообщения из `_messages.json`, а не угадывает по тексту.
- **Тесты:** `test_entities*.py` / `test_requirements_plan.py` — разбор ответа с `messages`, привязка, «утвердил» в окне и вне
  окна, пересечение выгрузок не даёт второго пункта; `test_contract.py` — автор и время из привязки.
- **Готово, когда:** после переизвлечения переписки «ПИЛОТА» у ≥ 95 % пунктов есть автор, дата и время сообщения;
  общий участок 106–148 не даёт дублей.

## 6. Этап 3 — время пункта в поиске устаревшего (Я3, Я5)

- `review_relevance._items`: момент пункта — `message_at` (переписка), начало записи + `start_sec` (созвон с временем начала),
  иначе только день. `_later` сравнивает моменты; один день без времени у одной из сторон — «неясно».
- Промпт `review_relevance.md` не меняется — в строке пункта вместо даты «25.08.2026 15:58».
- Ручная дата материала принимает и время (`PATCH …/recorded-at` с `datetime`, источник `manual`, точность «минута»).
- **Тесты:** `test_requirements_plan.py` — переписка позже созвона того же дня (время есть / нет), два сообщения одного дня,
  пересечение выгрузок.
- **Готово, когда:** на «ПИЛОТЕ» пункты переписки участвуют в темах и могут заменять и быть заменены.

## 7. Этап 4 — ссылка на место источника

- `services/source_links.py`: `source_url(artifact, *, start_sec=None, message_id=None, quote=None)` →
  созвон `/artifacts/<aid>/report?t=754`, переписка `…/report?m=106`, документ `…/report?q=<первые 80 знаков цитаты>`.
  У каждого источника в контракте и в очереди — `url` и числовой `start_sec`.
- `pages._serve_report` подмешивает `report-jump.js` (как `report-theme.css`): `?t=` — ждёт отрисовки реплик из `data.turns`,
  выбирает реплику по времени, переключает на вкладку стенограммы, прокручивает, подсвечивает, перематывает плеер без
  воспроизведения и показывает «▶ с 12:34» (Я4); `?m=` — сообщение по якорю `m106`; `?q=` — находит текст (без учёта
  пробелов и регистра, иначе — самое длинное совпадение начала), подсвечивает `<mark>`.
- Отчёт переписки рисует сообщения с якорями `id="m106"`, автором и временем (из `_messages.json`), остальное — как было.
- Где появляются ссылки: карточка требования (каждый источник, «Устарело» → что заменило), «Вопросы к заказчику», экран
  конфликтов, источники ответа чата (у чанка созвона — время начала), строки ТЗ — не трогаем.
- Ссылка открывается в новой вкладке; права — как у страницы отчёта (`require_artifact_project`).
- **Тесты:** `test_source_links.py` (адреса по видам источников), `test_pages*.py` (скрипт подмешан в отчёт созвона и документа,
  в `embed`-режиме тоже), проверка в браузере: отчёт открывается на нужной реплике, плеер на 12:34 (скриншот).
- **Готово, когда:** из карточки требования «ПИЛОТА» клик по «▶ 12:34» открывает созвон на этой реплике, клик по источнику
  из переписки — на сообщении.
