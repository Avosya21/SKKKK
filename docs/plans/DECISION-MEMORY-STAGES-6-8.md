## 1. Э6-UI. Экран «История решения» (размер M)

Цель: человек видит, о чём решали, чем закончилось, кто и когда сказал, и может поправить итог. Видно: вкладка-карточка на странице проекта.

### 1.1. Где и как

Страница проекта собирается из сворачиваемых карточек (`project.html`, `include "partials/…_card.html"`, скрипт подключается в строке `current_role in ('admin','manager')` рядом с `background.js`). Делаем так же:
- `app/app/templates/partials/memory_card.html` — карточка «Память решений» (по образцу `background_card.html`: `px-card`, кнопка-заголовок с `collapse`, бейдж со счётчиком «ждёт решения»);
- `app/app/static/memory.js` — вся логика экрана; версия в `?v=1`;
- включение: `{% include "partials/memory_card.html" %}` после `background_card.html`; `<script src="/static/memory.js?v=1">` в той же строке прав.
Карточка видна только админу и менеджеру проекта (как API) и только если у проекта включён флаг `memory_platform` в `settings_json`.

### 1.2. Содержимое карточки

1. **Шапка**: счётчики по состояниям (из `counts` ответа списка): «согласовано N · отклонено N · заменено N · обсуждается N · выполнено N», поиск по названию (`q`), фильтр состояния (`state`), выбор даты «Состояние на дату» (`/memory/state-at`).
2. **Список предметов** (постранично, `limit=50`): строка — состояние (цветной бейдж), название, «с 11.09.2026 13:53», число реплик, итог одной фразой (`summary`), значок «решено человеком», если у предмета событие `decided_by=human` (нужен признак в ответе списка — см. 1.4).
3. **Раскрытие предмета** (`GET …/subjects/{id}`):
   - блок «Позиции» — варианты и значения с состоянием и «заменено: …» (из `positions`);
   - лента реплик: дата-время, сторона (заказчик/исполнитель), автор, вид акта словами, цитата, ссылка «открыть в материале» (поле `url` уже строится `source_links.source_url`: таймкод созвона, сообщение переписки, абзац документа с подсвеченной цитатой);
   - блок «Как менялось»: события журнала (вид, когда, кто, `decided_by`); у событий с неизвестным порядком внутри дня — пометка «порядок внутри дня неизвестен» (`flags.ambiguous_order` свёртки);
   - «Состояние на дату»: поле даты, запрос с `as_of`.
4. **Действия человека** (кнопки только у админа/менеджера): «Согласовано», «Отклонено», «Выполнено», «Снято», «Заменено», «Возобновить» (`POST …/decide`, комментарий до 300 знаков), «Вернуть модели» (`POST …/release`). После действия — перезагрузка карточки предмета; в ленте события человека подписаны именем.
5. Пустое состояние: «Память решений для проекта ещё не построена» и подсказка для админа (кнопка постановки — Э8, пока команда `scripts/build_decision_memory.py`).

### 1.3. Правила интерфейса

- Тексты по-русски, без внутренних терминов («предмет» оставляем: так называет его экран; «акт» → «реплика», «свёртка» не показываем).
- Мобильная вёрстка: список — карточками, лента — списком без таблицы; кнопки в `px-actions`.
- Ошибки API через `errors_ru.js` (по образцу `background.js`).
- Любая цитата — только из ленты, не пересказ; ссылка на источник обязательна для каждой реплики.

### 1.4. Правки API под экран

- В ответ списка добавить `human` (булев: есть активное событие человека) и `positions_count`; считать одним запросом на страницу.
- `GET /projects/{id}/memory/summary` (новый, лёгкий): `{counts, last_built_at, acts_total, needs_attention}` — для бейджа на карточке и чек-листа; `needs_attention` — предметы в состоянии `proposed`/`open` старше 14 дней (срок — константа в сервисе).
- Все новые поля — через существующие функции `_summary`, без новых таблиц.

- JS: самопроверка форматирования (даты, подписи состояний) — по образцу `meeting_layout.selfcheck.js`.

## 3. Э7. Тень и включение (размер L)

Цель: убедиться, что память решений не хуже прежней проверки актуальности, и только потом показывать пользователям и использовать в ответах.

### 3.1. Режим работы

В проекте уже есть режимы автопроверки `off / shadow / live` (`services/auto_review.py`, `review_mode`). Для памяти — собственная настройка в `settings_json` проекта: `decision_memory`: `off` (по умолчанию) / `shadow` / `live`.
- `off` — экран и чат память не используют; построение вручную скриптом.
- `shadow` — память строится и пишется в таблицы, **экран виден только админу**, чат её не использует, отчёт расхождений собирается.
- `live` — экран виден менеджерам, чат использует блок журнала.
Переключатель — в карточке «Память решений» (только admin), запись в `people_log`-подобный журнал не нужна: достаточно `activity_log` (как другие переключатели проекта).

### 3.2. Отчёт расхождений «память против прежнего контура»

Скрипт `scripts/compare_memory_vs_review.py --project N` и экран в карточке (раздел «Расхождения», только admin):
- для каждого пункта проекта (`Entity` типов `decision`/`task`) с адресом источника найти предмет памяти по акту на том же адресе (`speech_acts.unit_ref`/`artifact_id`);
- сравнить состояние: прежнее (`memory_scorecard._state`: current/done/superseded/duplicate/rejected) и новое (`SUBJECT_TO_RULE_STATE` и позиции);
- выдать три списка: **совпадают**, **расходятся** (с цитатами обеих сторон), **есть только в одном контуре**;
- расходящиеся — очередь на разбор человеком: кнопки «Прав прежний контур» / «Права память» (пишут оценку в таблицу `memory_shadow_review`: `project_id`, `entity_id`, `subject_id`, `verdict` (`old`/`new`/`both_wrong`), `by_user_id`, `at`). Эта таблица — основа решения о включении.
- Отчёт строится без модели (код) и без записи в боевые статусы.

### 3.3. Критерий включения (`live`)

По размеченным расхождениям (минимум 30 штук или все, если их меньше) память «права» не реже прежнего контура: `new / (old + new) ≥ 70 %`, ложных «отклонено/заменено» при подтверждённом человеком = 0, M2 ≥ 90 %, A2 ≥ 90 % (**пока не достигнут — см. 3.4**), M6 ≥ 85 %.

### 3.4. Что делать с A2 = 76 %

A2 остаётся ниже порога 90 %. Варианты, которые надо проверить до включения (по одному, с замером на проекте 18 и на втором проекте, чтобы не подогнать под один):
1. Усилить различение «согласился» / «предложил» примерами из реальных ошибок эталона (в промпт `speech_acts.md` — 4–6 коротких пар «реплика → вид» без персональных данных); замер A2.
2. Второй проход модели только по репликам, где вид акта «предложил» или «сообщил факт» после предложения другой стороны (узкий вопрос: «это согласие, новое предложение или справка?»); замер A2 и числа вызовов.
3. Если A2 не растёт — зафиксировать в DECISIONS, что порог для включения в `shadow` — A2 ≥ 75 %, для `live` — M2 ≥ 90 % и согласие владельца; ответственность за вид акта берёт судья (он видит ленту целиком).
Выбор — за владельцем после замеров п.1–2.

Перед включением: взять второй проект с материалами (проект 34 в `data/eval` имеет чат-оценку), построить память, вручную разметить 20 пунктов (скрипт выгрузки листа в CSV по образцу `memory_scorecard --export-people`), измерить A1/A2/M2. ## 4. Э8. Инкремент и очередь (размер M)

Цель: новый материал (созвон, выгрузка чата, документ) дописывается в память сам, без ручного запуска скрипта.

### 4.1. Постановка в очередь воркера

Очередь автопроверки — таблица `jobs`, `kind=auto_review`, поле `scope` в `payload_json`; список допустимых — `queue.REVIEW_SCOPES`; обработчики по scope — `workers/review.py` (`REVIEWERS`); этапы для экрана «Фоновая работа» — `services/project_jobs.STAGES` и `DEFAULT_SECONDS`.
Добавить scope `memory` (на материал) и `memory_judge` (на проект, после всех материалов):
1. `queue.REVIEW_SCOPES` += `memory`, `memory_judge`.
2. `workers/review.py`: обработчик `memory` — `speech_acts.extract_artifact` для материала; `memory_judge` — `subject_windows.assign` (только акты без предмета) → `merge_similar` → `subjects.build_events` → `subject_judge.judge_project`.
3. `project_jobs`: этапы `("memory", "Память решений: реплики")`, `("memory_judge", "Память решений: итоги")`; `FOLLOW_UP_SCOPES` не менять (память не часть обычной «Перепроверки», пока режим `off`); отдельные кнопки «Построить память решений» и «Пересобрать память» в карточке (только admin; `queue_memory(db, settings, project_id, rebuild)`).
4. Порядок: после извлечения требований и до выжимки? — **нет**: память независима от них; ставится последней и не блокирует сводку проекта.
5. GPU: задачи идут общей очередью воркера, модель одна (`llm_lanes`: фоновая полоса); чат не ждёт.

### 4.2. Инкрементальность

- `speech_acts.extract_artifact` уже заменяет акты только этого материала; новые акты получают `subject_id=NULL`, `subject_windows.assign(rebuild=False)` раскладывает только их (известные предметы — кандидаты в окне, центры обновляются).
- `subjects.build_events` пересобирает события правил для всего проекта (дёшево, без модели); события человека не трогаются.
- Судья: пересчитывать только предметы, у которых добавились акты после `subjects.updated_at` (экономия вызовов). Нужен признак «изменён» — взять `max(speech_acts.id)` по предмету против сохранённого в `basis_json` (или добавить `judged_at`; без миграции — сравнивать с `updated_at` предмета).
- Удаление материала: акты и события этого материала снимаются (`artifact_id`), предметы без актов — `is_active=false`; решения человека остаются.
- Переизвлечение материала — те же шаги; повторный разбор уже безопасен для внешних ключей (исправлено 2026-10-06).

### 4.3. Эксплуатация

- Бейдж на карточке и экране «Фоновая работа»: ход этапов `memory`, ошибки, повтор (механизм `retry_errors`).
- Табло: `memory_scorecard.changed_since_last_run` — при смене модели или версии промпта актов/предметов/судьи требовать новую строку табло (уже есть для прежних метрик; добавить версии `speech_acts`, `subject_window`, `subject_merge`, `subject_judge`).
- Размер: копия БД перед первой построенной памятью проекта (как делает скрипт).

### 4.4. Тесты

- Юнит: постановка (дубли не ставятся), обработчик `memory` на подставных данных, инкрементальная раскладка (второй материал присоединяется к предмету первого), судья только изменённых, удаление материала.
- Интеграция: тест полного пути «загрузили материал → задачи → экран показывает предметы» с подменой модели.
- Карта: §3.2 (очередь), §5, §7, §12.2 (если появятся переменные).
