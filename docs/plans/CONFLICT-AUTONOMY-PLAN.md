# PrimaryAnalitics — Автономное разрешение противоречий: созвоны и документы без ручного разбора

Статус: **v1 (2026-09-25): Р1–Р4 приняты, этапы 1, 3–7 сделаны в коде и покрыты тестами; режим по умолчанию — тень. Ждёт: разметки эталона (этап 2) и контрольного прогона `eval_auto_review.py --gold` на живой модели, затем включения live; разовой чистки `scripts/fix_conflict_links.py` по рабочей БД (сначала отчёт).** Продолжение этапа 4 [`AUTO-REVIEW-PLAN.md`](AUTO-REVIEW-PLAN.md).
Цель: система сама решает, какое из двух противоречащих утверждений в силе, объясняет почему и позволяет откатить решение. Человек задаёт правила один раз и видит только сводку важных изменений, а не каждый конфликт.

## 0. Исходное состояние (по коду, 2026-09-25)

| Узел | Где | Что делает сейчас |
|---|---|---|
| Поиск конфликтов | `graph.py::seed_graph` | косинус bge-m3 ≥ `similarity_threshold`, один тип `decision`/`task`/`fact`, разный текст → `POTENTIAL_CONFLICT` |
| Авторазрешение по фразе | `graph.py::_try_auto_resolve` | «отменяем / вместо пункта / исправляем» где угодно в тексте → побеждает `source` |

| Человек | `knowledge.py::resolve_conflict`, `undo_conflict_model` | выбор победителя; «Вернуть» решение модели |

| ТЗ | `tz.py::_collect_project_material` | то же, что в чате, — все конфликты сырым `value_json` |

**Найденные ошибки** (по чтению кода, тестами не подтверждены — подтвердить на этапе 1):

| # | Ошибка | Где | Последствие |
|---|---|---|---|
| О1 | Фраза отмены в материале закрывает **все** открытые автоконфликты проекта, не только его | `_try_auto_resolve` | одно «исправляем ошибку в отчёте» молча выключает чужие решения |

## 1. Решения пользователя

| # | Вопрос | Рекомендация |
|---|---|---|
| Р1 | Иерархия источников (правило кодом, без модели) | **принято:** документ заказчика 3 > решение с `decided_by` / внутренний документ 2 > высказывание 1 > вопрос 0. Противоречие — в силе более весомый, при равном — более поздний. Уточнение при реализации: явная отмена работает, если отменяющий не слабее отменяемого **или сам утверждён** — иначе решение, утверждённое на созвоне после ТЗ («не как в ТЗ, а…»), никогда не смогло бы заменить пункт документа |
| Р2 (**принято**) | Что делает модель | не выбирает победителя, а **классифицирует отношение** двух пунктов (отмена / уточнение / то же / разные объекты / не решение); победителя выводит код по Р1 |
| Р3 (**принято**) | Важные темы — решать автоматически и показывать в сводке (не блокировать) | да: бюджет, сроки, объём работ (scope ТЗ) → запись в сводку «модель изменила: …, Вернуть?» |
| Р4 (**принято**) | Чат при открытом конфликте | не просить уточнение, а отвечать по хронологии: обе версии с датами и источниками + какая в силе и почему |

Поправки `DECISIONS.md` — только после согласия, вместе с кодом этапа, где они нужны (Р1 — этап 3, Р4 — этап 5).

## 2. Принципы (все этапы)

1. **Правило раньше модели.** Всё, что решается датой, весом источника и `decided_by`, решает код. Модели остаётся узкий вопрос: какое отношение между пунктами.
2. **Ничего не удаляется, всё видно.** Проигравший пункт — `is_active=false` + `model_review.reject_kind="superseded"` (как сейчас). В `Resolution.reason` — правило и основание (`rule:<id>`). «Вернуть» работает для любого авторешения.
3. **Человек главнее.** Решение человека и подтверждённую человеком сторону не трогают ни правила, ни модель, ни пересборка графа.
4. **Хронология вместо «победитель/проигравший» для потребителей.** Чат и ТЗ видят «было → стало, с какой даты, по какому источнику».
5. **Тень до включения.** Каждый новый слой сначала работает в `auto_review_mode=shadow`, включается по порогам §9.
6. Правила проекта: LLM только `*_no_think`; `db.commit()` до вызова LLM; новый промпт — **новый файл** (`review_conflict_v3.md`), не правка старого на лету; один GPU-воркер.

## 3. Этап 1 — исправление ошибок О1–О5

- `_try_auto_resolve(db, artifact, source_text)`:
  - только связи, где одна из сторон — сущность **этого** артефакта;
  - «новее» — по `review_conflicts._order_key` (дата материала, таймкод), не по направлению связи;
  - фраза отмены должна быть **в источнике нового пункта** (реплики `turns` / абзац документа), не где угодно в тексте; `исправляем` убрать из шаблона или требовать рядом слово из пункта;
  - пропускать пары, где у проигравшего есть `human_review`;
  - `Resolution.reason = "rule:explicit_cancel — «<фраза>»"`, проигравшему — `model_review` (`reject_kind=superseded`), чтобы работало «Вернуть».
- `seed_graph`: проверка `exists` без направления (`(src,tgt) or (tgt,src)`).
- `rebuild_project_graph`: не удалять связи и `Resolution` с `resolved_by IS NOT NULL`; пары, закрытые человеком, при пересеве не создавать заново.
- Скрипт разовой чистки `scripts/fix_conflict_links.py --project N [--apply]`: схлопнуть обратные дубли, отчёт по конфликтам, закрытым `_try_auto_resolve` (кандидаты на «Вернуть»). По умолчанию только отчёт.
- **Тесты:** `test_graph.py` — фраза отмены в артефакте B не трогает конфликт C↔D; победитель по дате при пересборке; нет дубля A↔B после `rebuild_project_graph`; ручное решение переживает пересборку; подтверждённая человеком сторона не выключается.
- **Готово, когда:** тесты зелёные, отчёт скрипта по рабочей БД показан пользователю.

## 4. Этап 2 — разметка и замер (база для всех решений)

- Выгрузить все `POTENTIAL_CONFLICT` проектов 30 и 35 в `data/eval/conflicts_gold_<дата>.csv`: оба пункта, источники, даты, `decided_by`, тип материала; столбцы для разметки: «отношение» (отмена/уточнение/то же/разные объекты/не решение/неверно извлечено) и «в силе».
- Разметка пользователем (≥ 40 пар). Это единственный ручной шаг плана — дальше он заменяется правилами.
- Сделано: `scripts/eval_auto_review.py --export-gold --project N` дописывает пары в постоянный `data/eval/conflicts_gold.csv`; `--gold` — прогон по размеченным на копии БД (правила + модель, как в live), построчный отчёт и метрики: неверные победители, доля `unsure`, решено правилом.
- **Готово, когда:** есть размеченный набор и замер текущего v2 по нему.

## 5. Этап 3 — слой правил (Р1)

- Новый модуль `services/conflict_rules.py`:
  - `source_weight(entity, artifact)`: документ заказчика (`source_type="document"` + `priority_weight`) / решение созвона с непустым `decided_by` / прочее высказывание созвона / вопрос-вариант;
  - `decide_by_rules(pair) -> RuleVerdict | None`: разный вес → побеждает старший (`rule:source_weight`); равный вес и явная отмена в источнике нового → новый (`rule:explicit_cancel`); одна сторона не решение (нет `decided_by` у decision, вопросительная реплика) → в силе другая (`rule:not_a_decision`); иначе `None` → идёт в модель.
  - **Как сделано:** до модели кодом решается только явная отмена (`review_conflicts.rule_before_model`, общий с `graph._try_auto_resolve`). Вес источника применяется **после** ответа модели «противоречие»: если применить его до модели, пункт документа выключал бы уточнение с созвона («интеграция с банком» → «со Сбербанком по API») — это не противоречие. Функции: `source_weight`, `cancel_allowed`, `winner_by_weight`, `is_material_topic`; перевод ответа модели в вердикт — `review_conflicts.interpret`.
- `review_artifact_conflicts`: правила до модели; вердикт правил пишется тем же `apply_conflict_verdict` с `model="rule:<id>"` и проходит те же защиты (человек, `_source_supports`).
- `DECISIONS.md`: иерархия Р1.
- **Тесты:** `test_conflict_rules.py` (новый) — каждое правило, равный вес → `None`, человек главнее; `test_review_conflicts.py` — правило срабатывает без вызова LLM.
- **Готово, когда:** на наборе этапа 2 правила дают 0 неверных «в силе» и закрывают заметную долю пар без модели (цифру показать).

## 6. Этап 4 — промпт v3: модель классифицирует, код решает (Р2)

- `docs/prompts/review_conflict_v3.md` (новый файл): вход — оба пункта с источниками, датами, весом источника; выход `{"relation": "cancels|refines|same|different_objects|not_decision|misextracted|unsure", "which": "A|B|null", "confidence", "reason"}`.
- Код: `cancels` → в силе та сторона, что отменяет (с проверкой по Р1: вопрос не отменяет решение); `refines`/`same`/`different_objects` → `not_conflict`; `not_decision` → в силе другая сторона; `misextracted` → пункт уходит в очередь автопроверки требований (`review_requirements`) с `reject_kind=not_said`, конфликт закрывается после неё; `unsure` → человеку.
- `PROMPT_VERSION = "review_conflict-v3"`; v2 остаётся файлом для сравнения.
- **Тесты:** `test_review_conflicts.py` — каждое `relation` → ожидаемый итог; `misextracted` не даёт победы.
- **Готово, когда:** на наборе этапа 2 v3 лучше v2 по доле решённых при 0 неверных «в силе».

## 7. Этап 5 — хронология для чата и ТЗ (Р4, О6)

- Общая функция `services/conflict_context.py::conflict_lines(db, project_id, *, entity_ids | artifact_ids)`:
  - только конфликты, касающиеся найденных материалов/сущностей;
  - человеческая строка (`format_entity_line`) для обеих сторон;
  - формат: «В силе: <B> (созвон 19.09, утвердил Иванов). Раньше: <A> (документ 12.09). Основание: правило/модель/человек — <причина>»; открытый конфликт: «Не решено: <A> ↔ <B>».
- `chat._supplement_context` и `tz._collect_project_material` используют её вместо сырого `value_json`.
- `detect_chat_ambiguity`: при `open_conflict` не возвращать уточнение, а передавать обе версии в контекст; `rag_chat.md` — правило «при противоречии назови обе версии с датами и какая в силе». Уточнение остаётся только для `source_split` без правил приоритета.
- `DECISIONS.md`: Р4.
- **Тесты:** `test_chat.py` — открытый конфликт не блокирует ответ; в контексте нет сырого JSON; только конфликты по теме; `test_tz*` — строки хронологии в материале ТЗ.

## 8. Этап 6 — сводка важных авторешений (Р3)

- Тема важности: пункт содержит сумму/валюту, дату/срок или совпадает с требованием контракта (`contract` scope). Функция `is_material_topic(entity)` в `conflict_rules.py`.
- Авторешение по важной теме → запись в `user_activity_log` (`block=knowledge`, `action=auto_resolve`) + блок «Модель изменила» на странице конфликтов (`conflicts.html`) с кнопкой «Вернуть». Работа не останавливается.
- Контрольная выборка (`auto_review_audit_every`) распространяется на конфликты.
- **Тесты:** важная тема → запись в журнале; «Вернуть» из блока возвращает пункт.

## 9. Этап 7 — включение и контроль

- Бэклог: `scripts/auto_review_backlog.py --scope conflicts --mode shadow` по всем проектам, затем сверка с набором этапа 2.
- Пороги включения `live`: неверных «в силе» — **0** на ≥ 20 размеченных; `unsure` ≤ 30% (было 17/26 ≈ 65%).
- Контроль после включения: доля «Вернуть» по авторешениям за 14 дней; если > 5% — проект автоматически обратно в `shadow` (настройка проекта), запись в журнал.
- **Готово, когда:** `live` включён, неделя без откатов выше порога.

## 9а. Эталон — постоянный, не на проект

- Один файл data/eval/conflicts_gold.csv на все проекты: правила и промпт от проекта не зависят, разметка нужна один раз.
