# Личный пароль пользователя — план реализации

Статус: шаги 0–7 сделаны 2026-09-26 (портал работает с `PERSONAL_PASSWORD=off`, пока владелец не включит); шаг 8 — включение — за владельцем. Отличия от плана: страницы `/admin/users` нет (сброс — пункт 7 меню и скрипт), сброс пишется в лог `personal.reset`, а не в журнал действий.

## Цель

Сейчас вход — логин из `Login_up.txt` + Telegram ID + **пароль роли** (общий для всех с этой ролью; роль определяется паролем и живёт в токене сессии). Добавляем второй, **личный пароль** каждого логина:

- пароля ещё нет → после проверки пароля роли человек придумывает пароль (два поля: «Новый пароль», «Повторите») и входит;
- пароль есть → после пароля роли вводит личный пароль и входит.

Пароль роли остаётся и по-прежнему определяет роль. Личный пароль только подтверждает, что это тот самый человек.

## Принятые решения (владелец, 2026-09-26)

| Вопрос | Решение |
|---|---|
| Защита от «захвата» логина, у которого ещё нет пароля | **Не защищаем.** Людей мало, все известны; при захвате админ сбрасывает личный пароль |
| Где хранить | Отдельная БД `data/credentials.db`, только хеши |
| Порядок входа | Два шага: сначала пароль роли, потом личный. Что у логина нет пароля, узнаёт только тот, кто знает пароль роли |

Открыто (решить до шага 7): создание пароля **обязательно** или можно отложить. По умолчанию план делает режимом в `.env` (см. шаг 1), раскатка — `optional` → `required`.
Предположение: одним логином пользуется один человек (DECISIONS «логин общий» — про роли, не про людей). Если это не так — остановиться и обсудить до шага 3.

## Устройство (кратко)

```
Шаг 1  POST /auth/login           логин + Telegram ID + пароль роли
        ├─ режим off                → сессия, как сейчас
        └─ режим optional/required  → {step: "setup" | "personal", ticket} (без сессии)
Шаг 2a POST /auth/login/setup      ticket + новый пароль + повтор → пароль сохранён → сессия
Шаг 2b POST /auth/login/personal   ticket + личный пароль        → сессия
       POST /auth/login/skip       ticket (только optional, только для step=setup) → сессия
```

- `ticket` — JWT на 5 минут, `purpose="login_step"`, внутри `login_key`, `role`, `telegram_id`, `jti`. Одноразовый: использованный `jti` запоминается в памяти до истечения.
- Токен сессии получает поле `pv` (версия личного пароля). Смена или сброс пароля увеличивает версию → все старые сессии этого логина перестают действовать.
- Хеш — Argon2id (`argon2-cffi`). Пароль в открытом виде нигде не пишется: ни в БД, ни в лог, ни в `log_event`.

## Шаг 3. Сервис личного пароля

`app/app/services/personal_password.py` — вся логика здесь, роутеры только вызывают:

- `hash_personal(plain) / verify_personal(plain, hash)` — Argon2id; `needs_rehash` → пересохранить при успешном входе.
- `state(login_key) -> "none" | "set"` (`reset_pending` = `none`).
- `set_password(login_key, new, confirm, *, role_password) -> None` — проверки:
  - `new == confirm`;
  - длина ≥ `personal_password_min_len`, ≤ 128;
  - не совпадает с логином (без регистра) и с введённым паролем роли;
  - без требований «заглавная/цифра/символ».
  Ошибки — понятным текстом по-русски (для показа под полем).
- `change_password(login_key, current, new, confirm)`.
- `reset(login_key)` — для админа/скрипта.
- `current_version(login_key) -> int` — с кешем на несколько секунд (вызывается на каждом запросе).

Тесты: `app/app/tests/test_personal_password.py` — хеш/проверка, правила пароля, версия растёт при смене и сбросе, сброс не возвращает версию к 0.

## Шаг 4. Вход в два шага (API)

`routers/auth.py`:

1. `POST /auth/login` — всё как сейчас (лимит, allowlist, пароль роли, создание/слияние пользователя). Затем:
   - `off` → сессия (поведение без изменений);
   - иначе → `LoginStepResponse {step, ticket, name}`; сессию **не** ставить. Создание пользователя в `users` оставить здесь (как сейчас), чтобы шаг 2 работал по готовой записи.
2. `POST /auth/login/personal {ticket, password}` — проверить ticket, пароль; неудача → `LOGIN_LIMITER.fail` по IP и по логину (те же 8 за 5 мин), 401 «Неверный личный пароль». Успех → сессия + журнал «Вход на сайт».
3. `POST /auth/login/setup {ticket, password, password_confirm}` — только если `state == none`; иначе 409. Успех → пароль сохранён, сессия, журнал «Личный пароль создан».
4. `POST /auth/login/skip {ticket}` — только `optional` и `state == none`; иначе 403.

- Пароль роли в шаг 2 не передаётся повторно — для правила «не совпадает с паролем роли» проверять новый пароль против всех трёх хешей ролей (`authenticate_new_user`).
- `create_access_token` (`dependencies.py`) — добавить `pv`.
- `_user_from_access_token` — при режиме `optional/required` сравнить `pv` из токена с `current_version(login_key)`; не совпало → 401 (страница уйдёт на `/login`). Токены без `pv` (выданы до включения) считать `pv=0`.
- `user_activity.py`: действия `ACTION_PASSWORD_SET`, `ACTION_PASSWORD_CHANGE`, `ACTION_PASSWORD_RESET`.
- `log_event`: `login.step`, `personal.set`, `personal.denied`, `personal.reset` — без паролей.

Тесты (`test_auth.py`, новый `test_login_personal.py`):
- `off` — старые тесты проходят без правок;
- новый логин: шаг 1 → `setup` → пароль создан → cookie сессии;
- повторный вход: шаг 1 → `personal` → верный пароль → сессия; неверный → 401;
- 8 неверных личных паролей → 429;
- ticket: просрочен, повторно использован, подделан, `purpose` другой — 401;
- без пароля роли до шага 2 не дойти (шаг 2 без ticket — 401/422);
- `required` + `skip` → 403; `optional` + `skip` → сессия;
- `setup`, когда пароль уже есть → 409;
- смена пароля → старый cookie даёт 401, новый вход работает;
- ответ шага 1 одинаков по времени/форме для неверного пароля роли и неизвестного логина (как сейчас).

## Шаг 6. Смена и сброс

- **Смена своего пароля:** пункт в меню пользователя в шапке → модальное окно «Текущий / Новый / Повторите» → `POST /auth/password/change`. После смены — новая сессия в этом браузере, остальные устройства разлогинены.
- **Сброс админом — из меню запуска `main` в PyCharm** (решение владельца 2026-09-26, страницы в портале не делаем). В меню выбора LLM (`startup_llm._pick_cli`) пункт **7 — сбросить личный пароль пользователя**:
  1. выводится нумерованный список логинов из `Login_up.txt`: есть ли личный пароль, дата создания, последний вход (из `users`/журнала);
  2. ввести номер из списка **или** логин;
  3. подтвердить «да» → `personal_password.reset(login_key)`, в консоль — «Пароль сброшен, при следующем входе <логин> создаст новый»; запись в `log_event`;
  4. меню показывается снова (как после пункта 9).
  Подключение — через `actions` в `resolve_llm_provider_at_startup`, как у пункта 9.
- Пункт **9 — перевыпустить пароли ролей** уже сделан (2026-09-26): подтверждение «да», новые пароли печатаются в консоль, хеши пользователей синхронизируются (`_run_credentials(reset=True)`).
- **Скрипт на случай запуска без PyCharm** (служба): `scripts/personal_password.py list | reset <логин>` — работает с `credentials.db` напрямую, без входа.

Тесты: смена с неверным текущим → 400; пункт 7: выбор по номеру и по логину, неизвестный логин, отказ от подтверждения ничего не меняет; после сброса вход ведёт на `setup`, старые сессии этого логина → 401; скрипт `reset` на временной БД.
