# PrimaryAnalitics — Кадры экрана: время, момент, дубли, база знаний

**Статус:** план, 2026-09-25. Продолжение [`MEETING-SCREEN-PLAN.md`](MEETING-SCREEN-PLAN.md) (C1–C2 сделаны, C3–C4 впереди).

## Зачем

Разбор 2026-09-25 показал:

1. **Кадры привязаны к неправильному времени.** Рекордер пишет кадр не чаще 1/с, а ffmpeg считает время файла по номеру кадра. Реальный интервал ≈1,13 с, поэтому файл короче показа на 10–15%. Отставание растёт от 0 в начале показа до 4–6 мин в конце 35–42-минутного показа. Замер по всем 7 записям — в разделе «Факты».
2. Реплики в последних 10–15% показа не получают кадров: `share_end` считается по длине файла.
3. Кадр берётся в первую секунду фразы: видно экран до действия, о котором говорят.
4. Одинаковые экраны описываются vision-моделью заново: 7 описаний одного окна Docker подряд.
5. В базе знаний описания экрана занимают 88% текста созвона (проект 33: речь 27 тыс. знаков, экран 206 тыс.). «Речь на экране» дублирует реплики в индексе. Экранные блоки уходят в извлечение сущностей.
6. Разные места привязывают кадр к реплике по-разному: `speech_screen_links.json` никто не читает, HTML и `_append_screen_context` считают свои окна, `summarize_call` берёт только реплики того, кто показывает, и другой прогон.

## Ш1. Рекордер пишет по реальному времени

**Где.** `tools/livekit/screen_recorder.py` (`ScreenWriter.consume`, `close`), `app/app/services/meeting_recordings.py` (`upsert_screen_video`, `set_screen_video_frames`).

**Что.**
1. Номер кадра в файле всегда равен секунде показа: `due = floor((now − started_epoch) · fps) + 1`. Пока `frames < due`, в ffmpeg пишется последний кадр. Новый кадр пишется, как только его время пришло.
   - Если кадры пришли раньше срока, лишнее отбрасывается, как сейчас.
   - Если был провал (замерший экран, сеть), дыра заполняется повтором предыдущей картинки. Это правда: экран не менялся.
2. `close()` дописывает повторы до `ended_epoch`, чтобы длина файла совпала с длиной показа (±1 кадр).
3. В манифест пишется `"timebase": "wall"`. По этой метке Ш2 отличает новые записи от старых.
4. Статистику повторов (`dup_frames`) пишет в манифест и в событие `track end`. Видно, насколько часто экран замирал.

**Ограничение.** Размер файла вырастет примерно на 12%: повторные кадры при `keyint=1` весят как обычные. Это приемлемо. Если не так, повторы можно кодировать P-кадрами, но это отдельное решение.

**Тест** (`test_screen_recorder.py`):
- кадры приходят каждые 1,13 с в течение 100 с → записано 100 кадров ±1;
- кадров нет 30 с → 30 повторов;
- 30 кадров за 1 с → записан 1;
- `close()` после 5 с тишины дописывает 5 кадров;
- в манифесте есть `timebase: wall`.

**Живая проверка.** Созвон с показом экрана 5+ мин: `frames / fps` совпадает с `ended_epoch − started_epoch` ±1 с. На экране показа — секундомер. Кадр на файловой секунде N показывает секундомер ≈ N (+ задержка сети).

**Осторожно.** Перезапуск `primaryanalitics-rec` — только когда нет живых комнат (урок потерянного созвона: одна копия, без перезапусков во время записи).

## Ш2. Одна шкала времени для кадров (и старые записи)

**Где.** `app/app/services/meeting_frames.py`, `app/app/services/meeting_analyze.py` (`_track_contract`).

**Что.**
1. `_track_contract` переносит в контракт `ended_epoch`, `frames`, `fps`, `timebase`.
2. Новая функция `track_clock(track) → (offset, wall_duration, k)`:
   - `timebase == "wall"` → `k = 1`;
   - иначе `k = (ended_epoch − started_epoch) / (frames / fps)`. Если `k` вне `[1.0; 1.35]` или нет `ended_epoch`, то `k = 1`, и в лог пишется `meeting.video_clock.suspect`.
3. Все переводы времени идут через две функции:
   - `file_to_meeting(ts) = offset + ts · k`;
   - `meeting_to_file(t) = (t − offset) / k`.

   Их используют:
   - `_speech_marks` — начала реплик переводятся в секунды файла;
   - `t_rel` кадра считается через `file_to_meeting`;
   - конец показа `share_end = offset + wall_duration`: в окна попадают реплики до реального конца показа;
   - `scene_times` остаются в секундах файла: они и так на шкале файла.
4. В `frames.json` у кадра добавляется `clock_k`, чтобы было видно, какой коэффициент применён.

**Тест** (`test_meeting_frames.py`):
- трек со старой шкалой, 1872 кадра, реальная длина 2112,5 → кадр на 1788 с файла получает `t_rel = offset + 2017,7`;
- реплика на 2200 с встречи (в хвосте показа) получает кадр;
- `timebase: wall` → `k = 1`;
- нет `ended_epoch` → `k = 1` и запись в лог.

**Готово.** Ш0 на пр. 33 показывает 0 реплик без кадра в хвосте показа. Кадр Docker оказывается рядом с «А докер — что такое?».

## Ш6. Одно правило «кадр ↔ реплика» (делается вместе с Ш2)

**Где.** `meeting_frames.py`, `pipeline_lab.py` (`_append_screen_context`, `load_run_screen_segments`), `artifact_lab.py` (`vision_run_id`), `asr/summarize_call.py` (`_attach_video_context`), `asr/transcript_view.py`.

**Что.**
1. Окно кадра считается один раз в `frame_windows(rows, tracks)`: `[t_k; t_{k+1})` **внутри своего показа**, у последнего кадра показа окно заканчивается на `share_end` (сейчас оно берётся от кадра другого показа или имеет нулевую длину). Окна пишутся в `video_transcript.json` (`start`/`end`), а `bind_replicas` использует те же окна.
2. `speech_screen_links.json` становится единственным источником связей. Его читают `_append_screen_context` (вместо собственного пересечения), HTML стенограммы (вместо `screen_idx` по времени) и `summarize_call`.
3. `summarize_call`: берёт тот же прогон и те же связи. Экран прикладывается ко всем репликам, пересекающимся с окном, с пометкой `relation` (`own_share` / `over_others_share`). Сейчас только к репликам того, кто показывает; см. вопрос В3.
4. Прогон: экран берётся из того же прогона, что и реплики. `vision_run_id` остаётся только как запасной вариант для старых прогонов без описаний. Неверный docstring «кадры на всех прогонах идентичны» исправить.

**Тест:**
- два показа подряд, у последнего кадра первого `end = share_end` первого показа;
- одна и та же реплика видит один и тот же набор кадров в `speech_screen_links.json`, в `_final.txt`, в HTML и в выжимке;
- прогон без `speech_screen_links.json` (старый) — запасной расчёт по окнам, без ошибки.

## Ш3. Кадр после начала фразы, а не в первую секунду

**Где.** `meeting_frames.py` (`_speech_marks`, `select_share_frames`).

**Что.**
1. Метка речи ставится на `начало + min(2,5 с; половина фразы)`, но не позже конца фразы. Константа `SPEECH_SHIFT_SEC = 2.5`.
2. Если внутри фразы есть смена картинки (`scene`), берётся она, а не сдвинутое начало. Показанное «вот сейчас открою» попадает в кадр после открытия.
3. Правило кластера 8 с и дедупа 2 с не меняются.

**Тест:**
- фраза 0–10 с без смены сцены → кадр на 2,5 с;
- фраза 0–3 с → кадр на 1,5 с;
- фраза 0–10 с со сменой сцены на 4 с → кадр на 4 с;
- края показа не сдвигаются.

## Ш4. Одинаковые экраны: описывать один раз

**Где.** `meeting_frames.py` (`_extract_track`, `_write_video_transcript`).

**Что.**
1. После снятия jpg — сравнение с предыдущим **описанным** кадром этого показа: уменьшенная серая копия 64×36, средняя разница пикселей. Порог `SAME_SCREEN_DIFF` подбирается на кадрах пр. 33 (Docker ×7 — одинаковые, смена вкладки Cursor — разные). Точная сумма `sha256` не годится: курсор и часы меняют байты.
2. Похожий кадр не отправляется в vision-модель. В `frames.json` у него `same_as: <frame_id>`, а текст копируется от оригинала.
3. В `video_transcript.json` подряд идущие одинаковые кадры склеиваются в один сегмент с общим окном. В базу знаний и в HTML идёт одно описание на период, jpg остаются все.
4. Лог `meeting.video_frames.dedup` с числом склеенных кадров.

**Тест:**
- два одинаковых jpg → vision вызывается 1 раз, сегмент 1;
- одинаковые кадры, разделённые другим (A B A), не склеиваются через B;
- сумма окон склеенного сегмента = сумма окон исходных кадров.

**Готово.** На пр. 33 число вызовов vision и объём экранного текста падают. Ожидаемо в 2–4 раза, точная цифра — после Ш7.

## Ш5. База знаний: экран без мусора

**Где.** `pipeline_lab.py` (`_append_screen_context`), `entities.py` (`_numbered_turn_parts`), `chunking.py`, `transcript_turns.py`.

**Что.**
1. Блок «Речь на экране» в `_final.txt` больше не пишется. Реплики уже лежат в стенограмме, а связь «кадр ↔ реплика» живёт в `speech_screen_links.json` и HTML. Разбор `KIND_SCREEN_SPEECH` остаётся для чтения старых файлов.
2. Экранные блоки не участвуют в основном извлечении сущностей: `_numbered_turn_parts` берёт только речь. Факты с экрана — отдельным проходом C3 (`frame_id` + издатель), см. вопрос В2.
3. Экранный фрагмент индекса получает `start_sec`/`end_sec` из исправленных окон (Ш2/Ш6) и метку показавшего в тексте, как сейчас.
4. Объём: после Ш4 оценить долю экрана заново. Если доля всё ещё больше половины текста созвона — см. вопрос В1.

**Тест:**
- `_final.txt` после публикации не содержит «Речь на экране»;
- `_numbered_turn_parts` не содержит строк «Экран (показывал»;
- `chunk_transcript` на старом `_final.txt` с «Речь на экране» не падает;
- поиск по фразе из речи возвращает один фрагмент, а не два.

**Переиндексация.** Для созвонов с экраном — `index_artifact` + пересборка сущностей. Сущности пересобираются через LLM, стоимость известна заранее: список созвонов из Ш7.

## Ш7. Перепрогон старых созвонов

**Где.** `scripts/rebuild_screen_frames.py` (новый; основа — `scripts/redescribe_screen_frames.py`).

**Что.** Для каждого созвона с `screen_video`:
1. Заново снимает кадры из MP4. MP4 не удаляются (DECISIONS: кадры извлекаются повторно).
2. Описывает кадры с учётом Ш4.
3. Пишет `frames.json`, `speech_screen_links.json`, `video_transcript.json` в **новый** прогон, старый не трогает.
4. Публикует стенограмму, переиндексирует, пересобирает сущности.

Флаги:
- `--dry-run` — только список созвонов и число вызовов vision;
- `--artifact <id>` — один созвон.

**Список** (`frames.json` на 2026-09-25): пр. 23 `art_2026-09-21_161623_fa46df`, пр. 30 `art_2026-09-20_222340_03aca8` и `art_2026-09-22_011911_9b9158`, пр. 31 `art_2026-09-24_102120_e7fa0f`, пр. 33 `art_2026-09-23_143905_91bc2e`. Перед запуском `--dry-run` сверит, что список полный.

**Осторожно.** Резервная копия артефакта перед публикацией (как `data/backups/meeting*-before-repair-*`). Без `git checkout` по грязным файлам.

**Готово.** Ш0 «после» на пр. 33: 0 реплик без кадра, Docker на 36:45, доля экрана и число повторов ниже, чем «до».
