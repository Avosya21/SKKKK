## 2. Принципы (обязательны для всех этапов)

1. **Модель решает, человек видит спорное.** Вердикт: `confirm` / `reject` / `unsure`. Человеку — только `unsure` + контрольная выборка.
2. **Решение модели отличимо от человеческого.** `needs_review` сохраняет смысл «человек не смотрел». Вердикт модели — в `value_json.model_review` `{verdict, reason, confidence, at, model, prompt_version, audit}`. Человеческое `human_review` всегда главнее.
3. **Ничего не удаляется.** Отказ модели = `is_active=false` (как у человека), любое авторешение отменяется одной кнопкой «Вернуть», отмена пишется как решение человека.
4. **Контрольная выборка.** Каждое 20-е авторешение (детерминированно по `entity.id`) дополнительно идёт человеку с пометкой «проверка модели» — по ним видна доля ошибок.
5. **Теневой режим до включения.** Сначала модель пишет вердикты без последствий; включаем, только когда согласие с человеком на выборке ≥ порогов §9.
6. **Фоном, не мешая расшифровке.** Отдельный вид задачи в очереди с низким приоритетом: `process_artifact` всегда берётся первым. Один GPU-воркер (инвариант).
7. **Правила проекта:** LLM только через `*_no_think` (`test_llm_no_think_guard.py`); `db.commit()` до каждого вызова LLM (DECISIONS 2026-09-21); оба провайдера `lmstudio`/`cursor` через `services/llm.py`; для lmstudio — `prepare_for_llm`.
8. **Урок 2026-09-23:** работающий процесс читает промпты с диска на лету, а код держит старый. Новые задачи — **новые файлы промптов**; существующие промпты меняются только вместе с перезапуском воркера и API.

## 3. Этап 1 — каркас автопроверки и теневой режим

**Очередь**
- `Job.kind`: новый вид `auto_review` (сейчас всё `process_artifact`). `payload_json`: `{"scope": "artifact"|"conflicts", "mode": "shadow"|"live"}`.
- `queue.claim_next_job`: приоритет — `process_artifact` раньше `auto_review` (`ORDER BY CASE kind WHEN 'process_artifact' THEN 0 ELSE 1 END, created_at, id`).
- `queue.enqueue_auto_review(db, artifact_id, scope, mode)`; не ставить дубль, если такой же `queued`/`running` уже есть.
- `gpu_worker.run_once`: ветка по `job.kind` → `workers/review.py::process_review(db, settings, job)`. Ошибка ревью не трогает статус артефакта (он уже `done`), только `job.error`.
- Постановка: в конце `run_knowledge_pipeline` (после `done`) → `enqueue_auto_review(artifact, "artifact")` и, если `seed_graph` создал конфликты, `"conflicts"`.

**Настройки** (`config.py`, `.env.example`, переопределение в настройках проекта):
`AUTO_REVIEW_MODE=shadow|live|off` (по умолчанию `shadow`), `AUTO_REVIEW_AUDIT_EVERY=20`, `AUTO_REVIEW_BATCH=5` (сущностей на вызов LLM), `VOICE_AUTO_ACCEPT_MIN=0.85`, `VOICE_AUTO_ACCEPT_MARGIN=0.10`.

**Запись решения** — `services/auto_review.py`:
- `record_model_review(entity, verdict, reason, confidence, mode)` → `value_json.model_review`; в `live`: `reject` → `is_active=false`; `confirm` → ничего больше (контракт читает `model_review`).
- `undo_model_review(entity, user)` → вернуть `is_active`, `model_review.undone={by, at}`, записать `human_review`.
- `is_audit(entity_id)` → `entity_id % AUTO_REVIEW_AUDIT_EVERY == 0`.
- `model_review` добавить в `graph.PROVENANCE_KEYS` (не входит в эмбеддинг и сравнение), в `knowledge._keep_provenance` сохраняется.
- Журнал: `review.verdict` (artifact, entity, verdict, confidence, mode), `review.undo`.

**Тесты:** `test_auto_review_queue.py` (приоритет, без дублей, ошибка ревью не портит артефакт), `test_auto_review_record.py` (shadow без последствий, live reject/undo, audit), страж `*_no_think` и `PRIMARY_ANALITICS_STRICT_DB_HOLD=1` зелёные.

## 4. Этап 2 — проверка требований (decision / task)

**Вход для модели** на каждую сущность: текст, тип, срок/исполнитель; окно реплик вокруг `start_sec` (±4 реплики речи из `transcript_turns.load_turns`, строки как в каноне `[05:51 - 07:34] Имя: текст`); дата созвона (`material_date_label`). У старых сущностей без `start_sec` — окно через `entities._match_turn` по тексту; не нашлось → сразу `unsure` (к модели не идём). Документы — абзац-источник через `contract._evidence` / цитату; нет цитаты → `unsure`.
Пакет: до `AUTO_REVIEW_BATCH` сущностей одного созвона в одном вызове (окна объединяются), чтобы 1505 шт. не заняли сутки.

**Промпт** `docs/prompts/review_requirement.md` (новый файл): вердикт на каждую сущность
`{"id", "verdict": "confirm|reject|unsure", "reject_kind": "not_said|not_decision|duplicate|noise|null", "reason": "≤200 знаков", "confidence": 0..1, "decided_by": [{"name", "turn"}]}`.
Правила в промпте: `confirm` — в окне действительно прозвучало и принято/поручено; `reject` — нет в окне / вопрос-обсуждение без итога / дубль соседней сущности / шум; сомнение → `unsure`. `decided_by` — кто утвердил/явно согласился.

**Код** `services/review_requirements.py`:
- `review_artifact_requirements(db, settings, artifact, mode)`: сущности `decision/task`, `is_active`, без `human_review`, без `model_review` той же `prompt_version`.
- Пороги: `confirm` при `confidence ≥ 0.7`; `reject` при `confidence ≥ 0.8`; иначе `unsure`.
- `decided_by`: проверка теми же правилами, что при извлечении (`entities._validated_decided_by`: реальная реплика речи, имя совпадает, ≤ 5 реплик); пишется, если у сущности пусто. Так заполняется «кто утвердил», которого сейчас почти нет (2 из 68 на проекте 35).
- Дубли внутри созвона сначала без LLM: `_text_overlap` ≥ 0.8 с другой сущностью того же типа → `reject/duplicate` у короткой.

**Контракт и потребители** (`verification` сейчас читают: `contract.py:455`, `project_mcp_data.py:198`, `requirement_review.review_list`, `routers/project_mcp.py:180`, `px_agent.js:76`, `agent_guide.py:50`, `docs/agent-exchange/CONTRACT.md`):
- `verification`: `human_confirmed` (есть `human_review` confirm/status) → `model_confirmed` (live, `model_review.verdict=confirm`) → `extracted`.
- В контракт — `model_review` `{verdict, reason, at, prompt_version}` рядом с `human_review`; `_fingerprint` учитывает число `model_review`, чтобы кэш не отдавал старое.
- `review_list`: фильтр по умолчанию «нужен человек» = `extracted` без вердикта + `unsure` + контрольная выборка; счётчик `requirements_unconfirmed` → «ждут человека».
- `px_agent.js`: бейдж «подтверждено моделью» / «отклонено моделью» с причиной; кнопка «Вернуть»; вкладка-фильтр «Проверка модели» (контрольная выборка) с кнопками «Согласен / Не согласен».
- `agent_guide.py`, `CONTRACT.md`, `POLICY.md`: описание `model_confirmed` — «проверено локальной моделью по реплике-источнику, не человеком».

**Тесты:** `test_review_requirements.py` (разбор ответа, пороги, дубли без LLM, `unsure` без окна, `decided_by` отбрасывается при чужом имени, shadow/live), `test_contract.py` (три значения `verification`, человек главнее модели), `test_project_mcp.py`, `test_requirement_review.py` (фильтр «ждут человека»).

## 5. Этап 3 — спикеры

**3а. Автопринятие узнанных голосов** (правило §0: cosine ≥ 0.85, отрыв ≥ 0.10):

- Профиль голоса **не** дообучается автопринятием: не вызывать enroll и `sync_confirmed_to_global` (она сравнивает эмбеддинги профиля с global-реестром и может слить профили) — авто-ссылка указывает на уже существующий профиль-кандидат как есть.
- UI match: у авто-имени значок «узнан автоматически (0.91)», «Это не он» → обычный выбор.

**3б. Подсказка имени неизвестного голоса моделью:**
- Промпт `docs/prompts/suggest_speaker_names.md` (новый): реплики `speaker_N` + обращения к нему и самопредставления («Павел, вы меня слышите?», «Меня зовут…») + участники проекта (`participant` сущности, известные профили проекта).
- Результат — только **подсказка** в UI (`matches[label].llm_hint = {name, evidence_quote}`), не имя. Имя новому человеку даёт пользователь.

**3в. Неблокирующий шлагбаум (R3):**
- `pipeline_lab._process_lab_core`: вместо `speakers_pending` при неизвестных голосах → `transcript_ready` с именами для узнанных и `Спикер N` для остальных; знания строятся сразу; артефакт получает флаг `speakers_unnamed=[...]` (в match JSON) и уведомление «Назовите N голосов».

- `voice_gate_before_asr` остаётся выключателем: `strict` (как сейчас) / `soft` (новое, по умолчанию после R3).

## 9. Приёмка теневого прогона и критерий готовности

`scripts/eval_auto_review.py --project N --sample 60` — случайные теневые вердикты в HTML/терминал, человек отмечает «согласен/нет» (≈ 15 минут), скрипт считает:

| Метрика | Порог для `live` |
|---|---|
| Ложный `confirm` (модель подтвердила то, что человек отклонил бы) | ≤ 5 % |
| Ложный `reject` (модель отклонила верное) | ≤ 2 % |
| Доля `unsure` (идёт человеку) | ≤ 25 % |
| Конфликты: неверный победитель | 0 на выборке 20 |
| Голоса: ошибка автопринятия | 0 (правило 0.85/0.10 на истории — 0 из 26) |

Готово, когда:
- на проектах 18 и 35 очередь «ждут человека» ≤ 25 % от прежней, а контрольная выборка не показывает ошибок выше порогов;
- новый загруженный созвон без человека доходит до `done` (R3), знания с именами узнанных голосов, неизвестные — `Спикер N`; после «Запомнить» имена обновляются в чате, сущностях, индексе и выжимке;
- расшифровка ни разу не ждала автопроверку (журнал: `process_artifact` берётся раньше `auto_review`);
- любое авторешение отменяется одной кнопкой; `pytest app/app/tests` зелёный; `check_map_drift` чистый.
