## 1. Цель и критерий «готово»

Любой разработчик или ИИ-агент, не знавший проекта, за один запрос получает:

| Что нужно знать | Пример вопроса | Чем отвечает |
|---|---|---|
| Где что лежит | «где подтверждение требований» | путь, строка, назначение |
| Как работает | «что делает `log_activity` с сессией» | фрагмент кода функции с окружением |
| Кто кого вызывает | «кто вызывает `log_activity`» | точный список вызовов, не догадка |
| Какой путь запроса | «`GET /projects/{id}/artifacts`» | роут → зависимости → сервис → таблицы, роль |
| Что в БД | «кто пишет в `meeting_participants`» | схема, миграции, читатели/писатели |
| Какие настройки | «за что отвечает `LIVEKIT_TOKEN_TTL_HOURS`» | значение по умолчанию, где читается, где описано |
| Чем это проверено | «какие тесты покрывают `rate_limit`» | тесты, команда запуска |
| Почему так | «почему Caddy, а не Nginx» | запись из DECISIONS / FINDINGS |
| Что менялось | «что правили в комнате за неделю» | коммиты, незакоммиченные правки |
| Что нельзя ломать | «инварианты по ролям» | список инвариантов с источником |
| Как запускать и где смотреть | «где лог API, какой порт» | процессы, порты, логи, каталоги |

**Приёмка всего плана:**

1. Золотой набор ≥ 60 вопросов ([Фаза 0](#фаза-0-измерять-до-того-как-улучшать)) — **recall@5 ≥ 85 %** (нужный файл среди пяти первых), сейчас — измеряется в Фазе 0.
2. Индекс не старше кода: после любой правки актуализация занимает секунды, а поиск предупреждает об устаревании.
3. Карта и индекс не расходятся с кодом: проверка дрейфа зелёная в `qa_all.py`.
4. Агент использует индекс первым по правилу репозитория, а не по памяти.

## 2. Принципы

1. **Один источник правды.** Карта в `docs/` описывает смысл; всё, что можно вывести из кода (список роутеров, моделей, скриптов, переменных окружения, роутов), **генерируется**, а не пишется руками. Руками — только «зачем» и инварианты.
2. **Точность важнее красоты.** Вопросы про идентификаторы (`QueuePool`, `log_activity`) решаются точным поиском и таблицей символов, а не эмбеддингами. Вопросы «про смысл» — векторами. Работают вместе.
3. **Каждый ответ — с адресом.** Всегда `путь:строка`, чтобы сразу открыть файл. Ответ без адреса считается непригодным.
4. **Индекс устаревает молча — этого нельзя допускать.** Свежесть проверяется автоматически.
5. **Ничего секретного в индексе.** `.env`, `Login_up.txt`, токены, `data/`, `venv*` — не индексируются и не попадают в ответы.
6. **Индекс не трогает GPU и боевую БД.** Эмбеддинги — Ollama на CPU (`num_gpu=0`), хранилище — отдельный `data/project_map.db`, ни одной записи в `app.db`.
7. **Каждый шаг закрывается измерением** на золотом наборе: улучшение доказано числом.

## Фаза 2. Гибридный поиск: точный + по смыслу

**Зачем:** эмбеддинги плохо ловят идентификаторы, сообщения об ошибках и редкие слова.

| Шаг | Что делать | Готово, когда |
|---|---|---|
| 2.1 | Таблица FTS5 `map_fts` (токенизация по идентификаторам: `snake_case`, `camelCase`, точки, дефисы; ru+en) рядом с `map_vectors` | запрос `QueuePool` находит `db.py` и упоминания |
| 2.2 | Слияние выдачи (reciprocal rank fusion) вектора и FTS; вес настраивается | на золотом наборе не хуже лучшего из двух по каждой группе |
| 2.3 | Понимание запроса: если в запросе есть идентификатор из репозитория (`snake_case`, путь, `id` узла, эндпоинт) — поднять точное совпадение; иначе — смысловой | вопросы с идентификаторами дают точное попадание первым |
| 2.4 | Расширение запроса синонимами предметной области (словарь: «сессия БД» ↔ `Session`, `get_db`; «микрофон» ↔ `mic`, `audioinput`; «встреча» ↔ `meeting`; «динамик» ↔ `speaker`, `sink`) в `scripts/index_glossary.yaml` | словарь пополняем, тест на 10 синонимов |
| 2.5 | Переранжирование топ-30 (необязательно): локальный кросс-энкодер или та же LLM в режиме `no_think` только по запросу `--rerank` | измерено на золотом наборе; включаем, только если даёт ≥ 3 п.п. recall@5 |
| 2.6 | Фильтры: `--kind`, `--path`, `--since`, `--lang`, `--doc-only`, `--code-only` | фильтры работают и покрыты тестом |

**Тест:** золотой набор по группам; отдельные тесты токенизатора идентификаторов.

## Фаза 5. Актуальность: инкрементальность, свежесть, автоматическое обновление

| Шаг | Что делать | Готово, когда |
|---|---|---|
| 5.1 | Хеш каждого файла в `map_files(path, sha, indexed_at)`; переиндексация только изменённых; удалённые файлы удаляются | повторный запуск без правок < 5 с; правка одного файла — секунды |
| 5.2 | Кэш эмбеддингов по хешу текста фрагмента (`embedding_cache`): неизменённый фрагмент не пересчитывается даже при переименовании файла | доля пересчёта на типичной правке < 5 % |
| 5.3 | Блокировка индексатора (один процесс), защита от прерывания (запись во временную БД → атомарная замена) | параллельный запуск безопасен; обрыв не портит индекс |
| 5.4 | Проверка свежести в поиске: перед ответом сверять `mtime`/хеши; если изменённых файлов > 0 — предупреждение `индекс отстаёт на N файлов` и, при `--auto`, дообновить только их | предупреждение выводится в тесте |
| 5.5 | Запуск: git-хуки `post-commit`/`post-merge` (необязательные, ставятся `scripts/install_hooks.ps1`), вызов в `restart.ps1`, команда `py scripts/index_project_map.py --changed` | после коммита индекс обновляется без ручных шагов |
| 5.6 | Долгие индексации — только в фоне, с логом прогресса в `data/logs/index.log`; учесть таймауты Windows и `PYTHONIOENCODING=utf-8` | индексация полной сборки не блокирует терминал |
| 5.7 | Индексатор **не занимает GPU** (Ollama CPU), не трогает `app.db`, лимит памяти на батч | проверено в тесте (мок Ollama) и вручную |

## 5. Риски и решения

| Риск | Решение |
|---|---|
| Полная сборка на CPU долгая | кэш эмбеддингов, инкрементальность (Фаза 5), фоновый запуск |
| Динамические вызовы Python не видны в графе | помечать связи «неточно», не выдавать за факт; `grep` остаётся запасным путём |
| Разбор JS регулярными выражениями хрупок | при провале — `tree-sitter`; тесты на реальных файлах комнаты |
| Индекс расходится с кодом | проверка свежести в поиске, хуки, шаг в `qa_all.py` |
| Утечка секретов | исключения + маскирование + тесты (принцип 5) |
| Индекс «врёт» уверенным тоном | порог уверенности, источник совпадения, требование проверять в файле |
| Слишком много шума в выдаче | фильтры, гибридное ранжирование, измерение recall и precision по группам |
