# Карточка пользователя — план реализации

Статус: шаги 0–12 сделаны 2026-09-26; шаг 13 (включение) — перезапуск сервера за владельцем. Отличия от плана: `optional` убран совсем (ошибка старта); путь `credentials.db` по умолчанию — в `DATA_DIR` (QA-экземпляр не трогает боевую базу); сессия проверяет и саму карточку (сброс админом закрывает сессии сразу); модальные окна шапки перенесены после `<main>` (скрипты искали поля входа как `form input`); голос — только задел (`user_id`, привязка по подтверждению). Продолжение `PERSONAL-PASSWORD-PLAN.md` (личный пароль сделан, шаги 0–7).

## Цель

При первом входе, после личного пароля, человек заполняет **карточку**: фамилия, имя, компания (из списка), должность, фото; на форме — уведомление о том, что голос используется для распознавания в записях. Без личного пароля и без заполненной карточки на портал не пускаем. Потом сессия живёт 30 дней или до «Выйти».

Карточка — постоянная сущность «человек», к которой дальше привязываются: фото в плитке созвона, голосовые слепки, сторона (исполнитель/заказчик) в анализе документов, будущий чат.

## Решения владельца (2026-09-26)

| Вопрос | Решение |
|---|---|
| Личный пароль | Обязателен всегда: «Позже» убираем, режим по умолчанию `required` |
| Поля | Фамилия, имя (**без отчества**), компания из списка, должность, **фото — обязательно** |
| Список компаний | Файл в корне проекта (как `Login_up.txt`); пока одна: `ACME`, пометка «Исполнитель» (в списке не видна, нужна анализу) |
| Кто меняет компанию | **Только админ.** ФИО, должность и фото человек меняет сам |
| Согласие на голос | **Не галочка, а уведомление об автоматическом согласии**: текст на форме карточки, «Сохранить и войти» = согласие. Сохраняем дату и версию текста. Отозвать — через админа (слепки удаляются). Риск владельцу назван: для биометрии 152-ФЗ ст. 11 требует письменного согласия, уведомление может не подойти — решение владельца |
| Гости созвонов (без логина) | Ничего не меняем: карточек нет, в плитке буква |
| Сессия | 30 дней (`JWT_EXPIRE_MINUTES=43200`, как сейчас) или до «Выйти» |

## Устройство (кратко)

```
Вход:  шаг 1 пароль роли → шаг 2 личный пароль (создать/ввести) → шаг 3 карточка (если не заполнена) → сессия 30 дней
Данные:
  users            — учётка для входа (без изменений)
  user_profiles    — карточка, 1:1 с users.id (ФИО, компания, должность, фото, согласие, extra_json)
  companies        — из Companies.txt (название, сторона, активна)
  data/people/<user_id>/avatar-<hash>-512.webp, -96.webp — фото
  speaker_profiles.user_id — слепок голоса привязан к человеку (задел)
```

- Карточка отдельно от `users`: `users` — «как входит», карточка — «кто это». Новые данные о человеке — новые таблицы со ссылкой `user_id` или ключи в `extra_json`, карточку не ломаем.
- Карточку `app.db` хранит, но наружу (MCP, внешний агент, экспорт) она **не отдаётся** без отдельного решения.

## Шаг 3. Карточка: модель и сервис

Модель `user_profiles` (`app/app/models/user_profile.py`):

| Колонка | Тип | Смысл |
|---|---|---|
| `user_id` | PK, FK `users.id` ON DELETE CASCADE | |
| `last_name`, `first_name` | str(100) | обязательны |
| `company_id` | FK `companies.id`, null | обязательна для завершения |
| `job_title` | str(150) | обязательна |
| `avatar_key` | str(64), null | хеш файла фото; пусто — фото нет |
| `voice_consent_at` | datetime, null | когда человек сохранил карточку с уведомлением; пусто — согласия нет (отозвано или карточка не заполнена) |
| `voice_consent_text_version` | str(16), null | версия текста уведомления, который он видел (`CONSENT_TEXT_VERSION` в коде; текст меняется — версия растёт) |
| `completed_at` | datetime, null | анкета заполнена полностью; пусто — на портал не пускаем |
| `extra_json` | text, `{}` | запас полей без миграций |
| `created_at`, `updated_at` | datetime | |

`services/user_profile.py`:
- `get_profile(db, user_id)`, `display_name(profile, fallback)` → «Имя Фамилия»;
- `validate(fields)` — ФИО: буквы, пробел, дефис, апостроф; длина 1–100; обрезка пробелов, первая буква заглавная не навязывается; должность 2–150; компания — активная из `companies`;
- `complete_onboarding(db, user, fields, avatar_bytes)` — всё сразу, одной транзакцией; `completed_at = now`, `voice_consent_at = now`, `voice_consent_text_version = CONSENT_TEXT_VERSION`;
- `update_own(db, user, fields)` — ФИО, должность (без компании и без согласия);
- `withdraw_voice_consent(db, user_id)` / `restore_voice_consent(db, user_id)` — только для админской консоли;
- `set_company(db, user_id, company_id)` — только для админской консоли;
- `is_complete(profile)` — все обязательные поля и фото на месте.

**Слияние дублей** (`user_identity._reassign_user_rows`): `user_profiles` нельзя переносить общим `UPDATE` (PK `user_id` → конфликт, если карточки есть у обоих). Правило: остаётся карточка победителя; если у него нет — переносится карточка проигравшего вместе с каталогом фото; у обоих — оставить более полную (`completed_at` позже), вторую удалить вместе с файлами. Тест обязателен.

Тесты `test_user_profile.py`: валидация, завершение, неполная карточка ≠ complete, `update_own` не меняет компанию, слияние (4 варианта).

## Шаг 4. Фото

`services/avatars.py` (Pillow уже в `venv`, 12.3):
- приём: ≤ 10 МБ; тип — по содержимому (`Image.open` + `verify`), JPEG/PNG/WebP/HEIC-нет (HEIC с iPhone → понятная ошибка «сохраните как JPEG» или конвертация, если Pillow умеет — проверить на шаге);
- защита от «бомб»: `Image.MAX_IMAGE_PIXELS` ~ 40 Мп;
- `ImageOps.exif_transpose` (поворот по EXIF), затем **удалить все метаданные** (GPS, модель телефона);
- центральный квадрат → `512×512` и `96×96`, WebP качество ~85;
- файл: `data/people/<user_id>/avatar-<sha1[:16]>-512.webp` и `-96.webp`; запись во временный файл + переименование; старые файлы удаляются после успешной записи новой пары;
- `avatar_key` = хеш — он же версия для кеша браузера.

Маршруты:
- `GET /people/{user_id}/avatar?size=96|512&v=<key>` — только вошедшим пользователям портала; `Cache-Control: private, max-age=31536000, immutable` (при смене фото меняется `v`);
- `GET /m/{token}/avatars/{user_id}?size=…` — гостю созвона, **только** если `user_id` — участник этой встречи (шаг 8).

Тесты `test_avatars.py`: JPEG с GPS в EXIF → в результате метаданных нет; повёрнутое по EXIF фото выпрямлено; PNG с прозрачностью; не-картинка с расширением `.jpg` → 400; > 10 МБ → 413; огромное разрешение → 400; путь `user_id` не выходит из `data/people`; чужой без входа → 401.

## Шаг 5. Вход: шаг 3 «Карточка»

- `/auth/login/personal` и `/auth/login/setup`: если карточка не завершена — сессию **не** выдавать, вернуть `{step: "profile", ticket}` (новый пропуск, 15 минут: фото и ввод занимают время), иначе — сессия.
- `POST /auth/login/profile` (multipart): `ticket`, `last_name`, `first_name`, `company_id`, `job_title`, `avatar` (файл) → `complete_onboarding` → сессия 30 дней.
- `GET /auth/login/profile/options?ticket=…` — список активных компаний (`id`, `name`; **без стороны**) и текст уведомления с версией.
- Токен сессии получает `pf: true` (карточка завершена). `_check_personal_password` → переименовать в `_check_session_gates`: при `required` без `pp` или без `pf` → 401. Кто уже вошёл до обновления — при следующем запросе уйдёт на вход и дозаполнит карточку.
- Журнал действий: «Заполнена карточка».

Тесты (`test_login_profile.py`): первый вход — setup → profile → сессия; повторный вход с заполненной карточкой — personal → сессия сразу; без фото / без компании / неактивная компания / пустое ФИО → 400 с понятным текстом; после сохранения записаны `voice_consent_at` и версия текста; старая сессия без `pf` → 401; пропуск шага profile нельзя использовать для `setup`/`personal` и наоборот.

## Шаг 6. Страница входа: форма карточки

`login.html`, третий вид формы (как шаг 2, на месте):
- «Фамилия», «Имя» (`autocomplete="family-name"` / `given-name`), «Компания» (`<select>`, одна компания — выбрана сразу), «Должность» (`autocomplete="organization-title"`);
- «Фото»: круг-предпросмотр, кнопка «Выбрать фото» (`accept="image/*"`); на телефоне — «Сделать снимок» (`capture="user"`); подсказка «лицо крупно, по центру — фото обрежется в квадрат»;
- **уведомление** над кнопкой (не галочка): «Сохраняя карточку, вы соглашаетесь, что ваш голос в записях созвонов используется для автоматического распознавания, кто говорит» + «подробнее» (раскрывающийся текст: что храним — числовой слепок голоса, не запись; зачем; как отозвать — через администратора);
- кнопка «Сохранить и войти»; ошибки под полями; фото отправляется одним запросом с полями.

Проверка: браузер — полный первый вход; телефон 375 px без горизонтальной прокрутки; выбор фото с телефона (эмулятор Android, `docs` в памяти `mobile-testing-tools`).

## Шаг 9. Созвоны: имя и фото в плитке

- `meetings.join_member`: `display_name` участника-сотрудника = «Имя Фамилия» из карточки (сейчас — логин). **Осторожно:** имя попадает в стенограмму и в `speaker_profiles` (слепки по строке имени) — сверить, что сопоставление спикеров со старыми слепками не ломается (шаг 10 снимает зависимость от имени).
- `meeting_room.js`: для `identity` вида `member:<id>` вместо буквы в `meeting-tile-placeholder` — `<img>` фото 96 px (512 — в крупной плитке ведущего); ошибка загрузки → буква, как сейчас. Метаданные участника LiveKit не трогаем (там живёт `denoise`) — адрес фото строится из `identity`.
- Гостевая страница `/m/{token}`: фото сотрудников — через `/m/{token}/avatars/{user_id}`; сами гости — буква (без изменений).

Проверка: синтетический созвон (как в находке 45: участник-сотрудник + гость), скриншоты плиток с камерой и без; рекордеры не запускать вне сервера (память `recorders-single-instance`).

## Шаг 10. Голос: привязка к человеку (задел)

Только основа, автосбор слепков — отдельный план:
- миграция: `speaker_profiles.user_id` (null, FK `users.id`, индекс);
- при подтверждении спикера, который — сотрудник с карточкой (`member:<id>`), слепок пишется с `user_id`;
- **без согласия** (`voice_consent_at` пусто — отозвано админом) слепок с `user_id` не создаётся; отзыв → удалить слепки этого `user_id`;
- `scripts/link_voice_profiles.py` — показать слепки, чьё имя совпадает с логином или «Имя Фамилия» сотрудника, и привязать по подтверждению (ничего не привязывать автоматически).

Тесты: слепок без согласия не пишется; отзыв согласия удаляет слепки; привязка не трогает слепки гостей.

## Критерий готовности

- Без личного пароля и без заполненной карточки (ФИО, компания, должность, фото) сессия не выдаётся; старые сессии без них — 401.
- Фото хранится без метаданных, в двух размерах, отдаётся только вошедшим и гостям той встречи, где человек участник.
- Компания — только из `Companies.txt`; сторона не видна пользователю, есть в данных; сменить компанию может только админ (консоль/скрипт).
- Слияние дублей пользователей не теряет карточку и фото.
- В созвоне у сотрудника без камеры — его фото; у гостя — буква.
- На форме карточки — уведомление об автоматическом согласии; дата и версия текста сохранены; после отзыва админом слепок с `user_id` не создаётся, старые удалены.
- Все тесты и смоук проходят; телефон 375 px без горизонтальной прокрутки.
