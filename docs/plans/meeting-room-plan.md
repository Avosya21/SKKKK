## 1. Суть

Комната — вход для сырых дорожек. Если участник не понимает, включён ли у него микрофон, слышат ли его, куда делась трансляция экрана и почему из колонок звучит его же голос, — созвон превращается в разбор полётов (ровно как встреча (тестовой): из 15 минут по делу — полторы). Плюс каждая такая беда портит запись: два входа = две дорожки, ПК, играющий гостя в комнату, = протечка в микрофон.

## 2. Цель

Три вещи должны быть верны **всегда**, без перезаходов и «нажми ещё раз»:

1. Индикаторы говорят правду: мик/камера у каждого, качество связи, «микрофон молчит».
2. Трансляция экрана — на предсказуемом месте: **последняя запущенная всегда сверху**, у всех, на любом экране.
3. Кнопка «Звук» выключает **весь** входящий звук и держит его выключенным до конца сессии.

И одно про запись: один человек — одна identity на всю встречу, сколько бы раз он ни перезаходил.

## Дыра 1. Флаги микрофона и камеры врут

**Симптом.** У других участников плитка показывает «мик выключен», хотя он включён; исправляется только после того, как человек сам пощёлкает mute. Список участников (`_fillRoster`) врёт так же.

**Где в коде.** `meeting_room.js::_bind` — набор событий, по которым зовётся `_renderTiles`. `_fillTile`/`_fillRoster` читают `person.isMicrophoneEnabled` / `isCameraEnabled` — у `RemoteParticipant` это `getTrackPublication(Source.Microphone)?.isMuted === false`; пока публикации нет — `false`. `ParticipantConnected` приходит раньше `TrackPublished`, между ними плитка нарисована с «выключено» и не перерисуется.

**Что сделать.** Один `redraw` (через `requestAnimationFrame`, чтобы пачка событий при входе не рисовала десять раз) на `TrackPublished`, `TrackUnpublished`, `TrackSubscribed`, `TrackUnsubscribed`, `TrackStreamStateChanged`, `ParticipantNameChanged`, `ConnectionQualityChanged`. `TrackSubscribed` продолжает звать `_attachTrack`, но после него — `redraw`. Флаг «нет публикации» отличать от «выключен»: без публикации микрофона — серый чип «нет микрофона», с публикацией и `isMuted` — красный «выключен».

**Тест** (`test_meetings.py`, по конвенции строковый): в `_bind` есть `RoomEvent.TrackPublished` и `RoomEvent.TrackSubscribed` → `redraw`; в `flagChip` три состояния.

**Что получится.** Критерий 1; та же перерисовка закрывает половину дыры 2 (класс `is-screen-lead` пересчитывается при подписке на видео экрана).

## Дыра 2. Трансляция экрана прыгает, теряется под закреплением, не имеет приоритета

**Симптом.** На телефоне экран то в первом ряду, то в середине сетки. У человека, который закрепил чью-то плитку, трансляции не видно вовсе. Две трансляции подряд — непонятно, какая где. Требование Пети: **последняя запущенная — сверху**, предыдущая — обычной плиткой.

**Где в коде.**
- `chosenVideoPub`: экран вытесняет камеру в плитке того же человека — камера ведущего пропадает, а порядок плиток = порядок входа.
- `_renderTiles`: `is-screen-lead` считается здесь, а подписка на видео идёт через `_attachTrack → _paintVideo` без `_renderTiles` (закрывается дырой 1).
- `_renderTiles`: `if (LAYOUT_SPEAKER && !_pinLocked && !hasScreen) follow speaking` — при `_pinLocked` экран не получает spotlight; в `has-focus` остальные плитки — миниатюры 4.4 rem (телефон) или `display:none` (десктоп), `adaptiveStream` гасит видео в невидимой/крошечной плитке.
- CSS: `.is-screen-lead .meeting-tile-screen { grid-row: 1 }` только в `@media (max-width: 575.98px)`; в планшетной ветке (713) и на десктопе (315) экран не поднимается.

**Что сделать.**
1. **Экран — отдельная плитка.** `_participants` → список «плиток»: для каждого человека плитка камеры + по плитке на каждую публикацию `Source.ScreenShare` (`id = meeting-tile-screen-{trackSid}`, класс `meeting-tile-screen`, подпись «Экран — Имя»). `chosenVideoPub` оставляет только камеру. Своя трансляция тоже показывается плиткой (сейчас человек не видит, что именно шарит).
2. **Порядок.** `Map trackSid → Date.now()` при `TrackPublished`/`LocalTrackPublished`; плитки экранов сортируются по убыванию, идут первыми; самая свежая получает `is-lead`. Люди — после, в порядке входа. DOM переупорядочивать через `tilesEl.append(...)` в нужном порядке (без пересоздания узлов, чтобы `<video>` не перезапускался).
3. **Приоритет над закреплением.** Появление новой трансляции: `_pinLocked = false`, spotlight на `is-lead`; уход трансляции — spotlight на следующую трансляцию, иначе возврат к сетке. Ручное закрепление человека при живой трансляции разрешено, но кнопка «Экран сверху» в доке возвращает lead одним нажатием.
4. **CSS** — одно правило для всех ширин: `.meeting-tiles .meeting-tile-screen.is-lead { grid-column: 1 / -1; grid-row: 1; }` вместо трёх media-веток; `.is-screen-lead` остаётся только для пропорций рядов на телефоне.
5. Для трансляции — `publishDefaults.screenShareEncoding`/`screenShareSimulcastLayers` и `contentHint: "detail"` (текст читаем при низком битрейте, см. дыру 6).

**Тесты** (`test_meetings.py`): в js есть `meeting-tile-screen-` (плитка на trackSid) и сортировка по времени публикации; в css правило `.meeting-tile-screen.is-lead` вне media; старый assert `".meeting-tiles.is-screen-lead .meeting-tile-screen" in phone` в `test_phone_meeting_grid_fits_all_tiles` меняется осознанно — правило переезжает из media-ветки в общую.

**Что получится.** Критерий 2. Живая проверка — R5/R6.

**Потолок.** «Предыдущая трансляция подменяет видео» реализуется как обычная плитка экрана (не как замена камеры): подмена камеры прячет лицо ведущего, а это то, на что Петя жаловался («не видно, что губы шевелятся»).

## Дыра 3. «Звук» выключается не насовсем

**Симптом.** ПК с выключенным «Звуком» играл в колонки голос Даши (и не играл Петю). Даша в одной комнате с ПК слышала себя с задержкой; всё, что играет ПК, попадает и в микрофон ПК (протечка, `final-plan.md` дыра 5).

**Где в коде.** `toggleSound → _applyOutputMute`: `node.muted = !this._soundOn` на всех `<audio>`; `_attachTrack` ставит то же новым узлам. Но `livekit-client` в `attachToElement` (`livekit-client.umd.js`: `t.muted = 0 === n.getAudioTracks().length`) при каждом (пере)присоединении трека **снимает `muted`**. Переприсоединение к уже существующему `<audio>` делает сам SDK при смене `MediaStreamTrack` (`setMediaStreamTrack` → `attachedElements.forEach(attachToElement)`): полный reconnect, переподписка, смена слоя. У Пети был VPN — reconnect-ов хватало. Трек Пети-2 был присоединён уже после нажатия «Звук выкл.» и не переприсоединялся — молчал; трек Даши пережил переприсоединение — заиграл. Сходится с наблюдением «только Дашу».

**Что сделать.** Выключение звука = **отписка**, не `muted`: `pub.setSubscribed(false)` на всех аудиопубликациях удалённых участников (включая `clean-*` от `primaryanalitics-dfn`); в `_attachTrack` — `if (!this._soundOn && track.kind === "audio") return`; на `TrackPublished` при выключенном звуке — сразу `setSubscribed(false)`. Включение = `setSubscribed(true)` + `_reattachAudio`. Нет пакетов — нет звука, что бы SDK ни делал с элементами; заодно экономит трафик на телефоне. `_applyOutputMute` удалить.

**Тест** (`test_meetings.py`): в js есть `setSubscribed(false)` в пути `toggleSound` и guard `!this._soundOn` в `_attachTrack`; текущий assert `"node.muted = !this._soundOn" in js` снимается осознанно — этот механизм и есть дыра.

**Что получится.** Критерий 3. Живая проверка — R4: ПК молчит, даже когда другие перезаходят.

**Потолок.** Если «Звук выкл.» на ПК был нажат не был (гипотеза Пети — «кнопка не работает», доказать по стенограмме нельзя), R4 это и покажет: после правки тишина обязана быть. Дополнительно — тост при нажатии «Звук выключен: вы никого не слышите», чтобы состояние было очевидно.

## Дыра 4. Гость при перезаходе — новый человек

**Симптом.** Петя дважды зашёл с телефона → две identity `guest:691c…` и `guest:fff08…`, два «Петя с телефона» в списке (первый висит до таймаута LiveKit), две дорожки в `manifest.json`, две полосы в лаб (`final-plan.md` дыра 6).

**Где в коде.** `services/meetings.join_guest`: `identity = "guest:" + secrets.token_hex(16)` на каждый POST.

**Что сделать.** Гость получает устойчивый `guest_id` на устройстве: `meeting_public.html` при первом входе кладёт `crypto.randomUUID()` в `localStorage` под ключ `primaryanalitics-guest-{token}` и шлёт его в `join` (`{display_name, guest_id}`). Сервер: `identity = "guest:" + sha256(public_token_hash + ":" + guest_id)[:32]` — детерминированно, не раскрывает `guest_id`, не даёт подделать чужую identity без токена. `MeetingParticipant` — не плодить строки: `upsert` по `(meeting_id, identity)`, обновлять `display_name` и `joined_at`. LiveKit при входе с той же identity сам отключает старую сессию (`DUPLICATE_IDENTITY`) — призрак в списке исчезает мгновенно. Валидация `guest_id`: длина ≤ 64, `[A-Za-z0-9-]`, иначе 400.

Побочный эффект на запись: рекордер пишет в тот же `guest-{stem}.wav` (`start_record` переиспользует writer, `PcmWavWriter` добивает паузу тишиной) — одна дорожка на человека **до** ASR, дыра 6 `final-plan` становится страховкой. Потолок: перезапуск `voice_cleaner` посреди встречи откроет файл на запись заново (`wave.open(..., "wb")`) — записать в `final-plan.md` §7 как известное ограничение.

**Тесты** (`test_meetings.py`): два `join` с одним `guest_id` → одна identity и одна строка `meeting_participants`; разные `guest_id` → разные identity; `guest_id` с мусором → 400; без `guest_id` (старый клиент) → как раньше, случайная identity.

**Что получится.** Критерий 4; R1.

## Дыра 5. Микрофон «есть», но молчит — никто не предупреждает

**Симптом.** Первая сессия Пети: трек опубликован, 165.8 с чистой тишины, 0 слов. Он не выключал микрофон и не знал, что его не слышно, пока не перезашёл. Причины типичны для телефона: микрофон занят другим приложением после лобби (`stopPreview` → `setMicrophoneEnabled(true)` открывает устройство заново), системный mute, Bluetooth-гарнитура «подключилась» без маршрута.

**Где в коде.** В комнате нет ни метра своего голоса (он есть только в лобби, `_startMeter`), ни подписки на `RoomEvent.LocalAudioSilenceDetected` (SDK 2.15.8 его шлёт после публикации, если трек тихий), ни на `MediaStreamTrack` `mute`/`ended` локального трека, ни на `RoomEvent.MediaDevicesError`.

**Что сделать.**
1. `_bind`: `LocalAudioSilenceDetected` → тост «Микрофон молчит. Проверьте устройство» с кнопкой «Перезапустить» (`_restartMic(this._dfn3On)`); `MediaDevicesError` → тот же тост с текстом `mediaErrorText`.
2. Локальный `MediaStreamTrack` (`localMicTrack(room).mediaStreamTrack`): `onmute`/`onended` → тост + попытка `_restartMic`; после `_restartMic` заново навесить обработчики.
3. Свой голос виден: на своей плитке тонкая полоска уровня — переиспользовать `_startMeter` с потоком `new MediaStream([mediaStreamTrack])`; на чужих плитках уровень не нужен — `isSpeaking` уже подсвечивает. Публиковать факт «молчу» остальным: `setAttributes({mic_silent: "1"})` (`canUpdateOwnMetadata` в JWT уже есть) → у остальных на чипе микрофона «молчит».
4. Не выключать `stopPreview` до `connect`, а передавать уже открытый `MediaStreamTrack` из лобби в `setMicrophoneEnabled`? SDK этого не умеет напрямую — делается через `createLocalAudioTrack` + `publishTrack`. Дороже; сначала пункты 1–3, и если R3 покажет, что перехват устройства между лобби и комнатой повторяется, — этот пункт.

**Тесты** (`test_meetings.py`): в js есть `LocalAudioSilenceDetected`, `MediaDevicesError`, `mic_silent`.

**Что получится.** Критерий 5; R3.

## Дыра 6. Качество связи невидимо, публикация не по силам телефону через VPN

**Симптом.** «Квадратиками вижу», «задержка пошла» — участники гадают, VPN ли это.

**Где в коде.** `connect`: `adaptiveStream`/`dynacast` включены, но `videoCaptureDefaults`/`publishDefaults` не заданы (720p по умолчанию, simulcast-слои дефолтные); `ConnectionQualityChanged` не слушается.

**Что сделать.**
1. `ConnectionQualityChanged` → чип качества на плитке (`excellent`/`good` — ничего, `poor`/`lost` — значок и title «Плохая связь»), у себя — ещё и строка статуса «Связь плохая: видео снижено».
2. `Room` опции: `videoCaptureDefaults.resolution = isPhoneClient() ? VideoPresets.h360 : VideoPresets.h540`, `publishDefaults: { simulcast: true, videoSimulcastLayers: [h180, h360], screenShareEncoding: ScreenSharePresets.h720fps5, dtx: true, red: true }`. Меньше исходящего с телефона — меньше «квадратиков» у остальных.
3. TURN сейчас только UDP 3478 (`livekit_env.build_livekit_yaml`), запасной путь — ICE/TCP 7881. VPN/корпоративные сети часто пускают только 443 — **не в этом плане**, но записать в §8.

**Тесты**: строковые — `ConnectionQualityChanged`, `videoSimulcastLayers`, `VideoPresets.h360` в js; `test_meetings.py::test_join_returns_livekit_when_configured` не трогать.

**Что получится.** Критерий 6; R7.

## Дыра 7. Ссылка на встречу недоступна из комнаты сотрудника — и запрос «отдельное приложение»

**Симптом.** Даша: «Хочу как отдельное приложение для созвонов, чтобы при заходе появлялась ссылка». У сотрудника `copyInvite` находит ссылку только в `sessionStorage` вкладки, где встречу создали; с другой вкладки/устройства — тост «возьмите в карточке встречи», а в карточке её нет: токен показывается один раз, в БД `public_token_hash` (решение в `DECISIONS.md`).

**Что сделать — две части.**

1. **Приложение.** Web App Manifest (`static/meeting.webmanifest`: `display: standalone`, `start_url` = `/m/{token}` для гостя, `/projects/{id}/meetings/{mid}/room` для сотрудника, иконка) + `<link rel="manifest">` в обоих шаблонах и подсказка «Добавить на экран» на телефоне. Это и есть «отдельное приложение» без второго фронтенда. Service worker не нужен (комната без сети бессмысленна).

**Тесты**: `test_meetings.py` — манифест отдаётся, шаблоны содержат `rel="manifest"`; при варианте B — `GET /projects/{id}/meetings` возвращает `public_url` для admin/manager, `test_create_meeting_returns_public_link_once` переписывается осознанно.

## 8. Чего этот план не делает

- **TURN через 443/TLS.** VPN и корпоративные сети, где открыт только 443, останутся на ICE/TCP 7881. Отдельная работа по `livekit_env.build_livekit_yaml` и порту на роутере.
- **Задержку сети не лечит.** Только показывает её (дыра 6) и снижает исходящий битрейт телефона.

- **Клиентский DFN3** остаётся выключенным; канон — сервер `primaryanalitics-dfn`.
- **Видео/экран в запись** не пишутся (см. `final-plan.md` §7).
- **JS-раннер (node/vitest)** не заводится; проверка — pytest-строки + selfcheck в браузере + контрольный созвон.
