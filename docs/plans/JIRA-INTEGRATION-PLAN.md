# PrimaryAnalitics — Подключение Jira: задачи трекера рядом с памятью проекта

Статус: **этапы 1–3 сделаны (2026-11-11):** чтение по ключу; личные токены, выбор проектов и загрузка задач с вложениями как материалов; обновление по кнопке и расписанию. Решения Р1–Р6 приняты владельцем 2026-11-11. Живой прогон на настоящей Jira — впереди (§4).
Повод: те же проекты ведутся и в Jira; портал знает, о чём договорились на созвонах, Jira — что заведено в работу. Сейчас они не связаны.
Цель: видеть задачи Jira рядом с задачами портала и находить расхождения: «договорились, но в Jira нет», «в Jira закрыто, а на созвоне всплыло снова».

## 0. Факты

| Что | Значение | Откуда |
|---|---|---|
| Задачи портала из материалов | сущности `entity_type=task` в `entities`: описание, исполнитель, срок, статус, источник (реплика, цитата) | `services/entities.py` (`TaskItem`), `services/task_board.py` |
| Ручные задачи | таблица `manual_tasks`; в контракт внешнего агента не уходят | `models/manual_task.py`, DECISIONS Р3 |
| Статусы портала | `open`, `in_progress`, `done`, `cancelled` | `task_board.STATUSES` |
| API задач портала | `GET/POST /projects/{id}/tasks`, `PATCH …/tasks/{entity_id}`, `PATCH/DELETE …/manual-tasks/{task_id}`, `GET …/deadlines` | `routers/knowledge.py` |
| Настройки проекта | `projects.settings_json` — место для привязки «проект портала ↔ ключ проекта Jira» | `models/project.py` |
| Внешнего идентификатора у задачи нет | ключ задачи Jira хранить пока негде | — |
| Облачная Jira | вход: почта + API-токен (Basic); поиск `/rest/api/2/search/jql`, страницы через `nextPageToken`; прежний `/search` удалён | документация Atlassian |
| Jira на своём сервере | вход: персональный токен доступа (Bearer), с версии 8.14; поиск `/rest/api/2/search`, страницы через `startAt` | документация Atlassian |
| Категории статусов Jira | `new`, `indeterminate`, `done` — одинаковы для любых схем статусов | поле `status.statusCategory.key` |

## 1. Как начать (этап 1)

1. В `.env` заполнить блок «Jira» (образец — `.env.example`): `JIRA_BASE_URL`, `JIRA_API_TOKEN`; для облачной Jira ещё `JIRA_EMAIL`.
2. `venv\Scripts\python.exe scripts\jira_pull.py` — проверка ключа и список доступных проектов.
3. `venv\Scripts\python.exe scripts\jira_pull.py --project КЛЮЧ` — задачи проекта в `data\jira\КЛЮЧ.json` и сводка на экране.
4. Ключи нужных проектов перечислить в `JIRA_PROJECT_KEYS`; тогда `scripts\jira_pull.py --all` выгружает все сразу.

Для ИИ-агента разработки те же данные отдаёт локальный MCP-сервер `tools/jira_mcp.py` (`primaryanalitics-jira` в `.mcp.json`, только чтение):
`jira_status`, `jira_projects`, `jira_project_statuses`, `jira_issues`, `jira_search`, `jira_issue`. Имена людей и тексты задач из Jira в git и документы не переносятся.

Режим выбирается сам: `JIRA_EMAIL` задан — облако, пуст — свой сервер. В Jira ничего не пишется, база портала не меняется.
Ключу достаточно прав на чтение проектов. Сертификат внутреннего сервера не проходит проверку — `JIRA_VERIFY_TLS=false`.

## 2. Решения владельца (приняты 2026-11-11)

- **Р1. Из Jira забираем всё и работаем локально.** Задачи, комментарии и вложения скачиваются на сервер портала и разбираются общим конвейером; в Jira портал ничего не пишет.
- **Р2. Токен у каждого свой.** Пользователь вставляет личный токен Jira на главной странице; токен хранится зашифрованным (ключ из `SECRET_KEY`), виден только владельцу, в ответы и журнал не попадает. Адрес Jira один на сервер (`JIRA_BASE_URL`).
- **Р3. Проекты выбирает пользователь.** После подключения — список проектов Jira с галочками; загружаются только отмеченные (admin, manager).
- **Р4. Совпадающие проекты вливаются в существующие.** Соответствие «проект Jira → проект портала» задаёт admin (в списке — «влить в …» или `PUT /projects/{id}/jira/link`). Без соответствия создаётся новый проект тем же способом, что «Новый проект». Ключ Jira привязан не более чем к одному проекту портала.
- **Р5. Доступ — по видимости в Jira.** Проект из Jira видит тот, чей токен видит его в Jira: участие выдаётся при подключении токена и при новой привязке, перепроверяется по расписанию и снимается, если Jira перестала показывать проект (`jira_grants`). Участие, выданное вручную, и свои проекты не трогаются.
- **Р6. Обновления — опросом.** Портал сам проверяет Jira каждые `JIRA_SYNC_MINUTES` минут (по умолчанию 30) и по кнопке; изменённая задача заменяет прежний документ. Вебхуки Jira — позже, если опроса станет мало (нужны права администратора Jira).

Следствия и пределы:
- Ключ к проектам — токен человека: по расписанию привязка обновляется токеном того, кто её создал, иначе любого, кому доступ выдан по Jira. Токен отозван — привязка показывает ошибку, пока кто-то не подключит рабочий токен.
- Материалы, загруженные из Jira, записаны на загрузившего пользователя; по правилам портала он сохраняет проект в «своих», даже если Jira доступ отозвала.
- Задачи Jira становятся документами, а не строками блока «Задачи»: поручения из них извлекает общий конвейер. Статусы и исполнители Jira попадают в текст документа.
- Удалённые в Jira задачи из портала не убираются; удалённый вручную материал заново не скачивается.
- На проект берётся не больше `JIRA_IMPORT_MAX_ISSUES` задач (свежие первыми); аудио и видео из вложений — только при `JIRA_IMPORT_MEDIA=true`.
