# PrimaryAnalitics — Две полосы локальной модели: чат отвечает во время обработки

Статус: **выполнен (2026-10-05).** Все решения приняты (П1–П3, Р1–Р3), этапы 0–7 сделаны; Р1 по замеру — модель выгружается на GPU-шаги ASR (§0.2); приёмка — §0.3. pytest 1398 passed, карта сходится с кодом.
Повод: пока идёт расшифровка, чат отвечает 409 «GPU занят расшифровкой». На созвоне 2026-10-05 (задача 699) это длилось 1 ч 43 мин, хотя около 85 минут из них модель была в памяти и простаивала для чата.
Цель: Qwen 3.8 всегда загружается с одними и теми же проверенными настройками и работает в два потока. Первый поток — обработка (воркер). Второй — только чат и черновики MCP-агента, строго по очереди. Когда все задачи выполнены, модель выгружается.

## 2. Целевая схема

### 2.1. Две полосы

| Полоса | Кто | Сколько одновременно | Порядок |
|---|---|---|---|
| Фоновая | только воркер: расшифровки, документы, автопроверки, выжимки, ТЗ, кадры, вспомогательные процессы `asr/lab_proof.py` и `asr/lab_sense.py` | 1 (воркер последовательный по устройству) | очередь задач `jobs` |
| Чат | только API: ответы чата и черновики MCP | 1 | FIFO по времени прихода, общая для всех пользователей и проектов |

- Обращения API к модели вне чата переходят в очередь воркера как задачи (этап 3). Тогда «строго по очереди» держится везде, и одновременно к модели идёт не больше двух запросов.
- Полоса чата — очередь «по талонам» внутри процесса API (`threading.Condition`, номер талона). Порядок не ломается при одновременных запросах. Позицию в очереди видно в `/chat/status`.
- Каждый вызов модели указывает полосу явно. Тест не пускает вызов модели из процесса API вне полосы чата.

### 2.2. Профиль модели — один источник правды в репозитории

- `config/lmstudio/qwen-profile.json` (имя уточнить на этапе 1): ключ модели, `contextLength`, `parallel=2`, flash-attn, KV q8_0, MTP, параметры выборки. Поля те же, что в пресете `swift-qwen-24gb` сейчас.
- Перед каждой загрузкой код записывает профиль в конфиг модели LM Studio (`.lmstudio/.internal/user-concrete-model-default-config/<indexedModelIdentifier>.json`), как сейчас делает `run_server.ps1`, и загружает модель явными флагами: `lms load <key> --gpu max -c <ctx> --parallel 2 --ttl <страховка> -y`.
- После загрузки код сверяет `lms ps --json` (`contextLength`, `parallel`, `status`). Если не совпало — выгрузка, ошибка в журнал и в `/health/ready`. Модель с неправильными настройками не используется.
- `run_server.ps1` читает тот же профиль, а не держит свою копию.
- Автозагрузку (JIT) выключаем. Иначе любой запрос мимо нашего кода поднимет модель с `parallel=1` и TTL 1 ч.

### 2.3. Загрузка и выгрузка (хранитель модели)

- `services/llm_keeper.py`: `ensure_loaded()`, `mark_busy()/mark_idle()`, `maybe_unload()`. Межпроцессный замок `data/locks/llm_model.lock` вокруг проверки, загрузки и выгрузки.
- Загружена ли модель, смотрим по `GET /api/v0/models/<id>` (`state == "loaded"`), а не по `/v1/models`.
- Загружает тот, кому модель нужна: воркер перед фазой LLM, API перед ответом чата или черновиком MCP.
- Выгружает только воркер, в цикле простоя, если одновременно: нет задач `queued/running`, полоса чата пуста и не ждёт, нет активных отметок «занято», простой ≥ `LMSTUDIO_IDLE_UNLOAD_SEC`.
- Страховка `--ttl`: если процессы PrimaryAnalitics упали, модель не висит в памяти вечно. TTL должен быть заметно больше самой длинной паузы между вызовами внутри задачи.

### 2.4. Бюджет окна

- Окно `n_ctx` выбирается на этапе 0 из 48k и 56k. Доли: чат ≤ 22 000 токенов (промпт + ответ), фон ≤ остаток.
- Перед отправкой запрос оценивается (символы → токены, коэффициент калибруется на этапе 0 по `prompt_tokens`). Фоновый запрос, который не помещается в свою долю (финальная сборка ТЗ, 16–20 тыс. на ответ), берёт исключительный режим: дожидается конца текущего ответа чата, и пока он идёт, следующий ответ чата не начинается.
- Чат, который не помещается в свою долю, ужимает контекст (выжимки документов и допконтекст режутся первыми). Заодно он отвечает быстрее: почти всё время ответа уходит на чтение промпта.

### 2.5. ASR и память

- По решению Р1. Если замер разрешает — `prepare_for_asr` больше не выгружает модель, а только проверяет свободную память. Если нет — выгружает, и чат на время ASR показывает «Идёт распознавание речи, вопрос в очереди».
- Контейнер GigaAM останавливается сразу после распознавания последней дорожки, а не после кадров.

### Этап 1. Профиль и хранитель модели

**Где.** `config/lmstudio/…`, `services/llm_keeper.py` (новый), `services/gpu_phase.py`, `services/llm.py`, `run_server.ps1`, `config.py` (`LMSTUDIO_CONTEXT_LENGTH`, `LMSTUDIO_PARALLEL`, `LMSTUDIO_IDLE_UNLOAD_SEC`, `LMSTUDIO_LOAD_TTL_SEC`), `.env.example`.
**Что.** §2.2–2.3. `lmstudio_model_loaded` / `check_llm_provider` / `prepare_for_llm` переходят на `state`. JIT выключается (настройка LM Studio + проверка при старте: включён → предупреждение в `/health/ready`). Выгрузка по простою в цикле воркера. В журналах `llm.load`, `llm.verify`, `llm.unload` с причиной.
**Тест.** Профиль пишется в конфиг модели. Аргументы `lms load` совпадают с профилем. Расхождение `lms ps` с профилем → выгрузка и ошибка. Нет задач и чата + простой → `unload`; есть задача или талон → нет. Состояние читается из `/api/v0`, а не из `/v1/models`. Живая проверка: два цикла «задача → простой → выгрузка → вопрос в чате → загрузка», `lms ps` каждый раз показывает `parallel=2` и нужное окно.
**Готово.** Модель поднимается только нашим кодом и только с профилем, выгружается после простоя.

### Этап 2. Полосы и очередь чата

**Где.** `services/llm_lanes.py` (новый), `services/llm.py` (параметр полосы во всех `*_raw`), `services/chat.py`, `services/agent_inbox.py`, `routers/knowledge.py`, `routers/project_mcp.py`, шаблон и JS чата.
**Что.** §2.1. Убрать 409 «GPU занят расшифровкой» и `asr_busy`. Очередь чата FIFO с позицией в `/chat/status` («В очереди: N», «Загружаю модель…», «Отвечаю…»). Защита от двойного вопроса: проверка «уже ждёт ответа» и создание сообщения под одним замком на пару проект+пользователь. Отсчёт «ответ не получен» (`CHAT_STALE_MINUTES`) идёт от начала генерации, а не от постановки в очередь.
**Тест.** Три одновременных вопроса от разных пользователей отвечаются строго по порядку прихода, одновременно генерируется не больше одного. Черновик MCP встаёт в ту же очередь. Чат отвечает, пока задача расшифровки `running`. Двойной клик — одно сообщение. Тест-страж: вызов модели из процесса API вне полосы чата → ошибка.
**Готово.** Во время обработки созвона чат отвечает. В LM Studio одновременно не больше двух запросов (`queued` в `lms ps` = 0).

### Этап 3. Фоновые вызовы из API — в очередь воркера

**Где.** `services/queue.py` (новые виды задач, например `tz_rebuild` и `summary_rebuild`), `workers/gpu_worker.py` (`_run_other_job`, метка `kinds=`), `routers/knowledge.py` (`rebuild-tz`), `routers/speaker_profiles.py` (пересборка выжимки), карточка «Фоновая работа».
**Что.** Кнопки ставят задачу и сразу отвечают «поставлено в очередь». Результат виден в карточке «Фоновая работа». Новые виды ставятся, только если запущенный воркер их понимает (`DECISIONS.md:334`).
**Тест.** Кнопка → задача `queued` → воркер выполняет по порядку. Старый воркер без нового вида — задача не ставится, понятная ошибка.
**Готово.** API обращается к модели только через полосу чата.

### Этап 4. Бюджет окна и исключительный режим

**Где.** `services/llm_lanes.py`, `services/llm.py`, `services/chat.py` (ужатие контекста), `services/tz.py` (оценка).
**Что.** §2.4. В журнал вызова добавить символы промпта рядом с `prompt_tokens`, чтобы коэффициент сверялся на живых данных.
**Тест.** Фоновый запрос сверх доли ждёт ответа чата и не даёт начаться следующему. Чат сверх доли ужимается до лимита. Под нагрузкой (параллельный чат + сборка ТЗ) в журнале LM Studio нет `failed to find free space` и `exceeds the available context size`.
**Готово.** Нагрузочный прогон этапа 0 повторён без ошибок окна.

## 4. Риски

- **Память при ASR.** Расширение окна до 56k может не поместиться рядом с GigaAM и диаризацией. Тогда либо окно 48k, либо выгрузка перед ASR (Р1). Решается замером этапа 0, не на глаз.
- **Скорость.** Два потока делят одну карту: при одновременной работе каждый запрос медленнее. Чат при этом всё равно отвечает за минуты, а не после конца обработки. Замер этапа 0.
- **Исчезающая память Windows.** Если Windows выгружает видеопамять в обычную, это замедляет всё без ошибок. При замерах следить за общей памятью GPU в «Диспетчере задач». Если увидим выгрузку — отключить «CUDA Sysmem Fallback Policy» для LM Studio (решение пользователя).
- **Обновление LM Studio** может сменить формат конфига модели или поля `lms ps --json`. Проверка после загрузки (§2.2) это поймает.

## 5. Не делаем

- Вторую модель или облако для чата: текст проекта остаётся локальным.
- Больше двух потоков: прошлый опыт (`n_parallel=4`) показал, что окно делится и ломается.
- Возврат тройного ASR.
