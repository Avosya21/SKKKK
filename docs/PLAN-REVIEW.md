# Ревизия плана SKKKK

Дата ревизии: 2026-08-18. Проверялся `docs/PLAN.md` целиком: соответствие железу (одна GPU 24 ГБ, Windows 11), совместимость библиотек, корректность конвейера, полнота схемы данных, тестируемость.

Итог: концепция подтверждена, **три параллельных ASR сохраняются**. Найдено 3 блокирующих дефекта, 5 существенных и 6 мелких. Все исправления внесены в план и в пофазовые файлы `docs/stages/`.

---

## Блокирующие дефекты

### B1. Склейка стенограммы не влезает в контекст

**Было:** три полные расшифровки часового-полуторачасового созвона подаются в Gemma одним запросом.

**Почему ломается:** 1.5 часа русской речи — это примерно 13–15 тысяч слов, в токенах Gemma порядка 25–35 тысяч на одну расшифровку. Три варианта плюс ответ — это 100k+ токенов. Веса `gemma-4-31b-qat` в Q4 занимают около 18–19 ГБ из 24 ГБ, на KV-кэш остаётся 4–5 ГБ. Такой контекст туда не помещается: LM Studio либо обрежет вход (и половина разговора молча исчезнет из стенограммы), либо упадёт по памяти.

**Исправление:** склейка по **окнам**. Аудио режется по границам тишины VAD на окна 120–180 секунд, каждое окно проходит все три ASR, Gemma склеивает окно за окном, финал сшивается. Побочная польза: тексты трёх движков гарантированно выровнены по времени, и Gemma сравнивает одно и то же место разговора, а не «начало Whisper против середины GigaAM».

Добавлена таблица `transcript_windows`.

### B2. Три ASR в трёх потоках одного процесса

**Было:** «загрузка в VRAM всех трёх моделей, запуск параллельно в разных потоках».

**Почему ломается:** faster-whisper тянет CTranslate2 со своей сборкой CUDA/cuDNN, GigaAM и T-one — PyTorch со своими библиотеками. На Windows это разные DLL с одинаковыми именами в одном адресном пространстве; типичный итог — падение при инициализации второй модели либо тихое повреждение памяти. Второе: PyTorch на Windows не отдаёт VRAM обратно системе после `empty_cache()` надёжно, поэтому фаза LLM получит уже занятую карту.

**Исправление:** три ASR запускаются как **три отдельных процесса** (`subprocess`), параллельно, каждый со своим окружением. Требование «только три параллельно» выполняется полностью; меняется способ параллелизма. Выход процесса гарантированно освобождает VRAM.

### B3. LM Studio поднимет Gemma посреди фазы ASR

**Было:** оркестратор выгружает Gemma перед ASR.

**Почему ломается:** в LM Studio включена автозагрузка модели по запросу (JIT). Любой пользователь, открывший чат в момент транскрипции, отправит запрос на `/v1/chat/completions`, LM Studio молча загрузит 19 ГБ поверх работающих ASR и уронит обработку по нехватке VRAM.

**Исправление:** JIT-автозагрузка в LM Studio выключается, приложение управляет загрузкой само. Плюс на уровне очереди: пока есть job с `phase=asr` в статусе `running`, запросы `phase=llm` ждут, а UI чата показывает «идёт транскрипция».

## Существенные замечания

**S1. Дедупликация.** Не было хеша файла. Один и тот же созвон, загруженный дважды, обрабатывался бы дважды (и удваивал сущности в графе). Добавлено поле `artifacts.sha256` и проверка на дубль в рамках проекта.

**S2. Деградация ансамбля не фиксировалась.** План говорил «два из трёх — всё равно зовём Gemma», но нигде не хранилось, какие движки отработали. Добавлены таблица `asr_runs` и поле `artifacts.asr_engines_json`; в UI у стенограммы видно, полный ли был ансамбль.

**S3. Таймауты и ретраи.** Обращения к LM Studio на длинных окнах могут идти минутами. Не были заданы таймауты, ретраи и поведение при обрыве. Задано: таймаут на запрос, до двух повторов, при исчерпании — `error` с указанием окна, остальные окна не теряются.

**S4. Порог схожести 0.82 взят из воздуха.** Это гиперпараметр, а не константа. В этап 5 добавлен тест-калибровка на реальных парах сущностей; порог живёт в `projects.settings_json`.

**S5. Подмена личности.** При входе Telegram ID вводится руками, значит любой сотрудник может назваться чужим ID и получить чужие уведомления. Для 20 человек за периметром это приемлемо, но зафиксировано как принятый риск с опциональным подтверждением через код от бота (этап 8), а не забыто.

## Мелкие замечания

**M1.** Имя файла от пользователя не должно попадать в путь на диске — только в БД. `stored_filename` генерирует система (защита от обхода каталога).

**M2.** Не было ограничения на длительность аудио. Введён предел и предупреждение: 3 часа — это порядка 60–90 окон.

**M3.** `tmp/` не чистился при ошибке — добавлена уборка по завершению job в любом исходе.

**M4.** Не было бэкапа `app.db` — добавлен в этап 8 (`VACUUM INTO` по расписанию).

**M5.** Не был описан граничный случай «тишина / нет речи»: три пустых расшифровки не надо отдавать в Gemma, артефакт закрывается с пометкой «речь не обнаружена».

**M6.** Не было формата логов. Задан один формат строки на всех сервисах, файлы в `data/logs/`.

## Что подтверждено без изменений

- Ролевая модель на трёх паролях, `position` как метка — достаточно для 20 человек.
- SQLite + sqlite-vec на старте, Qdrant/Neo4j на этапе 10.
- Ollama `bge-m3` на CPU: 1024-мерные векторы, VRAM не трогает, скорость для 20 человек достаточная.
- Пересборка ТЗ не на каждый файл, конфликты по умолчанию в ручную очередь.
- Telegram через HTTP Bot API без polling внутри FastAPI.
