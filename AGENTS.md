# PrimaryAnalitics — агент проекта

Читай и следуй:

1. `docs/PLAN.md` — единый пошаговый план
2. `docs/PROJECT-MAP.md` — карта проекта: каталоги, пайплайны, API, зависимости (обновлять вместе с кодом)
3. `docs/stages/STAGE-NN-*.md` — детальное исполнение текущего этапа: шаги, проверки, тесты, критерий готовности
4. `docs/DECISIONS.md` — что нельзя менять без пользователя
5. `docs/TESTING.md` — как и что тестируем
6. Правила в `.cursor/rules/`, скилы в `.cursor/skills/`

## Как ориентироваться в проекте (индекс)

Сначала индекс, потом `grep`. Индекс знает код Python/JS/шаблонов/CSS, документы, решения, связи и историю; каждый ответ — с адресом `путь:строка`. План и устройство: `docs/plans/PROJECT-INDEX-PLAN.md`.

```powershell
venv\Scripts\python.exe scripts\search_project_map.py "почему исчерпывается пул соединений"   # вопрос по смыслу
venv\Scripts\python.exe scripts\search_project_map.py --symbol log_activity                     # где определено
venv\Scripts\python.exe scripts\search_project_map.py --callers log_activity                    # кто вызывает
venv\Scripts\python.exe scripts\search_project_map.py --route "GET /projects/1/artifacts"       # роут: права, вызовы, таблицы
venv\Scripts\python.exe scripts\search_project_map.py --table meeting_participants              # столбцы, кто пишет/читает
venv\Scripts\python.exe scripts\search_project_map.py --env WEB_PORT                            # переменная или константа
venv\Scripts\python.exe scripts\search_project_map.py --ui "выбрать микрофон"                   # кнопка -> шаблон -> JS -> API
venv\Scripts\python.exe scripts\search_project_map.py --tests rate_limit                        # какие тесты и как запустить
venv\Scripts\python.exe scripts\search_project_map.py --changed                                 # незакоммиченное по функциям
venv\Scripts\python.exe scripts\search_project_map.py --invariants                              # что нельзя ломать
venv\Scripts\python.exe scripts\search_project_map.py --graph log_activity --depth 2            # граф: кто вызывает и что вызывает
venv\Scripts\python.exe scripts\search_project_map.py --deps app/app/services/tz.py             # зависимости модуля
venv\Scripts\python.exe scripts\search_project_map.py --orphans                                 # кого никто не вызывает
venv\Scripts\python.exe scripts\search_project_map.py --import-cycles                           # циклы импортов
```

- В запрос клади имена из репозитория (функция, файл, URL, `id` элемента), а не бытовое описание. Слабый ответ помечен «уверенности нет».
- Найденное проверяй в самом файле: индекс — указатель, а не источник истины.
- После правок кода: `venv\Scripts\python.exe scripts\index_project_map.py` (только изменённые файлы, секунды). Хуки git и `restart.ps1` делают это сами.
- Граф зависимостей: атлас `docs/project-map/DEPENDENCIES.md`, свод `docs/project-map/graph-modules.json`, страница `/admin/map/graph` (§16 карты). Пересборка после правок кода — `venv\Scripts\python.exe scripts\export_project_graph.py`.
- Диагностика: `scripts\index_doctor.py`; расхождения карты с кодом: `scripts\check_map_drift.py` (`--fix` пересоздаёт реестр модулей).
- Для ИИ-агентов тот же поиск доступен как MCP-сервер `primaryanalitics-index` (`.mcp.json`, `tools/projindex_mcp.py`); для людей — страница `/admin/map`.


**LightRAG (граф кнопок/API/БД):** Docker `tools/lightrag`, запросы — `py scripts/lightrag_query.py "вопрос"`. См. `tools/lightrag/README.md`.

Работай только внутри `D:\Primary_Analitics`.

## Карта проекта всегда актуальна (обязательно, для любого ИИ и человека)

Любое изменение портала отражается в `docs/PROJECT-MAP.md` **в том же коммите**. Не важно, какой ИИ или инструмент работает: правило держится на git-хуках и тестах, а не на памяти агента.

- Что описывать: новый или изменённый роут, таблица БД, переменная окружения, модуль, скрипт, промпт, кнопка или экран, статус, шаг конвейера. Куда: роут — §5, таблица — «Модели» в §7, переменная — §12.2, остальное — по §14 карты (там же пошаговые правила).
- Перед коммитом: `venv\Scripts\python.exe scripts\check_map_drift.py --fix`, затем без `--fix` (код выхода 0), индекс — `scripts\index_project_map.py`.
- Принуждают хуки (`scripts\install_hooks.ps1`; `INSTALL.bat` и `restart.ps1` ставят их сами, состояние — `scripts\index_doctor.py`): `pre-commit` сверяет карту с тем, что идёт в коммит (роуты, таблицы, переменные, файлы кода, реестр, манифест); `commit-msg` при правке роутеров, моделей, `config.py`, шаблонов, JS/CSS и `.env.example` требует карту в коммите либо строку `Карта: не требуется — причина` (опечатка, стиль, правка без нового поведения); тот же `pre-commit` через `scripts\scan_personal_data.py --staged` не пускает в коммит имена людей и названия компаний из базы портала (находки видны только в консоли: заменяй вымышленными). Эти же проверки гоняет тест `app/app/tests/test_map_coverage.py`.
- Хук отклонил коммит — исправь карту, а не хук. Запрещено: `git commit --no-verify`, снимать хуки, ослаблять проверки или расширять списки исключений ради прохода, писать «Карта: не требуется» там, где поведение изменилось.
- В рабочей копии могут быть чужие незакоммиченные правки (другая сессия, другой ИИ): коммить только свои файлы и только свои фрагменты общих файлов карты.

## Названия коммитов

На GitHub у каждой папки и файла видно название последнего коммита, который их менял, — по нему человек понимает, что это за раздел. Поэтому:
- один коммит — одна тема (раздел проекта); несвязанные правки — отдельными коммитами;
- заголовок по-русски, до ~60 символов, вида «Раздел: что сделано» — «Встречи: выбор микрофона во время созвона», «Портал: кнопка «Исправлено» в шапке», «Карта проекта: запуск и HTTPS»;
- без служебных слов («snapshot», «fix», «wip», «правки»); подробности — в теле коммита.

## Список «Исправлено» (кнопка в шапке списка проектов)

После правки, которая меняет функционал или качество сервиса для пользователя, добавь запись в `app/app/changelog.json` (`{"date": "ГГГГ-ММ-ДД", "text": "..."}`, дата — сегодняшняя) и покажи формулировку пользователю в ответе. Рефакторинг, тесты, документацию, индекс, внутренние скрипты — не вносить.

Формулировка — одна короткая фраза для человека, без имён файлов, функций и моделей-внутрянки:
- «Добавлена возможность …» — новая функция (что теперь можно сделать и в какой ситуации);
- «Исправлена проблема с …» — ошибка, которую видел пользователь;
- «Повышена точность/скорость …» — улучшение качества; допустимо коротко: «Диаризация до 8 спикеров. Повышена точность и скорость диаризации.»

Реализация идёт по этапам: стенд → каркас → очередь → **двойной слух ASR (Parakeet + GigaAM) + диаризация (Nemotron 3, откат Sortformer) + LLM** → документы → сущности/индекс → граф → ТЗ/чат → укрепление → службы.

Следующий этап не начинается, пока не выполнен «Критерий готовности» текущего. Не предлагай вернуть тройной ASR (Whisper + T-one + merge окон).
